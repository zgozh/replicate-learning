|---|---|---|---|
| `@Aspect` + `@Component` `:48-49` | 标成"切面"，并注册进 Spring 容器 | `@Aspect` 只声明"我是切面"，**还需要 Spring 把它当 Bean 管起来**，两件事缺一不可 | 只有 `@Aspect` → 容器不知道它的存在 → 切面不生效（注解白标，无任何报错） |
| `private final Gson gson = ...` `:59-70` | 自定义 Gson：把 `MultipartFile` 按**类型层级**适配成"只序列化 4 个元信息字段" | Gson 默认会反射进 `MultipartFile` 的所有 getter，**包括 `getInputStream()`**——那会去读整个文件流 | 不注册适配器 → 传 20MB 文件时，算指纹这一步读 20MB 进内存；且流是**一次性**的，被这里读掉后，业务里再读就是空流，**上传静默失败**（见 ⑩（隐含）） |
| `@Value("${ragent.eval.enabled:false}")` `:72` | 从配置读评测开关，缺省 `false` | 跑批/压测需要"临时关掉幂等"，这是运维手段；默认必须是关的 | 默认 `true` → 生产环境幂等整体失效而没人知道（配置项名字像个普通开关） |
| `if (evalEnabled) return joinPoint.proceed();` `:81-83` | 开关打开时**直接跑业务、不抢锁** | 放在最前面，是因为它是"这条切面整体旁路"的语义，去抢锁再判断就是白抢 | 放在抢锁之后 → 评测仍然会撞锁，开关失去意义 |
| `if (!lock.tryLock()) throw ...` `:88-89` | **非阻塞**抢锁；拿不到立刻抛"用户侧错误" | `tryLock()` 无参版本**不等待**：拿不到立刻返回 `false`。这正是"秒拒"——用户不该为前一次请求排队干等 | 用 `lock()`（会阻塞）→ 第二个请求线程挂在那里等 5 秒 → Tomcat 线程被占、前端白屏；高并发下线程池被打满 |
| `try { proceed() } finally { unlock() }` `:92-96` | 业务执行包在 `try`，解锁放 `finally` | **`finally` 保证"业务抛异常也必须解锁"**；否则一次业务失败就把锁永久留在 Redis 里，这个接口之后**所有人**都被拒 | 把 `unlock` 写在 `proceed` 之后（非 finally）→ 业务抛异常时锁不释放 → 该接口对全体用户"死锁"，直到锁超时（Redisson 看门狗默认可续期到线程结束，实际可能一直不释放） |
| `joinPoint.getTarget().getClass().getDeclaredMethod(...)` `:105` | 从**目标类自己的声明**上取方法，再取注解 | 代理类的方法可能没有注解（注解在原始方法上）；拿目标类能确保取到声明处的注解 | 直接 `signature.getMethod().getAnnotation(...)` → 某些代理场景下返回 `null` → 后续 `.key()` 空指针 |
| `idempotent-submit:path:%s:currentUserId:%s:md5:%s` `:140-145` | 默认 key = **接口路径 + 用户 + 参数指纹** 三维度 | 三维度合起来才等于"同一个用户、对同一个接口、用同一份参数发起的同一次操作" | 见 ② 场景四与 ⑩反例5：缺用户 → 别人顶掉你；缺参数 → 不同内容被判重复；缺接口 → 不同接口互挡 |

> **【讲解】视角卡：`tryLock()` 只是"抢锁"，可为什么必须让业务也包在 `try` 里？——锁的持有边界与"异常即泄漏"**
>
> 这段代码的结构是：**抢锁 → `try { 业务 } finally { 解锁 }`**。抢锁失败的分支在 `try` 之外，业务在 `try` 之内。为什么要这样切分？因为 `RLock` 是**有状态的资源**，而"有状态资源的释放"必须挂在 `finally` 上——这是所有锁/连接/流的共同规则，但幂等场景下的后果尤其严重。
>
> 想一下如果把 `unlock()` 直接写在 `proceed()` 后面（没有 `try`/`finally`）：业务正常返回时没事；但业务一旦抛异常（数据库超时、下游 500、参数校验失败……这些每天都在发生），执行流会**直接从抛异常处跳到方法外**，`unlock()` 那一行永远不执行。结果就是：这把锁**留在 Redis 里不被释放**。
>
> 关键在于"锁不被释放"和"普通内存泄漏"的严重程度完全不同。内存泄漏是慢慢积累；而**这把锁是按"三维度 key"命名的**——意味着"这个用户 + 这个接口 + 这份参数"这一组合被永久锁住。用户再点一次，永远收到"您操作太快"，而他自己什么都没做错。运营看到他反复投诉、开发去查却一切正常（日志里没有异常堆栈，因为是**别的请求**抛的异常导致的），排查方向很容易跑偏到"前端是不是重复提交了"。
>
> 所以这里的规则可以记成一句：**凡是"拿到了就必须还"的东西（锁、连接、文件句柄、事务），业务逻辑一律包在 `try` 里，归还动作一律放 `finally`**。这不是风格偏好，而是把"异常路径"和"正常路径"一视同仁——异常是常态，不是意外。

**★逐步回放（`idempotentSubmit` 的三条路径）**

场景：`@IdempotentSubmit` 标在某个提问入口上，小敏在 300ms 内点了两次；默认 key = `idempotent-submit:path:/api/chat:currentUserId:u1:md5:9f2a...`。

- **路径 A（首个请求，抢到锁）**：`:81` `evalEnabled=false` 跳过直通 → `:84` 取注解 → `:85` `buildLockKey` 因 `key()` 为空走 `:140-145` 拼三维度 key → `:86` `getLock(key)` → `:88` `tryLock()` 返回 `true` → `:91-93` 进入 `try`，调 `:93` `proceed()` 执行业务（这里耗时 5 秒）→ 业务返回 `"ok"` → `:94-95` `finally` 里 `unlock()` **立即释放** → `:97` 返回 `"ok"` ✅
- **路径 B（第二个请求，300ms 后到达）**：同样拼出**同一个 key**（同一用户、同一接口、同一参数）→ `:86` 拿到的是**同一把锁**（Redisson 按名字区分锁）→ `:88` 此时锁仍被路径 A 持有 → `tryLock()` 立刻返回 `false`（**不等待**）→ `:89` 抛 `ClientException("您操作太快，请稍后再试")` → **`:93` 的 `proceed()` 一次都没执行** ✅
- **路径 C（评测模式）**：`:72` 配了 `ragent.eval.enabled=true` → `:81` 判真 → `:82` 直接 `proceed()`，**不取锁、不拼 key**。跑批脚本连续提交相同请求也不被挡 ✅
- **失败路径**：业务内部抛异常（比如检索服务超时）→ `:93` 抛出 → 跳过 `:97`，直接进 `:94` `finally` → `:95` `unlock()` 仍然执行 → 异常继续向上抛。**锁被释放，接口不会"卡死"** ✅。若这里没有 `try`/`finally`（把 `unlock` 写成顺序语句），这条路径会让那把锁永久留存，**该用户对该接口对该参数的所有后续请求全部被秒拒**。

### 卡 2：Redis 单线程模型与 Lua 原子性 —— 为什么"三步必须合成一条"（★）

**L0 事实-源码**

| 事实 | 出处 |
|---|---|
| Redis 处理命令是**单线程**的（指命令执行阶段），命令之间串行、不会交错 | Redis 官方文档 *Redis is single threaded* |
| `EVAL`/`EVALSHA` 提交的整段 Lua 脚本，被 Redis 当作**一个整体命令**执行完，期间不插入其它客户端的命令 | Redis 官方文档 *Scripting with Lua* / *Atomicity of scripts* |

| 脚本中 `KEYS[n]` 用于传 key、`ARGV[n]` 用于传其它值；集群模式下必须把 key 放在 `KEYS` 里才能正确路由到分片 | Redis 官方文档 *Cluster and Lua* |

**设计要点**：
- **【核心约束】把"必须一条 Lua"写死**，是因为这是状态机型唯一的原子性红线：`SETNX` + `EXPIRE` 两条命令之间宕机，key 就永不过期，那条消息被永久拒绝——而这个 bug 在正常测试里**根本复现不出来**（要在极窄的时间窗内杀掉进程），只能靠写代码时就写对。
- **【禁止】里的"禁止进业务前写 CONSUMED"是刻意点名的**：AI 出于"先把状态置好再干活"的直觉，很容易把置终态提前，结果第一次失败、重投读到终态跳过 → **消息永久丢失且无人报错**（→ ⑩反例4）。
- **【验收标准】第一条"业务方法一次都没跑"比"返回了错误"更严格**：幂等的正确判据不是"接口报了错"，而是"业务副作用一次都没发生"。让 AI 按这个可观测的判据自测，而不是按"看起来拦截了"。

### 8. 最终沉淀（`开发任务`）：可迁移结论

**四条可迁移结论**：

1. **"重复"有两种时间尺度，要用两种机制**。同一刻挤进来（毫秒级）用锁——释放就能再来；隔一段又来（分钟级）用状态令牌——终态活到 TTL 才过期。用锁去防 MQ 重投会失效（锁早就释放了）；用状态令牌去防连点会误伤（第一次的令牌还在 TTL 内，用户正常第二次操作被拒）。
2. **"多步读改写"必须原子，`SETNX`+`EXPIRE` 这类写法是定时炸弹**。两条命令之间的宕机窗口极窄，所以它在测试里几乎不可能复现——**"测不出来"不等于"不会发生"**，这类正确性只能靠"写代码时就写成一条命令"来保证。
3. **幂等的正确判据是"业务副作用零次"，不是"接口返回了错误"**。测试要断言"目标方法一次都没被执行"（mock 验证 `proceed` 未被调用），而不是断言"抛了 `ClientException`"——后者可能业务已经跑了一半才抛。
4. **`@Around` 是唯一能做"幂等"的 AOP 通知类型**，因为只有它能决定"要不要调 `proceed()`"。同样地，`this` 自调用绕过代理、`@Transactional` 自调用失效——**同一个 AOP 代理机制的根本约束**，值得记成一条通用规则。

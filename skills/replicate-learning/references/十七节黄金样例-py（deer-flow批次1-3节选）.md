### 4.1 深潜：`端口就绪` 为什么必须单独等（本批最核心的概念）

**是什么**：一个进程 `fork` 出来只是"存在了"，它还要初始化（Python 要 import 半个 LangGraph、
Next.js 要绑路由、nginx 要读配置），**在这之前端口是没人监听的**。

**解决什么问题**：如果不等就起下一个服务，会出现两种很难查的故障：
① 前端起来了但 `/api/*` 全 502——因为 nginx 比 Gateway 先起，代理指向一个还不存在的上游；
② 脚本以为"都启动了"，打印成功，用户打开浏览器转圈。

**不用它会怎样**——本项目给了具体的代价数字：

```
Gateway  超时 30s      # 后端只需 import，30 秒足够；超了就是真挂了
Frontend 超时 300s     # 首次 make start 要跑 next build，300 秒是给它构建的
Nginx    超时 10s      # 读配置文件而已，10 秒不成就别等了
```

**代价分析**：等端口是**轮询**（`wait-for-port.sh:63-72`，间隔 1 秒），不是事件通知。
代价是最坏情况白等 N 秒（如 Gateway 真挂了也要等满 30 秒才报错）；收益是实现极简、
跨平台（Windows 上连 `lsof` 都没有，靠 PowerShell 兜）：
`wait-for-port.sh:36-59` 依次尝试 **PowerShell → lsof → ss → netstat** 四种探测手段。

> 为什么值得：如果换成"进程启动后 sleep 5"，在慢机器上会随机失败，在快机器上白等——
> 属于典型的"看起来能用、生产上会咬人"的实现。

### 6.1 `Makefile` —— 219 行里几乎没有逻辑，这是一件好事

**这一件解决什么问题**：一个多语言仓库（Python + Node + nginx + Docker）有十几种常用命令组合，
如果每个人都记 `cd backend && uv run uvicorn app.gateway.app:app --port 8001`，
用不了一周就会出现五种写法。Makefile 的作用是**把这些写法钉成唯一版本**。

**输入**：命令行上的目标名（如 `dev`）与可选变量（如 `SKIP_FRONTEND_BUILD=1`）。
**输出**：要么调用一个脚本，要么直接起进程。**它自己不做编译、不做配置解析、不做日志处理。**

**本件构造方式与实现手法**：
- **构造方式**：Makefile 不是被 `new` 出来的对象，它是 **`make` 进程的输入**；生命周期 = 一次
  `make <目标>` 的调用周期；每个 target 的 recipe 各起一个 `/bin/sh -c` 子进程，执行完即销毁。
- **实现手法**：**声明式目标表 + 变量抽象 + 解析期条件分支**。`ifeq ($(OS),Windows_NT)` 是
  **解析期**分支而非运行期判断——代价是两套路径要么都对、要么有一条没人测（⑬ 已知限制 ❌2）。

- **L1 机制拆解**：`uv sync` 做四件事——① 读 `pyproject.toml` 解析依赖图；② 与 `uv.lock` 对账，
  `--locked` 时**不一致直接失败**；③ 为 `.venv` 计算需要安装的集合；④ 实际安装。
- **L2 等价实现**：手写版 = `pip install -r` + 自己比对版本；**省略了什么生产边界**：锁文件
  完整性校验、workspace 成员传播、增量安装的哈希短路。
- **L3 设计取舍**：不加 `--locked` 会"顺手升级锁文件"——CI 与本地出现两份依赖真相；
  失败时间线：本地跑通、CI 挂——排查方向被误导到代码而不是环境。
- **L4 故障实证**：E3 实测 `--locked` 下锁文件被手工改动 → 立即失败（未实测：纯离线环境）。

**实物（deer-flow 批次1 节选）**：

**Q1：为什么 `Makefile:146` 的 `dev` 目标要先跑 `check.py`，而不是直接跑 `serve.sh`？**
A：`serve.sh` 在缺 `uv` 时会在 `uv sync` 阶段以一句网络/找不到命令的报错炸掉，
真正的原因被埋在下游。`check.py` 把"缺工具"提前到第一步，并且给出安装指引。
【反例5】也说明了反面的道理：它的输出是给人看的，**不能**当结构化接口用。

**Q2：`serve.sh:97-103` 的 `DEERFLOW_ROOTS` 为什么要按路径长度降序排？**
A：链接工作树的路径是主检出路径的子串。降序（最长/最深优先）才能把端口归属判给**正确**的那棵树；
升序会让深层路径先被浅层根匹配，归属判错。【⑥6.2 / ⑧卡2】

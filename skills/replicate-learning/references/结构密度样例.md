#### ⑦.4 边界与不变式（编号列表）

1. **入口唯一性**：一个 JVM 只能有一个 `main`（`RagentApplication.java:43`），全仓只有 `bootstrap` 模块有 `spring-boot-maven-plugin`（`bootstrap/pom.xml:49-52`）；`mcp-server` 若也需要入口，必须另建引导类，**不得复用这个**。
2. **扫描根不变式**：`@SpringBootApplication` 所在包（`com.nageoffer.ai.ragent`，`:18`）必须是所有业务模块的公共父包，否则 Bean 装配静默缺失。
3. **Mapper 集中登记不变式**：全仓 `@Mapper` 注解为 **0 处**，所有 Mapper 必须落在 `:32-40` 登记的 7 个包内；包名是字符串，重构不会编译报错。
4. **漏斗单调不变式**：`recall-budget ≥ default-top-k`（`application.yaml:140` vs `:139`）且 `rerank-candidate-limit ≥ default-top-k` 或 `= 0`（`:163`），违反即启动失败（`SearchChannelProperties.java:92-101`）。
5. **档位—装配一致不变式**：通道开关为 true 时，对应后端档位不能是 `none`（例：`rag.search.channels.keyword.enabled` 与 `rag.keyword.type`），违反即启动失败（`RetrievalChannelConfigValidator.java:95-98`）。
6. **DDL—配置一致不变式**：`vector(1536)`（`schema_pg.sql:563`）↔ `dimension: 1536`（`application.yaml:90`）；`vector_cosine_ops`（`:568`）↔ `metric-type: COSINE`（`:91`）。**这条没有启动校验**——靠人守（见 ⑩反例7 的教训）。
7. **启动期失败优于运行期静默**：能在启动期发现的矛盾（1~5 条）必须在启动期失败；不能在启动期发现的（外部依赖可达性、编码显示）必须写进 `.2 未实测清单`。

**通用四步**（落到上表任何一行）：

1. **先定插入点类型**：新增一种类型（走查表登记，只加不改）/ 换策略实现（调用方不感知）/ 改参数（改预算或配置）——三者改动面差一个数量级。
2. **找登记处与调用处**：`git grep -n "rag.graph.type"` 拿到"哪个类哪个方法哪一行在用"，**不凭印象**；本批的规律是：**档位键的登记处是 `RetrievalChannelConfigValidator.SPECS`（:72）与条件注解**，不是业务代码。
3. **只加不改**：能不动既有文件就不动；必须动时（新增 `<module>`、新增 `SPECS` 一行、新增 `@MapperScan` 包）写进"必须同步改"一栏，不留暗账。
4. **配一条机械验证**：新增档位/通道必须有"配错就启动失败"的验证——否则漏登记的表现为"**配置写了但不生效**"，这是最难查的一类（见 ⑧ 卡 2 与 ⑩反例7）。

#### 4.1 `条件装配`（本批 2 个核心概念之一）

**是什么**：Spring 判断"要不要创建这个 Bean"的机制。判断依据几乎总是**配置里的一个键**：

| 写法 | 含义 | 本仓实例 |
|---|---|---|
| `@ConditionalOnProperty(name="rag.keyword.type", havingValue="es")` | 值为 `es` 才装配 | `rag/src/main/java/com/nageoffer/ai/ragent/rag/config/EsClientConfig.java:40` |
| `@ConditionalOnProperty(prefix="ragent.engine", name="type", havingValue="agent")` | 组合键 + 值 | `agent/src/main/java/com/nageoffer/ai/ragent/agent/config/ConditionalOnAgentEngine.java:34` |
| `matchIfMissing = true` | **键缺失时也装配**（默认开） | `rag/src/main/java/com/nageoffer/ai/ragent/rag/config/MilvusConfig.java:44` |

**解决什么问题**：同一个 jar 要支持"用 pg 还是 milvus""用不用 ES""跑 workflow 还是 agent"三种以上组合。没有条件装配，就只能靠 `if` 在运行时分支，或者维护多份构建产物。

**不用它会怎样**：`rag.keyword.type: none`（本仓当前值，`application.yaml:74`）时若不装配仍有 `if` 分支兜底，业务代码里就会布满 `if (keywordEnabled)`；更糟的是**忘记兜底**——`KeywordSyncVectorStorePostProcessor` 的设计正是"容器里没有 `KeywordIndexService` 就跳过同步"，条件装配让"没装配"成为**可观测的事实**而不是隐藏状态。

**代价**：Bean 的"存在与否"变成**配置驱动的隐式事实**——`@Autowired` 一个当前档位下不存在的 Bean 会直接启动失败；读者必须同时看 yaml 和注解才能确定容器里有什么（这也是本批存在的理由）。

**③ 现场会怎样**：AI 对这类需求的**默认理解**是"用 Spring Initializr 生成一个单模块工程 + `Application.java` + `application.properties`"。产物**看着完全正确**（能编译、能启动、能打日志），但会踩五个坑，**而且它一个都不会报错**：
① 单模块结构 → 后续模块无处安放，只能重开工程；
② `.properties` 平铺 → 没有"档位"（`xx.type`）概念，切换实现只能改代码；
③ 没有启动期校验 → 配错静默生效；
④ 没有日志配置 → Windows/容器里中文乱码，功能却全正常；
⑤ 逐接口打 `@Mapper` 注解 → 与"集中登记"的既有约定不一致，新增模块时两边都要改。

**④ 你怎么定、落在哪**

- **谁**：你（复刻者）与后续照这份契约写业务的人；收益是"**能启动、能验收、改配置立刻有反馈**"。
- **现有代码为何不够**（具体到"没有哪个类 / 哪个文件"）：① 没有 `bootstrap` 模块 → 产不出可执行 jar；② 没有 `application.yaml` → 端口/库/档位/漏斗预算没有落点；③ 没有 `RetrievalConfigEnvironmentPostProcessor` 这类钩子 → 配置矛盾只能等运行期暴露；④ 没有 `schema_pg.sql` → 向量表与维度契约无处定义。

## 四、⑩ 反例一条（❌/✅ 代码对照块）

**看点**：❌ 块给"错法代码"，然后**现象 → 定位 → 根因 → 修复（✅ 块）→ 教训**五段；读者能"立等可见"看到修对长什么样。⓪e 的 E5 要求 ❌ ≥3 且代码块 ≥3 对——批次31-38 这类对照块**整体归零**、退化成纯文字清单。

```java
// ❌ application.yaml（示意改动，键的真实行号见 :139-140）
rag:
  search:
    default-top-k: 10
    recall-budget: 5          // 比 default-top-k 还小：召回 5 条却要 10 条最终结果
```

**现象**：进程起不来，控制台在 Spring Banner 之前就出现异常（注意时间点）：
`IllegalStateException: 检索预算漏斗不变式被破坏：recallBudget(5) < contextTopK(10)，召回扇出不得小于最终条数，请调大 rag.search.recall-budget 或调小 rag.search.default-top-k`
**定位**：异常消息里直接给了两个键名 → 直接读 `rag/src/main/java/com/nageoffer/ai/ragent/rag/config/SearchChannelProperties.java:86` 的 `afterPropertiesSet`。
**根因**：这是**第二道**校验（绑定之后、用对象校验）。注意一个细节：把 `recall-budget` 写成 `0` **不会**报错——因为 `resolveRecallBudget`（`:76-78`）把 `<=0` 解释为"未配置，回退到最终条数"；写 `5` 才会报。**"缺省"和"填小了"是两种语义。**
**修复**：

```java
// ✅ 二选一（推荐前者，保持召回扇出大于最终条数）
rag:
  search:
    default-top-k: 10
    recall-budget: 20         // 恢复 20
// 或者：接受"召回就是 10 条"，把 default-top-k 调到 ≤5
```

**教训**：**能被配置的数值关系必须由代码守着**——写进 ⑫ 第 5 条的【禁止】清单，也写进 ⑫ 第 8 条规则。

## 七、⑥【讲解】段的排版（v2.27 新增 · ⓪e E8）

**看点**：多个论证点**每点独立成段**（加粗标签起头）、段间空行、单段 36-80 字；**不写"其一/其二"内联枚举**。⓪e E8 判据：`【讲解】` 段最长行 ≤300 字。

**【讲解】为什么把 4 个注解全压在一个 46 行类里，而不是拆成多个 `@Configuration`**：

- **问题聚焦**：装配开关应该"集中可读"还是"分散就近"？
- **本仓选择**：集中。因为它们都属于**部署级契约**（一处改、全进程变），集中后"要开一个全局能力"只需看一个文件；
- **代价**：这个类成了"必须每次启动验证"的热点文件；且注解之间的关系（谁能覆盖谁）不在代码里表达；
- **替代方案对比**：① 拆成 `SchedulingConfig`/`MapperConfig`/`LogRecordConfig` 三个 `@Configuration` —— 更符合单一职责，但会把"启动契约"打散到三处，新人排查启动问题时要在三个文件间跳；② 用 `spring.factories`/自动装配把开关收敛到各模块自己的 `@Configuration`（本仓的 `ConditionalOnAgentEngine` 就是这种风格的局部实践）—— 模块自治更好，但"全局有哪些能力"没有一个统一入口。本仓按"启动契约集中、业务档位分散"来切：**全局开关集中在这里，可切换的档位（type 键）分散在各模块**（见 ⑥6.3 与阶段1批次2）。

## 第 2 件 · 一条请求打穿全栈（真跑出来的 Trace）

> **要求：不是画出来的想象链，是真跑一遍抓出来的**——起服务 → 发一个请求 → 从入口日志/调用栈逐层走到 DB/外部系统 → 原路返回，把每一跳的真实日志/类名贴进来。

```
（示例骨架，跑完替换成真实证据）
用户点"提问" → Nginx(:80) → Tomcat → DispatcherServlet(SpringMVC总入口)
  → AuthInterceptor（拦未登录） → RagController#chat（业务入口）
  → RagService → EmbeddingClient（外部 LLM 服务，真实HTTP调用日志…）
  → MySQL（检索向量，真实SQL/慢日志…） → 组装回答 → 序列化回前端
```

每一跳标注：真实类名/方法名 + 一句"它干嘛" + 贴一行真实日志佐证。

## 第 4 件 · 模块依赖方向图（切几块、谁能用谁）

```
bootstrap（装配，依赖所有人）
   ↑
rag（业务编排） ── rag 依赖 framework 与 infra
   ↑
infra-ai / system（支撑：模型接入、用户认证）
   ↑
framework（地基：零业务名词，出参/校验/日志等横切）
```

| 模块 | 一句话职责 | 删掉它，哪个业务问题会回来 |
|---|---|---|
| framework | 全项目共用地基 | 每层各写一份出参/校验，改一次规格改十处 |
| … | | |

**依赖方向规则**：稳定在下、易变在上；地基不许依赖业务，业务可依赖地基。

## 第 5 件 · 业务约束 → 架构决策推导链（为什么会这么选型）

| 业务约束（非功能需求） | 需要的技术能力 | 备选方案 | 选了谁 | 不选别人的理由 / 代价 |
|---|---|---|---|---|
| 检索要快（QPS 1000+、延迟 <1s） | 高速检索 | ES / PG 全文 / 向量库 | … | ES 重、运维贵；向量量小用 PG 够 → 先简单后升级 |
| 提问会话要连续 | 服务端状态 | 内存 / Redis / DB | Redis | 内存重启即丢；DB 太慢 |
| 计费不能丢单 | 持久 + 幂等 | … | DB + 唯一键 | … |

> **给读者的意义**：每行都是一道"为什么"的答案。以后在任何项目看到类似选型，都能用这张表反推它的约束。

## 使用纪律

1. 每批讲解的②架构位置**挂回本图**（"这个类在部署图/模块图的哪一处，为什么"）；
2. 发现全景图与代码不符 → 先弄清是图错还是代码怪，回填修正并记一笔；
3. 阶段收官时把全景图过一遍：删掉任何一件，"业务问题回来了吗"——答不上 = 还没懂，回去补。

V2 包自检命令：在 Skill 根目录运行 `python scripts/v2_selfcheck.py`。

## V2 硬约束

1. 知识教材写入被学习项目的 `NOTES/`；工程日志写入独立目录，不污染目标项目。
2. 三本书默认同步推进：源码实现、实验验证、架构挑战；一个批次至少留下三书索引链接。**单册优先模式（仅用户明确指令时启用，2026-09-17 · 用户要求 3）**：用户说"先要第一册 / 只要第一册 / 先不管二三册"时，可以集中火力推第一册、暂停其余——但暂停必须是**显式落盘的工程决策**，不是悄悄不做：① 状态文件写明"用户指令暂停：第X册（原话摘录）+ 预计何时补"；② 能力账本为被暂停的册各记一条欠账条目；③ 每次收尾报告的缺口清单列出暂停中的册；④ 用户回到"继续"且状态允许时，先确认是否恢复同步，恢复后第一批动作 = 回补欠账。三本书的框架不变，变的是节奏。
3. 关键机制和工程任务先记录用户预测或 AI 调查证据，再实现或实验；不得把推断写成事实。
4. AI 可以完成绝大多数检索、写作、脚本和代码劳动；用户只需参与关键预测、设计、审查和验收。
5. AI 不得自行宣布交付完成。最终状态只能由用户确认：`Accept`、`Accept with known risk`、`Reject and revise` 或 `Blocked with evidence`。
6. 每次运行结束前必须落盘当前状态、已完成产物、失败证据和下一步入口；上下文不足时也必须先落盘。

## 1. 任务定义

你的任务不是解释几个框架 API，也不是把项目复制出来，而是把一个真实项目转换成一套能让初学者逐步获得以下能力的教材：

1. 说清楚项目服务谁、解决什么业务问题、完整业务闭环如何运行。
2. 说清楚模块、进程、数据、依赖和外部系统为什么这样组织。
3. 读懂项目范围内每一个文件：源码、测试、配置、脚本、SQL、构建文件、前端资源、工具和部署文件。
4. 解释关键代码从入口到出口的真实执行链，并指出边界、失败模式和底层机制。
5. 判断 AI 生成代码是否正确、是否越界、是否缺测试、是否会在生产环境出问题。
6. 使用 Vibecoding 高效生成、修改、验证和演进项目，而不是只会拼接 API。

教材是主要交付物。交互、提问、手写练习和强制用户输入均为可选，不得阻塞主流程。

## 1.1 入口与动作路由

先从用户原话识别模式，不要让用户学习本技能的命令格式：

| 用户意图 | 立即执行的动作 |
|---|---|
| “学习/深度拆解/讲解整个项目/覆盖全部文件” | 定位项目根目录和教材目录，先完成项目考古，落盘四份基础地图，再从第一批继续 |
| “继续学习/继续复刻/next” | 读取磁盘状态、覆盖矩阵、最近教材和 Git 状态，从第一个未完成批次继续 |
| “只要产出/不要问我” | 采用默认路径和默认批次策略，直接扫描、讲解、验证、落盘；只有路径或安全边界无法推断时才提一个问题 |
| “先要第一册/只要第一册/先讲源码实现” | 进入**单册优先模式**：第一册照常全量推进；第二、三册显式暂停——状态文件、能力账本、缺口清单三处写明"用户指令暂停 + 预计何时补"（见 V2 硬约束 2）；三本书框架不变，只变节奏 |
| “讲解 X/讲第 N 批/讲某文件” | 补齐该对象所需的最小上下文，生成并落盘完整对象教程，同时更新矩阵和索引 |
| “验收/检查是否完整” | 不新增教材为主，审计覆盖矩阵、文件链接、证据等级、验证记录和索引，输出缺口清单 |

若用户同时给出原项目和复刻项目，原项目只读、复刻项目按用户授权使用；若只给出一个项目，默认把它作为被学习项目，教材写入该项目的 `NOTES/教学讲解/`，不擅自创建第二个复刻项目。

## 1.2 Flash 模型执行策略

本技能必须适合上下文和推理能力较小的模型执行。遵守以下机械流程：

1. **摘要先行**：先读取目录树、入口文件、依赖清单、状态文件和已有索引；不要一次性读取全项目源码。
2. **小批推进**：每批只处理一个闭环及其直接依赖；默认先选少量强相关文件，项目越大就增加批次，不把几十个文件压成一篇。
3. **上下文复用**：已解释概念只回链概念词典和旧批次；已读文件通过覆盖矩阵定位，不重复全文装入上下文。
4. **先写后续**：完成一批就立即写入教程、更新矩阵和状态，再开始下一批；不能把成果只留在对话中。
5. **证据优先**：每个结论先找路径、行号、命令或日志；找不到就写“未验证/推断”，不得用模型记忆补齐。
6. **单次运行有边界**：一次运行至少完成一个可读批次或基础地图；若无法完成，先落盘当前扫描结果、未完成清单和下一步入口。

## 1.4 复杂度适配与降级

- 业务/机制批次执行 L0-L3；能运行时再做 L4。
- 纯配置、资源、文档、锁文件和生成文件重点说明作用、来源、引用关系、风险和排除理由，不强行制造“等价实现”。
- 无法安装依赖、启动服务或访问外部系统时，保留静态源码分析，明确写“未实测”，并记录阻塞命令、错误原文、已排查范围和剩余风险。
- 文件很多时不得删除文件以换取篇幅；应增加批次，或将低复杂度文件集中成“逐文件清单 + 每文件语义/引用/风险”，仍在矩阵中逐项出现。

## 2. 使用者定位与教学原则

假设读者只具备一门语言的基本语法、能运行命令并阅读简单报错，不熟悉当前项目的框架、数据库、中间件、协议和部署方式。

必须遵守：

- 新术语第一次出现时，用白话、类比和本项目真实位置解释；
- 不用一个未解释的术语解释另一个术语；
- 每一层回答“它是什么、为什么存在、数据从哪里来、失败时怎样”；
- **教材必须自足（2026-09-17 · 用户要求）**：每段代码/命令之前先用一句话说清"这段解决什么、看完能答什么"——读者不能要靠翻外部文档才能跟上（2.18 起进闸门报告档，供存量工单）；
- 目标是读懂、复述、审查和指导 AI，不是手写速度；
- 不把 DTO、枚举、配置、测试、脚本视为低价值文件；
- 不因文件简单而降低解释完整性，只减少重复。

## 3. 输入与证据边界

开始前自动识别原项目、复刻项目、教材目录、`AGENTS.md`、README、贡献指南、CI 配置、技术栈、构建入口、运行入口、测试入口、外部依赖、已有教材、Git 历史和未完成事项。

优先使用本地真实文件、命令输出、测试结果、Git 历史和可定位源码作为证据。解释第三方底层行为时，优先查阅官方文档、依赖源码、字节码或最小实验。无法验证的内容必须标记为“推断”，不得伪装成事实。

默认不修改原项目；不得删除用户改动、已有教材或历史记录，只能增量补充或纠正。

所有结论标注证据等级：

- `事实-源码`：能回链到本地文件、类、方法和行号；
- `事实-实测`：由命令、测试、日志、堆栈或最小实验得到；
- `事实-历史`：由 Git 提交、差异或 blame 得到；
- `外部事实`：来自官方文档、依赖源码或协议规范；
- `推断`：根据现象和代码推导，但尚未直接验证。

教材不得把不同等级混写。性能、并发、安全、故障和生产行为尤其要说明证据等级。

## 4. 七阶段工作流

> **详细描述见 `spec/阶段工作流.md`**（阶段 A~C 在项目开工时各做一次、G 在每批收尾做；**日常写批次不必重读**）。
> 下表是每阶段的一句话职责与产出，用来判断"我现在该做哪一步"。

| 阶段 | 一句话 | 产出 |
|---|---|---|
| **A 项目考古** | 扫全仓（含构建/配置/测试/脚本/部署/前端，不只业务源码），建**四份基础地图** | 全景地图 / 覆盖矩阵 / 概念词典 / 完整性地图 |
| **B 业务建模** | 从角色、场景、规则、状态、异常、审计重建业务；**不许拿"用了某框架"当业务解释** | 每个核心能力：角色 + 端到端闭环 + 核心对象与约束 |
| **C 架构推导** | 运行时/依赖/请求/异步/数据/部署六张图，每个重要选择给**替代方案与代价** | 六张图 + 选择理由，全部回链真实类/方法/表 |
| **D 全文件教材化** | 按业务闭环分批（不按目录）；**每个文件有唯一覆盖状态**，排除也要有理由 | 批次讲解 + 覆盖矩阵更新 |

## 5. 阶段与批次切分

阶段按能力和系统层次组织，例如：系统全景与运行入口、基础设施与数据层、支撑能力、核心业务闭环、前端交互、AI/工具链、部署运维与横向对照。具体名称随项目调整，不得机械套用。

批次按一个可解释、可验证的业务或技术闭环切分。一个批次不应把互不相关的文件堆在一起，也不应为了省篇幅把几十个文件压成一篇目录导读。大型项目宁可增加批次，也不能降低单文件讲解质量。

每批开始前先写两个内部清单：

1. **外部调用穿透清单**：列出本批所有框架、ORM、SDK、中间件、协议和工具调用，标注是否已有词典或前批证据、要穿透到哪一层、证据出处和完成状态。
2. **讲解骨架清单**：列出每个文件的业务镜头、架构位置、实现要点、调用链、失败场景、测试视角、Vibecoding 视角和验证证据，填完后再写正文。

关键机制按 L0-L4 穿透：

- `L0 源码证据`：真实源码、依赖源码、字节码或官方实现位置；
- `L1 机制拆解`：框架替项目自动完成的具体步骤；
- `L2 等价实现`：不依赖当前框架的可读示范，明确它仍省略了哪些生产边界；
- `L3 设计取舍`：替代方案、代价和具体失败时间线；
- `L4 故障实证`：实际破坏、日志、堆栈或数据变化；无法运行时必须写“未实测”，退回 L3。

本批至少有一个新机制达到 L0-L3；核心类和中间件尽量达到 L4。已经在前批完整解释过的机制可以回链，但不能假装本批首次解释。

### 6.1 初学者代码讲解硬标准（含 6.1.1 三问注释密度 / 6.1.2 快照与不符三分类 / 6.1.3 排版硬标准）

批次正文不是代码审查摘要，也不是"类职责 + 几个关键片段"。对每个重要源文件必须让读者能从文件入口读到出口：

- **代码块里的每一行必须逐字来自真实源码（2026-09-13 血证，本技能最严重的一类事故）**：**禁止凭"这个类应该长什么样"重写代码**。写 ⑥ 节之前必须先打开该源文件；★类一律走脚本注入（见下条），非★类也必须复制粘贴后再加教学注释。判断标准是"逐行逐字与源文件一致"，**不是"读起来像"**。
  - 实测事故：某批次 12 个代码块全部凭设计描述重写——字段从 `headingHandler`+`chunkPacker`+`registry` 变成 `chunkers`+`assembler`、异常从 `ServiceException("Block 分块器注册冲突…")` 变成 `IllegalStateException("Duplicate BlockChunker for …")`、未知类型从"抛异常"变成"`continue` 跳过"、包名编成 `com.agenticrag`（该字符串在仓库与参照实现中**出现 0 次**）。整批代码行保真度仅 **55.3%**，而读者看不出任何异样。
  - 这类错误比"贴码不讲解"更危险：**它教的是一个项目里根本不存在的实现**，读者照着敲必然编译不过、行为也对不上。
  - 自查：写完后用 §6.4 C 组脚本跑正向保真度，**必须 100%**；任何一行对不上都要么改回源码、要么显式标注为反例/手写版并移入对应小节。
- **源码在后续阶段被重写时，旧批次讲解要显式标注"历史版本"**：同一文件被后来的批次改造（如某 Service 从单来源加载改成并行加载 + 摘要）后，旧批次讲解里贴的是**当时**的代码。这不是编造，但必须在代码块前写明「**此为该阶段的历史版本，已在 <哪个能力/阶段> 被重写为 <现在什么样>**」，否则读者对照仓库会以为教材错了。
- 先给"本文件要解决的一个问题"和输入/输出，再解释类、字段、构造器、方法之间的关系；
- **每个代码块/命令块之前先有一句白话开场**（"这段解决什么、它在整条链路里的位置"）——读者遮住其它文字只看这一句，就知道接下来这段代码该带着什么问题去读（教材自足，呼应 §2）；
- **每件点名构造方式与实现手法**（2026-09-17 · 用户要求）：**构造方式**——它是被谁 `new`/注入/装配出来的、生命周期归谁管（请求级/应用级/单例）；**实现手法**——它用了什么模式/数据结构/算法，以及为什么这么权衡（不是"用了工厂模式"四个字，是"为什么这里用工厂而不是 if-else 分派"）。读者合上书要能回答"它是怎么来的、为什么这么写"（2.18 起进闸门报告档）；
- 代码块默认贴完整文件；文件过长时按完整方法或完整职责段拆开，并明确上下段如何衔接；
- **★核心类禁止摘录式贴码**：★ 类必须贴完整文件（保留真实行号），**禁止用"关键片段/关键段"替代全类**。上下文预算紧张时，全类源码**一律用脚本从仓库文件直接注入**（如 python 文件对文件拼接，源码不经过对话手打）——手打/摘录必然截断且行号漂移，即使自检表写"关键段全贴"也不算合规；
  - **注入 + 教材注释的落地方案（2026-09-14 实战定型，直接照抄）**：讲解正文放 `<<<SRC:key>>>` 占位符；脚本按 `key → (源文件, 起始行, 结束行)` 逐行读真实代码并追加 `// :L<真实行号>`；另备一份 **anno 叠加表**（`key → {行号: 说明}`），命中的行写成 `// :L<行号>  ←教材：<说明>`。
    - 好处：① 源码 100% 逐字、行号即真实行号；② 源码不经过对话上下文（省 token、零抄写错误）；③ 教材注释与源码注释**分离且可重生成**——闸门报密度缺口时，只改 anno 表重跑即可，不用动正文。
    - 参考实现：agentic-rag 项目 `NOTES/工具-源码块注入.py`（plan.json 驱动、含"每行必须真实来自源文件"的自校验）与 `.tmp_b2/assemble.py`（只替换 ⑥ 节 + 校验节外逐字节不变）。
    - **要点表完整性铁律（2026-09-18 批次33-35 实录）**：每个注入块后的"逐行要点表"必须是**完整 Markdown 表格**——引导句（`**逐行要点表**：`）+ 表头 + **分隔行**（`|---|---|`）+ ≥1 数据行。**只有一行表头不是表格**：Markdown 渲染器要求表格第二行是分隔行，否则整段按普通文本显示、竖线原样裸奔——实测事故：注入管线占位只插了 `| 行 | 要点 |` 一行表头，三个批次 18 处全部渲染失败且闸门绿灯（闸门 ⑤ 的 TBL_ANCHOR 只认"表头行存在"，判不了表格完整性）。落地要点：① 占位阶段就把 `|---|` 分隔行与表头一起插，数据行可在注入时用 anno 表自动生成（每件采样 ≤14 条关键行，import 区说明可选采）；② 孤立表头自查判据——**表格首行**（上一行不是表格行）的下一行必须能通过"去掉 `|`、`-`、`:`、空白后为空"的判定（正则版 `[\s:\-|]+` 在部分实现下意外失配，去字符法更稳）；③ 表格前必须有空行、数据行内禁止裸竖线（文本里的 `|` 先替换成 `／`）。
  - **密度收敛两步法**：拼装后跑闸门 → 闸门会报"哪个块、多长的无注释连段" → 用脚本把连段的**具体行**打出来 → 只给那些行补 `anno` 条目 → 重拼重跑。通常 1~2 轮收敛，不要凭感觉乱补。
    - **连段定位铁律（2026-09-18 批次33 实录）**：第 2 步的脚本**直接 `import` 闸门脚本模块**（`importlib.util.spec_from_file_location` 加载 `gate_lecture.py`），用其 `parse_blocks`/`is_key_line`/`has_cjk_comment`/`mark_text_block_lines` 按 `check_density` 同口径逐行复算并打印连段的 `:Lnn` 行号——**禁止手工逐行推演**。实录：手工推演认为补注释后最长连段 ≤6，闸门仍报 10；同口径脚本一次定位出 3 处连段——全在两块 javadoc **之间**的纯代码区，手工推演错在以为 javadoc 区都是断点（实际"含中文的注释行"才算断连，`/**`/`*/` 围栏行本身不算）。判定要点：① `package`/`import`/空行/纯标点行不进密度（`is_key_line` 直接排除）；② 教材 `anno` 与源码自带中文注释（javadoc 正文）都算断连；③ 多补 anno 只会让连段变短、不引入新 FAIL，断开位置选信息量最大的行即可。
- 代码块中的关键行必须有**贴近代码的中文注释**，至少说明"这是什么、为什么需要、不这样会怎样"；不能只在代码块外概括；
- 逐行讲解不能只翻译变量名，必须解释控制流、数据变化、状态变化、异常路径和副作用；
- 每个陌生 API 第一次出现时，先解释调用前拿到什么、调用后产生什么，再解释框架/JDK 内部做了什么；
- 必须提供一条"从真实输入到真实输出"的逐步回放，并指出读者应先看哪几个方法；
- 对测试代码，要解释测试前置状态、动作、断言对象、为什么该断言能证明业务行为，以及没有该测试会漏掉什么；
- 对配置、构建和脚本文件，要解释每个有效字段或命令如何影响源码运行，不得只说"添加依赖/配置参数"。

"完整代码"不等于把未经解释的大段源码搬进来。若源码本身没有注释，教材应在代码块中补充教学注释，但必须标明哪些是教材注释，不能把注释冒充源码事实。禁止用"其余类似""这里不展开""显然""读者可自行理解"跳过关键逻辑。

#### 6.1.1 逐行三问注释密度标准（防"贴码不讲解"）

代码块**不能只贴代码 + 代码块外一两句概括**——这是最常见的敷衍形态。每个代码块必须同时满足：

1. **代码块内**：**关键行**行尾或行首有中文注释，标注真实文件行号（`:L` 格式），每条注释至少答三问之一（①这是什么 ②为什么这行要它 ③不这样会怎样）。
2. **代码块外**：紧跟一张**逐行要点表**（行号 / 讲解），讲控制流、数据变化、状态变化、异常路径、副作用——**不是重复代码块内的注释，而是展开"为什么这样写、不这样会怎样"的因果链**。
3. **★核心类**额外提供至少一条**逐步回放**（真实输入 → 每行发生什么 → 真实输出；含一条失败路径的回放），让读者看到"代码跑起来是什么样"。

**「关键行」与「非关键行」的判定（可机械复核，2026-09-13 定）**

| 类别 | 范围 | 是否计入密度 |
|---|---|---|
| **关键行（必须注释）** | 控制流（`if/else/for/while/try/catch/switch/case`）、方法签名行（含 `public/private/protected` 的声明）、状态变更赋值、外部调用（框架/IO/网络/DB/中间件）、`throw`/`return` 非平凡返回、注解行（`@Xxx`）、语义非自明的常量与字段 | ✅ 计入 |
| **非关键行（可不注释、不计入密度）** | 许可证头、`package`/`import`、纯括号行（`{` `}` `);`）、空白行、局部变量声明、getter/setter/`equals`/`hashCode` 等模板行、纯数据字面量行 | ❌ 不计入（但**连续 ≥10 行纯数据字面量**须在段首加一条整体说明） |

**密度机械判据（三项全过才合格）**：

1. **无注释连段**：剔除"非关键行"后，**连续 ≥8 行关键行没有任何中文注释 = 密度不足**（《原"连续 5 行以上无注释"作废：许可证头与 import 块天然连续无注释，旧判据导致所有批次必然不合格，无法执行》）；
2. **最低条数**：单个代码块内的教学注释条数 ≥ **关键行数 ÷ 12**（即平均每 12 行关键行至少 1 条），★类不得低于 5 条——**但一律以该块的关键行数为上限**（`min(key_n, max(5, ⌈key_n/12⌉))`）。**理由是它曾经不可满足**：注释只落在关键行上，"关键行 < 5 的 ★ 块"要求 5 条却最多只能有 key_n 条，怎么改都红（血证 H22；判据 2.12 修正）；
3. **★类方法覆盖**：★类每个方法至少有 1 条注释落在其**签名行或首行**（防止"整类贴码但一个方法也没讲"）。**按整类判定**：★类允许拆成多个职责段块，只要全篇合起来每个方法都被讲到即可（脚本 ③c 就是这么判的）。

**⚠️ 行号标注 ≠ 注释（2026-09-13 血证）**

`// :L123` 只是**定位器**，用来把教材与源码对齐；它**不构成任何讲解**。若代码块里 90% 以上的注释形如 `代码  // :L123` 而其后没有任何文字，读者遮住块外文字后什么也读不出来 = **不合格**，即使行号 100% 准确。实测教训：agentic-rag 项目 61 个批次讲解里 **97% 的行号标注是"裸行号"**（27,657 / 28,512），其中阶段12~14 全部批次为 100% 裸行号——「全类注入 + 行号标注」把 ★类贴码做到了 100%，却把"逐行讲解"降级成了"逐行编号"。

**教材补充的注释必须自报家门**：源码自带注释与教材补充注释必须可区分，教材补充的一律以 **`←教材：`** 开头（如 `// :L19  ←教材：TTL 而非 ThreadLocal，跨线程池仍能透传上下文`）。**注释标记按语言取前缀**（2.22）：`//` 用于 java/ts/go 等；`#` 用于 yaml/sh/python/toml/makefile；`--` 用于 sql——闸门的 `ANNO`/`L_ANNO` 三种前缀都认（此前只认 `//`，YAML/Shell 项目里写对的 `# :Lnn  ←教材：…` **一条都认不出来**）。禁止把教材注释冒充源码事实。

**密度自检**：随机翻到任意一个代码块，遮住代码块外的文字，**只读代码块内的注释**，初学者能否知道每行在干什么？如果代码块内注释密度不足以独立支撑理解，就是不合格。

**反面教材**（以下形态均不合格）：
- 贴完整代码 + 代码块外一句"要点：xxx"（无逐行要点表）
- **只有 `// :Lnn` 行号、没有任何文字说明**（2026-09-13 新增，本项目最高发的形态）
- 贴代码 + 逐行要点表但只翻译变量名（"L45：调用 normalize 方法"——没说为什么调、调完产生什么）
- 贴代码 + 要点表但跳过异常路径（只讲"正常跑会怎样"，不讲"LLM 超时会怎样"）
- ★类无逐步回放（读者看不到"代码跑起来是什么样"）
- ★类有方法没有任何注释落在签名行/首行（整类贴了，但读者不知道每个方法干什么）

### 6.1.2 批次源码快照与「不符」三分类（2026-09-15 新增 · 血证驱动）

**问题**：C 组闸门的正向保真度是拿**当前源码树**比的；而复刻类项目里**同一文件会被后续批次重写**——于是旧批次必然"红灯一片"，而这红灯和"编造"混在一起、无法区分。实测事故：agentic-rag 阶段8批次4 闸门报 **43 行不符**，逐行核对 `git show 30b928c:<file>` 后确认 **43 行全部来自该批快照、0 行编造**（`ChatQueueLimiter` 被阶段11 批次1 从 141 行重写成 277 行、`StreamChatPipeline` 被阶段9/10 改成 305 行、`RAGChatServiceImpl` 被阶段11 批次3 加了 `traceRunner`）。按"编造"去重写，会把**对的代码改错**、还会毁掉分批次的增量叙事。

**铁律 1｜批头必须声明源码快照**：每个批次讲解头部固定一行
`> 源码依据：commit \`<sha>\`（<提交标题>）；<文件数> +<行数>；自写 <N> 例，<模块> <X>/<X> 全绿。`
没这行，闸门只能"只比当前树"，**无法区分演进与编造**（新批次强制；历史批次回扫时补上）。

**铁律 2｜闸门按快照判定**：`python scripts/gate_lecture.py <批次.md> --src <源码根> [--snapshot <sha>]`（不传 `--snapshot` 时自动读批头）。判定口径：
- 行只在**当前树**命中 → 正常；
- 行只在**快照**命中 → **源码演进**：不计 FAIL，但报告会打印漂移量，且该块必须按铁律 3 标注；
- 行**两处都不在** → **候选编造/改写**：FAIL，当场修。

**铁律 3｜"历史版本"必须是可核验的块，不是免检后门**：
1. 小节标题含 **`【历史版本示例】`** 或 **`已被阶段N 重写`**；
2. 块内代码**逐字来自该 commit 的文件**——闸门会拿快照逐行核验，**有一行不在快照里就按编造处理**（所以"标个历史版本"躲不过检查）；
3. **紧邻给出"当前实现"块**（标题里写清"当前实现见 6.x.y"）；只标注而不给当前实现 = 讲解停在旧代码上，不合格；
4. 原块的`// :L` 行号属于**那一版**（与当前实现块的行号不同是正常的，讲解里要写明口径）。

**铁律 4｜行号必须与真实行号一致**（C 组 ④）：`// :Lnn` 指向的行内容必须就是该行；行号由注入脚本自动生成，**禁止手打**（实测：agentic-rag 有 21 个批次 / 465 处行号漂移，其中 9 个批次保真度还是 100%——靠肉眼永远发现不了）。

**铁律 5｜"不符"必须先分类再改**（跑一次分类，别把不符行数当编造行数）：

| 分类 | 判据 | 处置 |
|---|---|---|
| **源码演进** | 行只在本批快照里命中 | 标【历史版本示例】+ 补"当前实现"块；**禁止重写历史块** |
| **教材注释格式** | 代码部分命中，只因行尾写了中文（含旧的 `// 【教材补注】`）而不符 | 改成 `// :Lnn  ←教材：…`——**不是代码错** |
| **缩写 / 改写 / 压行** | 多行压一行、去花括号、`……` 省略、变量名被"顺手优化" | 用注入工具**整块重注入**（逐字），不要逐行手补 |
| **编造** | 快照与当前树都没有 | 按源码重写该块，并回查同批其它块与节外引用 |

### 6.1.3 排版硬标准（2026-09-18 新增 · ⓪e 机械判定 · 血证 = 批次33-38 排版退化）

**为什么有这一节**：讲解的"可读性"长期被当成写作习惯、没有任何判据——以批次1/2/3 为标尺量化比对阶段3，六项排版指标在批次31-38 全线劣化（② 从"段短 + 空行"变成"一大段堆在一起"、① ② 图改用裸围栏导致渲染无底色）。**排版不是审美问题：没有空行的密排长段 = 读者直接跳过的那一段。**

**六条硬标准（全部机械可判，闸门 ⓪e 执行）**：

1. **单段 ≤300 字**（② / ④ 节）——超了就在句号后断段。标尺实测：批次1/2/3 的 ② 最长 103-135 字、④ 最长 195-239 字，**0 段超 300**；批次33-38 的 ② 最长 743、④ 最长 606，超 300 字 1-4 段。
2. **段间必空行**——两个段落之间留一个空行；① 的长段、⑦.5 的通用步骤同样适用。
3. **所有代码/图示围栏必须标语言**——`text`（ASCII 图/命令/片段）、`java`、`bash`、`sql`、`yaml`、`xml`。**裸围栏渲染时没有底色与着色**，与标注块的观感差异肉眼可辨。判据范围：① ② ⑦（批次33-38 的 ①② 图全是裸围栏）。
4. **⑥ 件内步骤标记统一**——`**本文件要解决的一个问题**` / `**白话开场**` / `**构造方式与手法**` / `【讲解】` / `逐行要点表` / `**逐步回放**` / `**【怎么用】**` / `**【上下游】**` / `**【怎么接】**`；**加粗标记与【】标记不得混用于同一步**（批次33-38 出现 `**【问题】**` 这类自造标记，与判据锚对不上）。
5. **⑦ 五小节与 ⑫ 八条的标题层级统一**——⑦ 用 `####`，⑫ 用 `###`/`####` 但同一节内不得混用（批次37 的 ⑦ 出现 `###` + `####` + 粗体小表三种层级混排 = 读者看不清层次）。
6. **⑩ 反例与 ③ 教学片段必须配代码块**——反例的 ❌/✅ 各配一块；教学片段用 `text`/`bash` 块并标"教学合成片段（不带行号）"。
7. **⑥【讲解】段的要点必须列表化、单段 ≤300 字**（v2.27 新增）——多个论证点（"其一/其二/其三"）**禁止挤在一个自然段里**：每点独立成段（或 `-` 列表项）+ 段间空行，**加粗要点标签**（如 `**其一，建空间=建一次共享 collection**：…`）。标尺实测：批次1-5 的【讲解】段 36-80 字；批次33-38 为 445-958 字（2-5 处超 300）、内联枚举 1-4 处——**读者看到的就是"一坨字"**。同理适用于【构造方式与手法】【上下游】【怎么用】【怎么接】四个标记段：**每个标记段独立成段、段间空行**，不得连排。
8. **⑫ 第 2/3/5 步的排版是"可复用性"的一部分**（v2.27 新增）——
   - **第 2 条现状勘察 / 第 3 条方案比较**：各须含 **≥1 个代码块 = 「你发给 AI 的原文」**（整段可复制；第 2 条给勘察指令、第 3 条给"要 ≥3 个方案 + 表格列 行为/成本/风险 + 每个落选方案写具体缺陷"的指令），并配"现场会怎样（正常形态 + 常见偏差 ≥2 条）"；
   - **第 5 条可直接使用的提示词**：八段（【任务】【依赖】【要新增的类】【核心约束】【注释要求】【验收标准】【禁止】【输出格式】）**各自独立成行**（不是挤在一个【任务书】段里），并配两张表——「投喂策略」（对象 / 怎么给 / 为什么）与「可复用的完整骨架」（段名 / 这一轮要写成什么）；设计要点 ≥5 条。
   - **⑫ 里所有"发给 AI 的提示词"一律放进 ` ```text ` 代码块**（v2.28 新增 · 用户要求）——提示词是给读者**复制**用的，散在正文里既不能整段复制、观感也差；第 2 条与第 3 条的提示词块（E9）、第 5 条的轮次块（E11）都适用。
   - **第 5 条必须"多轮递进"**（v2.28 新增 · 用户要求"详记提示词是分多轮的，符合现实开发环境"）——**≥2 轮、每轮一个可复制块**，每轮标：**目标 / 提示词正文（块内）/ 期望形态 / 偏差信号 / 本轮验收**。参照批次1 的轮次序列（轮0 上下文轮 → 轮1 契约轮 → 轮2 样例轮 → 轮3 实现轮），里程碑式的三轮最小形态是：**轮 1 勘察轮（只读不写、禁写实现）→ 轮 2 骨架轮（只出骨架与签名、方法体待实现占位）→ 轮 3 实现轮（逐文件实现 + 自检）**，并在设计要点里写明"轮 1 与轮 2 的价值在于便宜地错"。**禁止**把多轮压成一整段提示词——那等于抹掉"现实开发是多轮问答"这一最关键的事实。
   - 标尺：批次1-5 = 第2·3条各 1 个提示词块、第5条 8/8 段独立行 + 16 表格行；批次34-38 = ⑫ 内围栏 0 个（提示词块整体消失）、八段 0/8（挤成一个【任务书】段）。

**自检方式**：写完任意一节先自问两句——「这一段在渲染器里看起来是几个段落？」（一段超 300 字就是错的）、「这个代码块有颜色吗？」（裸围栏就是错的）。

### 6.2 Vibecoding 必须讲真实开发过程

> **读者画像**：本节的读者是"要用 AI 写代码但不知道怎么指挥"的开发者——他们最常用的就是 Vibecoding 教程，因为现在都是 Vibecoding 开发了。**本节是整份教材里实用价值最高的部分，绝不允许敷衍。**

Vibecoding 章节必须回答的是：**面对一个真实需求，如何让 AI 从现有代码中分析、设计、写出、验证并迭代出实现**——不是只讲"如何复刻答案卷"或"给 AI 加几条提示词"。

**写作视角铁律（从零构建视角；2.16 起升格为机械判据，血证 H26）**：全部以**"你现在接到这个真实需求，该能力尚不存在，要用 AI 从零构建出来"**的真实开发场景视角写——叙事从需求起步，经由勘察既有资产、方案比较、增量实现、提示词、审查、迭代，走到沉淀。禁令有两层，缺一不可：
- **教材自指禁令（继续生效）**：禁止出现"本批/本阶段/教材第N章/答案卷/阶段N/批次M/批N"等一切教材自指话语。读者拿这段去真实开发时，不需要知道它出自哪个教材的哪个批次；他需要知道的是"我遇到类似需求时，怎么用 AI 做"。
- **回顾语禁令（2.16 新增，闸门 ⓪ FAIL 档）**：禁止出现"回顾性重构 / 回顾性重建 / 本批已实现 / 本批的代码 / 回看这一批 / 当时我们 / 已经写完"等**以"已有该批成果"为前提的回顾表述**——"已经做完再回头看"的时态会让读者丧失"我当时该怎么做"的决策临场感，而临场决策链正是本节的全部价值。即使是按最终代码**逆向重建**的协作记录，也必须改写成"一个当时面对需求的人会怎么一步步做"的形态（诚实标注义务见 §6.2.3）。
> **既合规又不丢信息的改写方法（2026-09-15 实战）**：用**工程坐标**替代**教材坐标**——"阶段3 的 `StreamTaskManager`"→"项目里已有的 `StreamTaskManager`"；"批次1 的记忆服务"→"`ConversationMemoryService`"；"阶段9/10 接入新站"→"将来接改写/意图站时"；"阶段11 才解决"→"留给后来的公平排队改造"。**类名、模块名、配置项本身就是读者能直接用的坐标**，去掉的只是"它在教材里排第几"这层无关信息。

#### 6.2.1 八条开发过程（每条都有最低深度要求）

每个重要能力至少还原一条完整开发过程，**八条缺一不可，每条都不能是一句话带过**：

> **⑫ 内容深度：硬要求（判据 2.11 / 血证 H20）**——⑫ 是**整份教材里唯一能跨项目复用**的一节（其余各节都是本项目的知识），也是**唯一产生过"内容编造"级血证的一节（H16）**。全库体检（57 份）显示它长期是"最重要的一节 + 最松的判据"：形态合格但深度不足的占大多数。因此这四条是硬要求：
>
> **① 每条按"四层"写**（层次必须齐；小标题措辞自由）：**你手上有什么**（真实输入）/ **你发给 AI 的原文**（可整段复制）/ **现场会怎样**（AI 正常回什么形态、常怎么走偏、你凭什么一眼看出不对）/ **你怎么定、落在哪**（结论 + 回链正文）。缺第 ③ 层是通病——只写"我要求 AI 这么做"，不写"它会怎么做错"，读者拿不到真正的判断力。
> **② 材料必须是真实物证**：输入取**真实文件/真实数据片段**（指明路径与行号），产物取**实跑出来的结果**（报告/测试输出，把关键数字抄进来），迭代取**真实发生过的失败**（有报错就抄原文）。**禁止编造报错、编号、对话原文**——重建叙事可以，编造事实不行；凡重建处必须标【推断】。
> **③ 第 5 条不是一个提示词，是"轮次序列"**：至少 3 轮（复杂能力建议 8~12 轮），每轮给「你发的原文 / 期望回件形态 / 偏差信号 / 本轮验收」；末尾给一份**可复用的完整骨架**（八段：任务/依赖/要新增的类/核心约束/注释要求/验收标准/禁止/输出格式——写成 `【任务】` 或 `任务：` 都认）+ **设计要点**（逐条解释"为什么这么写"，让读者学会写而不是只会抄）。
> **④ 篇幅是结果不是目标**：一份"能跟着做完"的 ⑫ 通常 **≥400 行**（参考值，不是判据）。达不到通常说明第 2/3/6/7 条被写成了摘要——**宁长勿短，但不许灌水**。
>
> **闸门只保证下限**：2.11 机械判定四项（八类语义是否齐、第 5 条有没有提示词骨架、有没有设计要点、第 6 条审查项是否 ≥6），2.16 再加一条 **FAIL 档：⑫ 不得出现「回顾语」**（回顾性重构/回顾性重建/本批已实现/回看这一批/当时我们/已经写完 等，词表按全库实测给全、误报 0）；其余 15 个维度（勘察翻车场景数、落选论证、步表行数、四段轮次、沉淀条数、**既有资产清单带路径 ≥3 条、真实需求含企业级约束 ≥1 条**…）进**报告档**作存量工单。**"闸门绿"永远不等于"这一节讲好了"**。
>
> **已知盲区（必须知道，否则会误信绿灯）**：一份**每处都是空话**但满足上述四项的 ⑫，闸门会**放行**——实测见 `skill_selfcheck.py` ⑪ 组的"边界钉桩"用例。机械判据只能判"有没有"，判不了"好不好"；判据越形式化越容易被形式满足。**因此下面这条人工审读不可省。**
>
> **人工审读四问**（机械判据碰不到的地方；每份 ⑫ 交付前自问，任一问答不上就是不达标，不管闸门是不是绿的）：
> ① 第 1 条的**成功标准**能不能直接当验收清单用（有命令/数值/边界，而不是"功能正常"）？
> ② 第 2 条的"不先看会怎样"里，**至少有一条是"不报错"的后果**吗（静默降级 / 串味 / 答不准）？
> ③ 第 5 条的提示词**现在就能复制去用**吗（依赖全是真类名、验收可执行）？**设计要点**讲的是"为什么"，还是把"是什么"复述了一遍？
> ④ 第 6/7 条的"怎么查 / 现象"**今天还能照着复现**吗（命令、产物列、数字对得上）？

**1. 真实需求**（最低深度：4 个要素齐全 + 1 条企业级约束）
- **谁**遇到什么业务问题（具名角色，不是"用户"）
- 现有代码**为何不够**（具体到"现在没有 X 类/Y 方法，所以做不了 Z"）
- **成功标准**（可验证的 N 条，不是"实现改写功能"这种模糊话）
- **至少一条生产环境（企业级）约束**——性能 / 成本 / 并发安全 / 稳定性 / 降级 / 限流 / 幂等 / 审计 / 合规任选其真，并写出"不满足会怎样"的具体后果；不许全是功能点（真实工单从来不是"只要功能对就行"）
- 写成"你接到一个工单：……"的开发叙事，不是"本批要实现……"的教材叙事

**2. 现状勘察**（最低深度：既有资产清单 ≥3 条 + 5 项以上勘察清单 + 每项翻车场景）
- **先列既有资产清单**（≥3 条，每条带**路径/行号**）：本次开发要长在上面、或必须绕开的可复用资产（已有类 / 配置项 / 工具类 / 测试基建），每条说明"为什么长在它上面"或"为什么必须绕开它"，以及**必须遵守的既有约定**（命名 / 分层 / 依赖方向）——从零构建 ≠ 从空地构建，真实开发永远长在存量资产上
- 列出**让 AI 先读哪些文件**（具体路径/类名），每项说明"为什么要先看它"
- 给出**真实指令形态**（代码块包裹的 prompt，不是行内一句话）
- **每项勘察都配一个"不先看会怎样"的具体翻车场景**（"不先看 RedisKeySerializer 会以为 key 就是写的字面值 → 多环境调试时找不到缓存"）
- 输出要求："输出要新增哪些类、每个类依赖谁、不改谁的边界清单，不要写代码"

**3. 方案比较**（最低深度：3 方案对比表 + 选型理由 + 为什么不是其他方案）
- 至少比较三个方案（A 简单但有缺陷 / B 另一种思路 / C 当前方案）
- **行为/成本/风险三列对比表**
- **为什么选当前方案**：写出 2~3 条理由，每条对应一个具体优势
- **为什么不是其他方案**：写出每个落选方案的具体缺陷（不是"风险高"这种抽象话，是"先拆后改时指代消解拿不到全句上下文"这种具体因果）

**4. 增量实现**（最低深度：6 步以上拆分表 + 不应触碰边界）
- 拆成可独立编译/验证的小批次，用**表格**列出（步序 / 新增或修改什么 / 可验证形态）
- 列出**不应触碰的边界**（"不动 StreamChatPipeline 现有代码" / "不引入 Gson"），每条配理由

**5. 可直接使用的提示词**（最低深度：八段结构完整模板，不是一行抽象话）
- **这是本节的核心交付物**——读者会直接拿去改改就用。必须给出**完整可用的指令模板**，用代码块包裹，包含八段：
  1. **【任务】**：一句话说清要做什么
  2. **【依赖】**：显式列出允许用的已有组件（全限定类名），让 AI 不用猜能不能用某库
  3. **【要新增的类】**：逐个列出类名 + 一句话职责
  4. **【核心约束】**：用"X 失败 → 回退 Y"的因果句式，不是"要兜底"的抽象话；列出所有关键设计约束
  5. **【注释要求】**：逐行三问注释的要求（呼应 §6.1.1）
  6. **【验收标准】**：具体的测试命令 + 期望的测试例数与覆盖路径
  7. **【禁止】**：不该动的文件、不该引入的依赖、不该越界的范围
  8. **【输出格式】**：约定 AI 怎么给结果（逐文件完整给出 / 文件路径作分隔标题）
- 模板后附**"这个提示词的设计要点"**——解释为什么这么写（"依赖清单显式列出 → AI 不用猜能不能用 Gson"；"用 → 表达因果 → 让 AI 知道每条约束的触发条件"），让读者学会**怎么写好提示词**而不只是抄走一个

**6. AI 产出后的审查**（最低深度：6 项以上审查表 + 每项检查方法 + 结果）
- 用**表格**列出审查项 / 检查方法 / 本批结果
- 包含：依赖方向 / 异常路径 / 缓存一致性 / 并发安全 / 注释完整性 / 越界检查
- 每项写**怎么查**（"看 diff 里 rewrite/ 是否依赖 service/"）和**结果**（✅ + 一句依据）

**7. 验证反馈循环**（最低深度：3 轮以上真实迭代，每轮"现象→定位→修正→教训"四段）
- 展示**测试或运行失败后**的真实迭代——每轮包含：
  - **现象**：编译错/测试红的具体报错
  - **定位**：从哪行日志/哪个栈帧看起 → 缩小到哪个类哪行
  - **修正**：改了什么（代码 diff 级别）
  - **教训**：这一轮教会了什么（可复用的规则/踩坑）
- **不能只写"测试通过后微调了一下"**——必须展示真实的"失败 → 定位 → 修正"过程
- 如果某轮失败教会了一个设计约束（如"防重复替换只在 target 以 source 开头时生效"），要标注这个约束最终落到了讲解的哪一节

**8. 最终沉淀**（最低深度：5 条以上可复用模式/规则/踩坑）
- 把本次开发形成的**可复用规则**记录下来——后续遇到类似场景能直接套
- 包含：设计模式（"有损环节必须兜底链"）/ 技术模式（"缓存三层"）/ 踩坑（"Mockito void 方法用 doThrow().when()"）/ 配置纪律 / API 返回类型陷阱
- 每条写成"后续遇到 X 场景应该 Y"的可执行规则，不是"本批学到了 X"的教材总结

#### 6.2.2 提问回链（让 AI 协作产物反查回正文）

列出 4~6 条"协作过程中真实问过的（或应该问的）提问"，每条标注**引出了讲解里的哪个结论**：
- 「`reversed()` 到底反转什么？」——引出 ⑧卡3 的整链反转语义
- 「防重复替换什么情况失效？」——引出 ⑩反例6 的配置纪律

这让读者看到"这条提问直接驱动了讲解里的哪一节"——把 AI 协作过程与教材其他部分**形成反查网**。

#### 6.2.3 三分类标签与复刻对照约束

必须区分三种内容并明确标注：

- `开发任务`：真实项目要增加或修复的能力；
- `AI 协作过程`：如何指挥和审查 AI 产出代码；
- `复刻对照`：如何与答案卷或原项目比较。

复刻对照只能是辅助内容，不能替代真实开发过程。不得把"代码与答案卷一致""提示词要求机制对齐"当作 Vibecoding 教学的主要结论。

**若本节是按已有代码逆向重建的协作记录**（而非真实时序开发），在节首声明："本节开发过程为按最终代码逆向重建的叙事，目的是让读者能按同一条路径自己走一遍——而非声称这是当时的逐字对话实录。"——**声明解决"是否诚实"，不改变叙事视角**：正文仍必须按从零构建视角写（需求起步、能力尚不存在），声明不是"回顾语"的通行证；旧写法"回顾性重构声明"已作废（2.16 起闸门 FAIL），不要通篇用回顾框架做挡箭牌降低详细度。

### 6.3 教材质量自检

写完批次后，必须逐项检查并在文末记录：

- 初学者只读代码块，能否知道每个变量和分支的作用；
- 是否存在没有贴代码、没有解释、却声称“完整讲解”的核心方法（**机械判据**：§6.4 的 ★完整性逐行比对，覆盖 < 99.5% 即不合格——**本项曾真实漏检过一整章★类，必须跑脚本而非目测**）；
- 是否解释了失败路径和副作用，而不只是成功路径；
- Vibecoding 是否包含真实需求、可执行提示、AI 修改、验证反馈和迭代结果；
- 是否把“已复刻”误写成“已验证”，把“单测通过”误写成“生产可靠”；
- 是否把推断、源码事实和实测结果分开。
- 自检结论必须给出**可复核的机械证据**（行数、闸门输出、逐项引用），**与合规性自查输出矛盾的结论 = 自检无效**——禁止用"关键段全贴"这类不可验证的表述掩盖摘录式贴码。

每个批次还应记录“本批前置知识、后续依赖、未覆盖项和下一批入口”，避免跨会话后只剩孤立文章。

### 6.4 批次教材 16 节统一化规范

每批教材统一为 16 节结构（①~⑯）+ 索引节。本节定义每节的**必含项**、**可选项**与**反例/正向要点**，确保跨批次呈现一致。

> **节奏纪律**：必含项必须出现；可选项按本批内容复杂度自取；反例列出常见错误写法与警示。A/B/C1/C2 代号仅作"历史风格指纹"溯源，**写新批时按本节规范执行**。

#### 执行效率约定（提速不降质）

讲解质量由三样决定：**输入信息量**（源码读了多少）、**交付物清单**（代码/测试/讲解各节深度）、**量化闸门**（⑯ 自检 + A/B 自查）——与执行速度无关。以下三项优化**不改变任何交付物**，自始适用：

1. **源码精读静默批量**：2~3 轮 Bash 多文件读取，**不向用户展示源码全文**（读取是分析输入，不是交付物）——读进上下文的信息量一字不少；
2. **写码批量交付**：连续写完所有文件后**一次性汇报**，不逐文件中途叙述；
3. **构建单次全量**：直接跑 `mvn test`（编译错在 test-compile 阶段同样暴露），省一次 compile 预检。

**保留清单**（以下省了直接伤讲解，禁止精简）：源码精读本身（讲解的全部事实来源）、测试例数（回归保障 + ⑪ 素材）、讲解 17 节各节深度、★类逐步回放与【讲解】块、A/B 合规自查、归档五件、⑮ 下一批入口。

**质量保证机制**：不靠"写得慢"，靠**闸门**——⑯ 自检 + A/B 自查抓出的问题当场修，与执行速度无关。

#### ① 在系统全景中的位置（A 风格：盒状全景图 + 跨批关系）
- 必含：① 一张**盒状嵌套 ASCII 全景图**（节点/盒/箭头定位本批关键对象在系统中的位置；**2.17 起机械判定**：围栏块内含连接符/箭头 ≥5 行，且图中 **≥3 个标识符能在仓库中找到**——类名/模块名/中间件名，通用词如 Service/Mapper 不算数）② 关键对象的**频次级分工**（"一次流式问答里调用几百次 vs 注册一次"这种数量级对比）③ 与相邻批次、全局组件（异常处理、配置中心、事务等）的**对接关系与边界**
- 反例：① 只贴数据流图不点本批对象在系统中的"占位" ② 不交代与全局异常处理器/配置/事务等横切组件的关系

#### ② 业务场景与端到端闭环（C1 风格：流水线图 + 分支流预告）
- 必含：① **一句话场景开场**（"用户输入 X 点击 Y，前端发起 Z 请求"）② 一张**纵向 ASCII 流水线图**，**每站标注出自哪个批次**（阶段/批次来源可追溯）③ 结尾一段**分支流预告**（**按实际分支数量 N 写；N≥2 时必含，N=1 可省**；正常/异常/边界/取消等）
- 可选：仅 1 条分支时省第 ③ 项
- 反例：① 多场景轮番登场（破坏流水线一图到底的可读性）② 流水线图不标批次来源（读者无法判断每站出处）

#### ③ 文件清单与一句话职责（C2 风格：分组三表）

  - 5.2 讲解骨架清单：**每文件一行 × 九列**（文件 / 业务镜头 / 架构位置 / 实现要点 / 调用链 / 失败场景 / 测试视角 / Vibecoding 视角 / 验证证据）——填完再写正文
- 反例：① 状态列缺失（无法区分本批穿透与已讲回链，会把已讲概念假装首次解释）② 骨架清单只是节级复选框（无文件级防漏）

#### ⑥ 逐件讲解（完整代码 + 逐行说明）（B 主体 + ★类 C2 块）
- 必含**五层结构**（**顺序即结构**：下面 1→5 的顺序不得调换，⑤ 在**件末**，且必须排在「逐行要点表」之后、件内 `---` 之前——闸门 ⑤ 会判位置，血证 H15）：
  1. **本文件要解决的一个问题** + 输入/输出（SKILL §6.1 硬要求）
  2. 代码块（完整文件或完整职责段；**关键行必须有贴近代码的中文注释，至少答"这是什么/为什么需要/不这样会怎样"**——§6.1 硬要求；**陌生 API 第一次出现必给调用前拿到什么/调用后产生什么/框架内部做了什么**——§6.1 硬要求；**标注真实文件行号 `:L`——必须与真实行号一致（C 组 ④ 逐处核对，存在性只是下限）**；**关键行连续 ≥8 行无注释 = 密度不足，不合格**——§6.1.1 密度标准；**教材补注一律写 `←教材：`，禁止 `// 【教材补注】`/行尾中文直注**——后者会被 C 组判成"代码行不符"，见 §6.1.2）
  3. **逐行要点表**（行号 / 讲解）——讲控制流、数据变化、状态变化、异常路径、副作用、**"不这样会怎样"**；**不是重复代码块内注释，是展开因果链**
  4. **边界与副作用段**
  5. **【怎么用】+【上下游】+（可插入点必写）【怎么接】——"我拿到这份代码该怎么用"三段，位置固定在件末**（2026-09-16 新增，见下条）
     > **为什么定"件末、表后、`---` 前"**：放在代码块与要点表之前会打断"先讲清它是什么、再讲怎么用"的阅读顺序；放在件内 `---` 之后会被读者当成下一节的内容（真实事故：某批 9 个件都把 `---` 留在 ⑤ 前面，读起来像"这一件已经结束"）。
- ★ 核心类额外加：
  - **C2 式【讲解】为什么…块**——聚焦一个"为什么这么设计"的问题，含代价与取舍论证
  - **至少一条逐步回放**（真实输入 → 每行发生什么 → 真实输出；含一条失败路径回放）——§6.1.1 硬要求
- **第 5 层「用法与接入」的硬要求（2026-09-16 新增 · 血证驱动）**：血证 = 61 份讲解 / 515 个逐件小节 / 1088 个代码块里，**517 件没有任何"调用现场/实现注册"内容**：每行都讲透了，读者合上文件仍不知道"这东西怎么调、我怎么加一个新的"。逐行注释回答的是"**这行为什么这么写**"，不回答"**我要用它/扩展它该怎么做**"——两者缺一不可。每件必须写：

  | 块 | 标记（闸门按此字符串识别，必须原样出现） | 必须答什么 |
  |---|---|---|
  | 调用现场 | `**【怎么用】**` | ① 谁在**哪个类哪个方法哪一行**调它（真实调用点，`类:方法 :Lnn`；用调用点工具扫出来，禁止凭印象）② 可照抄的最小调用片段（`new` + 传参 + 拿返回值）③ 传进去什么形态、拿回来什么形态 ④ 生产里只有这一处调用时，明说"只有这一处" |
  | 上下游契约 | `**【上下游】**` | 上游谁喂它数据（类:行号 + 数据形态）、下游谁吃它的产出（类:行号 + 数据形态）、**失败时上下游各看到什么**（异常类名 + 消息形态） |
  | 实现与注册 | `**【怎么接】**`（**接口 / 抽象类 / 策略注册表 / SPI / 可插入节点 / 配置档位必写**；纯 DTO·枚举·常量·建表脚本免写） | ① 实现/继承要覆写哪几个方法、基类替你做了什么 ② **最小可编译实现**（完整类；能指到本仓一个真实同类实现就指过去并贴其核心段）③ **注册/装配路径**：谁扫描、谁收集、谁登记（机制名 + 真实行号）④ **扩展步骤 1..N**：加一个新的要动哪些文件——明确"只加不改"还是"必须同步改哪里" ⑤ 类型/泛型/生命周期陷阱 |

  - 写法要求：**由外向内**讲——先"谁在用它、怎么用、怎么加一个新的"，再"它内部怎么实现"；禁止只做"由内向外"的逐行翻译。
  - 第 5 层的代码块属**教学合成片段**（照抄式调用示例/实现骨架），**禁止带行号标注**（标了行号 = 声明"这是源码原文"，闸门会按源码逐字核验）；片段里出现的每个 API/类名必须真实存在（⑯ 自检逐条核对）。
  - **批级**：⑦ 必须有 **`⑦.5 扩展与接入路径`**——本批可插入点一览表（插入点 / 触发条件 / 必须新增 / 必须同步改 / 不必改及原因 / 验证手段）+ 通用步骤 ≥3 条。
- 必含**注释归属声明**：源码自带注释 vs 教材补注（教材补注一律以 **`←教材：`** 开头，写在 `// :L<真实行号>` 之后——2026-09-15 统一；旧写法 `// 【教材补注】` 与"行尾直接写中文"**已作废**，它们会被 C 组闸门判成"代码行不符"）
- **密度自检**（§6.1.1）：随机翻到任意代码块，遮住代码块外文字，只读代码块内注释，初学者能否知道每行在干什么？不能 = 不合格
- **用法自检**：把 ⑥ 的代码块全遮住，只读【怎么用】/【上下游】/【怎么接】三段——读者能否照着调起来、能否照着加一个新的实现？不能 = 没讲完
- **反例**：① 缺"本文件要解决的一个问题"开场 ② 逐行讲解只翻译变量名不解释控制流 ③ 教材注释冒充源码事实 ④ 陌生 API 未给调用前后+内部行为（§6.1 硬要求） ⑤ 贴码+代码块外一句"要点"无逐行表（最常见敷衍形态） ⑥ ★类无逐步回放 ⑦ 关键行连续 ≥8 行无注释 ⑧ **通篇只讲"这行为什么这么写"，没有【怎么用】/【上下游】/【怎么接】三段**（2026-09-16 血证：读者"看了还是不知道怎么用"） ⑨ **接口/抽象类只讲逐行，不给最小实现 + 注册路径 + 扩展步骤** ⑩ **【讲解】段把多个论证点挤成一坨**（"其一/其二/其三"同段、单段 400+ 字）
- **2.27 起机械判定（⓪e E8）**：【讲解】段最长行 ≤300 字；"其一，/其二，"内联枚举禁止（要点应列表化、每点独立成段）——批次33-38 实录 445-958 字

- 反例：① 只贴片段不拼闭环（与 L2 重叠无增量）② 不显式说明省略（等于假装等价）

#### ⑩ 失败反例（C1 主体 + A 对照）
- 必含：**按本批复杂度定的反例数**（通常 4~8 条；简单零件批可少、跨层编排批可多），**统一骨架 = 现象 → 定位 → 根因 → 修复 + 一句教训**（C1 式）
- 错误代码部分用 **A 式 ❌/✅ 对照**（贴错误版与正确版，让"修对长什么样"立等可见）
- 每条结尾**单列一句"教训"**（"教训：兜底分支是下游契约的执行者，不是锦上添花"）
- 可选（按本批内容复杂度）：
  - **C2 的跨实现对比**（"这条故障在 Milvus 下不会发生——天然隔离"）
  - **B 的实测日志解读表**（构建日志原样摘录 + "每条来自哪个测试、证明什么"）
- 反例：① 条数不足以覆盖本批主要坑（每条对应一个真实失败场景）或喧宾夺主挤占主体节 ② 缺"教训"句（反例节最大教学价值丢失） ③ **❌/✅ 只写文字不配代码块**（退化成纯文字清单，读者看不到"修对长什么样"）
- **2.26 起机械判定（⓪e E5）**：`❌` 标记 **≥3** 且**代码块 ≥3 对**（❌ 错法块 + ✅ 修法块 + 现象/定位/根因/教训）——批次31-38 实录：❌/✅ 代码对照块整体归零（批次1/2/3=12-14 块、批次30=12 块）

#### ⑪ 测试视角（B+C1+A 三段）
- 必含三段：
  1. **B 逐例六列表**（# / 用例 / **前置状态** / 动作 / 断言 / 为什么能证明 / 没它会漏什么）——最严最细
  2. **C1 测试类策略分层表**（测试类 / 例数 / 策略："真实 PG / mock / 真 Semaphore / mock 四依赖"）——类级总览
  3. **A 测试五问**（测什么 / 为何这样测 / mock 边界 / 缺陷 / 上限）——方法论抽问
- 优先级：B 六列表 > C1 分层 > A 五问；B 必备，C1+A 可按需
- 反例：① 缺六列表（无法作为"回归测试白名单"用）② 六列表只列用例名不列"为什么能证明"（信息密度不足）

#### ⑫ Vibecoding 视角（B 八条 + C1 回链）
- **这是整份教材实用价值最高的部分**（读者最常用的就是 Vibecoding 教程），**绝不允许敷衍——每条都不能一句话带过**。严格按 SKILL §6.2 八条，每条最低深度见 §6.2.1：
  1. 真实需求（`开发任务`）——谁/问题/现有代码为何不够/4 条以上成功标准；**写成"你接到一个工单"的开发叙事，不是"本批要实现"的教材叙事**
  2. 现状勘察（`AI 协作过程`）——5 项以上勘察清单（代码块包裹的真实指令）+ 每项"不先看会怎样"翻车场景
  3. 方案比较（`开发任务`+`AI 协作过程`）——3 方案行为/成本/风险对比表 + 选型理由 + 为什么不是其他方案
  4. 增量实现（`开发任务`）——6 步以上拆分表 + 不应触碰边界
  5. **可直接使用的提示词**（`AI 协作过程`）——**八段结构完整模板**（任务/依赖/要新增的类/核心约束/注释要求/验收标准/禁止/输出格式），代码块包裹，**不是一行抽象话**；模板后附"设计要点"解释为什么这么写
  6. AI 产出后的审查（`AI 协作过程`）——6 项以上审查表（审查项/检查方法/结果）
  7. 验证反馈循环（`AI 协作过程`）——3 轮以上真实迭代，每轮"现象→定位→修正→教训"四段
  8. 最终沉淀（`开发任务`）——5 条以上可复用模式/规则/踩坑，写成"后续遇到 X 场景应该 Y"
- **写作视角铁律**（§6.2）：全部以"你现在接到一个需求，要用 AI 完成"的真实开发场景视角写——**禁止出现"本批/本阶段/教材第N章/答案卷/阶段N/批次M/批N"等一切教材自指话语**；逆向重建的协作记录也要改写成"假设你从零接到这个需求"的开发叙事
- 每节带 `开发任务` / `AI 协作过程` / `复刻对照` 分类标签；**复刻对照只能是辅助，不得当主要结论**（SKILL 硬要求）
- C1 亮点：**4~6 条"提问→引出 卡 X/反例 Y"回链**（§6.2.2）——让 AI 协作的产物反查回正文其他节
- 逆向重建时节首声明"按最终代码逆向重建的叙事"——**声明后仍按真实开发场景视角写正文**，不用"回顾性重构"做挡箭牌降低详细度
- 反例：① 缺方案比较表 ② 复刻对照占主要篇幅 ③ 提示词只有一行抽象话（必须八段完整模板）④ 八条每条一句话带过（每条都有最低深度要求）⑤ 出现"本批/本阶段/教材/阶段N/批次M"等教材自指话语 ⑥ 用"回顾性重构"声明做挡箭牌降低详细度 ⑦ **八条标题在、内容薄**（每条 6-23 行 = 提纲不是叙事）
- **2.26 起机械判定（⓪e E2）**：全节 **≥180 行**；八条小标题（`### 1.` / `#### 1.` 均可）逐条存在且**每条 ≥12 行**——批次34-38 实录：全节仅 114-117 行（缩水 55%，标尺 256-259 行）
- **2.27 起机械判定（⓪e E9/E10）**：① 第 2 条（现状勘察）与第 3 条（方案比较）**各含 ≥1 个代码块**（"你发给 AI 的原文"提示词，整段可复制）——批次34-38 的 ⑫ 内围栏数为 0，提示词块整体消失，读者只看到结论、学不到"怎么问"；② 第 5 条八段（【任务】【依赖】【要新增的类】【核心约束】【注释要求】【验收标准】【禁止】【输出格式】）**各自独立成行** + 表格行 ≥8（投喂策略表 + 可复用骨架表）——批次37 实录八段挤在一个【任务书】段里（0/8），16 行标尺见批次1

#### ⑬ 验证证据与已知限制（B+C2 主体）
- 必含四件：
  1. **构建命令 + 关键输出**（最好带真实日志片段，C2 式）+ 多模块绿统计
  2. **证据等级标注表**（C2 式）：每条独立标 `实测` / `未实测` / `推断` / `外部事实`
  3. **已知限制详表**（B 式）：每条带 ❌ 标记 + 说明 + **何时/哪批归还标注**
  4. **"已验证≠生产可靠"边界声明**（B 式，SKILL §6.3 硬要求）："本文档所有'✅ 已验证'均指单测通过，不等于生产可靠"
- 可选：**编译修复实录**（C1 式，本批有真实修复坑时写，按轮次编号）
- 反例：① 缺证据等级逐条标注 ② "已验证"边界声明缺失 ③ 已知限制不带归还标注（读者不知道什么时候能解决）

#### ⑭ 复习问答（A+B+C1 融合：按本批决策点定题数 + 答案内嵌钩回）
- 必含：**按本批决策点定的 Q/A 配对数**（通常 10~15 题；A 式：Q+问题紧跟 A+答案，不分离）
- 题目应**均衡覆盖**：
  - 设计动机（"为什么这么选/这么写"）
  - 反面假设（"能不能用 X 实现"）
  - 跨批/跨阶段关系（"和批次3 怎么协作"）
  - 故障推演（"不这样会怎样"）
- 答案内嵌**【钩回标签】**（C1 式）：`【反例 X】` / `【卡 Y】` / `【阶段 Z】` / `【批次 N】` ——让问答与正文其他节形成反查网
- 题目应**指向本批具体实现**（B 式）：不只问概念，要问"resolveTierName 三条分支顺序为什么不能调换"这种本批实现
- 答案应**带具体数值/场景/钉死测试名**（B 式）：不只说"会出问题"，要写"standard 档 30s、deep 档 120s；200 个请求就省下 200 × 30s"
- 反例：① 题数不足以覆盖本批主要决策点（通常少于 10）或稀释教学价值（通常多于 15）② 题目只问概念不指向本批实现 ③ 答案无【钩回】标签

#### ⑮ 前置知识 / 后续依赖 / 未覆盖项 / 下一批入口（A 三表 + 必含段）
- 必含：
  - **15.1 前置知识表**（前置 / 本批哪里用到 / 在哪学过）——回链前批/其他阶段
  - **15.2 后续依赖表**（依赖方 / 用到什么 / 在哪 / 预计哪批）
  - **15.3 未覆盖项诚实清单**（未覆盖 / 原因 / 何时补）——诚实标"本仓库尚未实现"
  - **15.4 下一批入口段**（必含）——侦察答案卷路径、教材对应章节、关键风险
- 当本批内容少时三表可压缩为**段落**（C1 式）；三表骨架不变
- 反例：① 缺"下一批入口"段（续接生命线断裂）② 未覆盖项用"实现完整"掩盖（违反 §6.3）

#### ⑯ 教材质量自检（B 六项表 + 展开依据 + 遗留观察）
- 必含**SKILL §6.3 六项自检表**：
  - 自检项 / 结论（✅/无/否） / **展开依据**（不是一句话敷衍，是"逐项核对"——如"`ModelSelector` 全部 12 个方法均在 ⑥ 出现"）
  - 1. 初学者只读代码块能否知道每个变量和分支的作用
  - 2. 是否存在"没贴代码、没解释、却声称完整讲解"的核心方法
  - 3. 是否解释失败路径与副作用，而不只是成功路径
  - 4. Vibecoding 是否包含真实需求/可执行提示/AI 修改/验证反馈/迭代结果
  - 5. 是否把"已复刻"误写成"已验证"、"单测通过"误写成"生产可靠"
  - 6. 是否把推断/源码事实/实测结果分开

- 索引节**见下方独立小节**（5 链接：上一批 / 下一批 / 阶段总览 / 总索引 / 覆盖矩阵——此处不重复展开）
- 反例：① 六项自检每项一句"✅"走过场（无展开依据 = 无自检）② 缺遗留观察

| ③ 注释密度 | ①无注释连段 <8 行 ②教学注释条数 ≥ 关键行÷12 ③★类每方法签名行或首行有注释（按整类判定） | 只贴码不讲解（`// :Lnn` 裸行号即典型形态） |
| ④ 行号一致性 | **漂移 = 0 处** | `// :Lnn` 指错行——比少注释更误导（读者按行号回查源码会找不到） |
| ⑤ 用法与接入 | 每个 `6.x` 件有 `**【怎么用】**` 与 `**【上下游】**`；件内出现 `interface`/`abstract class` 的另有 `**【怎么接】**`；批级有 `⑦.5 扩展与接入路径`（≥3 条编号步骤）；**位置**：【怎么用】须在「逐行要点表」之后、件内 `---` 之前；**件段边界**：件段不得越过一级节标题（2.14，否则 ⑨ 的手写接口骨架会算到末件头上） | 逐行都讲了、读者仍**不知道怎么调、怎么加一个新的**（血证 H4：61 份 515 件里该内容为 0）。标题带【历史版本示例】的小节免检 |
| ⑥ 散文符号真实性 | 正文（代码围栏之外）里的 ① `Xxx.java:NN` 引用必须文件存在且行号在范围内 ② `6.x` 件标题声明的 `Xxx.java` 必须存在 ③ `本仓类.method(` 的方法名必须在本仓源码里出现过。反引号里的其他 CamelCase 符号走 `spec/散文符号白名单.txt` + **待人工确认清单**（不计 FAIL） | 正文描述了**不存在的东西**——①~⑤ 只管代码块，正文一个字都不查（血证 H16：整段工单描述了从未实现的类/方法，六组却全绿）。**只留误报率≈0 的三条**：naive 版实测 371 处里约 95% 是合法的第三方库类型 / 教学示例类 / 「尚未实现」的规划名，做成 FAIL 会淹没真信号 |

- **正反向必须成对跑**（血证 H6：只跑反向会漏"讲解编造了源码里没有的代码"，只跑正向会漏"整类没贴"）。
- **哪些块免检**：显式标注为 `手写版 / No-Framework / 反例 / 反面对照` 的小节内的代码块免检（它们本就不对应仓库文件），但**免检小节必须在标题里写明**，不得借"反例"之名夹带未核实代码。**`**【怎么用】** / **【怎么接】** / **【扩展步骤】** / **【上下游】**` 标记之下的代码块同样免检**（它们是照抄式教学合成片段），**但带行号标注的不豁免**——标了行号即声明"这是源码原文"，仍按逐字核验。**旧格式 `// :N` 不豁免**（`L_ANNO` 两种格式都认）。
- **形态雷同 ≠ 保真**：讲解与源码结构相似但字段名/异常类型/调用链不同（如把 `registry` 写成 `chunkers`、把 `ServiceException` 写成 `IllegalStateException`），正向保真度会直接暴露。**判断标准是"逐行逐字"，不是"读起来像"**。
- **⑥ 之外的"残留引用"必查**（血证 H7，闸门盲区）：闸门只核对代码块，其它节引用旧实现它查不出来。**必做清单与核对表见 `spec/操作手册-闸门与工具.md` §3**；铁律是"⑥ 改完，逐节扫一遍残留，⑪ 的每条都打开真实测试文件核对"，且**修批只替换目标节、节外逐字节不变**。

**判定与处置**：
- **A 组任何一项不符 = 不过关**，当场修，修完**整套重跑**（改 ⑫ 可能影响结构项）。
- **C 组任何一项不符 = 不过关**，当场修（**优先级最高**：代码错误会直接教错读者，比结构问题严重得多）。五项 = ① 候选不符 0 行（**"只在快照命中"的源码演进行不计 FAIL，但该块必须按 §6.1.2 标【历史版本示例】并给当前实现**）+ 可归属 ② ★反向 ≥99.5% ③ 注释密度三项 ④ **行号漂移 0 处** ⑤ **用法与接入三项齐**（每件【怎么用】【上下游】/ 抽象件【怎么接】/ 批级 ⑦.5）。
- **A 组全绿 ≠ 教材合格**（血证 H5）：★ 完整性（逐行比对）才是内容完整性，**必跑不得省略**；"行号标注"计数只验存在性、**不能当注释合格**（曾有批次 2617 处标注全是裸行号）。
- **批次间对比（质量水位防漂移）**：每批自查时**顺带输出与已交付批次的对比表**（总行数 / ⑥⑫ 行数 / 要点表 / ★回放 / 讲解块 / 问答 / 反例；**v2.25 起必含 ⓪d 形态四项：② 流水线图有无、⑤ 双清单表数（应=2）、⑥ 问题开场+要点表+★回放齐备率、⑭ 完整答案率（应=100%）**）——任一指标明显低于历史水位即当场补齐。**"提速不丢信息"靠这张对比表持续验证，不靠口头承诺。**（血证：批次33-38 六轮闸门全 PASS 期间 ②⑤⑥⑭ 形态全线丢失——对比表此前没有这些指标，等于没照）
- 机械闸门与 ⑯ 自检**两者都要做**：闸门验"结构合规与覆盖完整"，⑯ 验"内容充分"。

## 7. 输出目录

> **批量对齐旧批次时**：优先加载 `lecture-align-pipeline` 技能（`~/.workbuddy/skills/lecture-align-pipeline/`，含摸底分档→源码注入→⑫规范化→回放/讲解→闸门→归档的完整流水线 + 八件安全工具 + 五条事故铁律）。它把这套规范变成了**可复制的执行动作**，而黄金样例是它的**目标产物**。

教材必须落盘到目标项目的 `NOTES/教学讲解/`——**就地写入是默认值**：教材要靠行号/路径回链源码、随项目演进，搬到项目外这些都会断。

```text
NOTES/
  00-系统全景地图.md
  项目文件覆盖矩阵.md
  概念词典.md
  阶段对照-完整性地图.md
  教学讲解/
    00-总索引.md
    阶段N-主题/
      00-阶段总览.md
      批次M-主题.md
```

**写入位置与版本库可见性（2026-09-17 · 用户要求 1）**：开工时检查目标项目的 `.gitignore` 与用户意愿——若 `NOTES/` 会被忽略、或用户不希望教材进版本库，提供两个选项并落盘记录选择：**(a) 在 `.gitignore` 加 `!NOTES/` 例外（推荐）**——教材随项目走，回链不断；**(b) 项目外隔离副本**——仅限两种场景：需要"答案卷隔离"（复刻对照不许看到答案）或用户明确要求目标项目零 diff。没有 git 的项目跳过本条。

每个总览列出批次、文件范围、业务闭环、依赖关系、验证状态和下一步链接。每批次完成立即写盘并更新索引。

跨会话续传必须以磁盘状态为准。每批更新 `AGENTS.md` 或项目约定的状态文件，至少写入：当前阶段、当前批次、已讲文件数/总数、未完成文件、最近验证命令与结果、已知风险、下一步。不得依赖聊天记录恢复进度。

**单册优先模式下的收尾落盘（V2 硬约束 2）**：被暂停的册不是"没有"，是"欠账"——每批收尾时状态文件必须重述"用户指令暂停：第X册（预计何时补）"，能力账本保留欠账条目，缺口清单列出暂停中的册；恢复同步后的第一批动作是回补欠账。

## 8. 交互约定

用户说“继续复刻”“继续学习”或 `next` 时，读取约束文件、全景地图、覆盖矩阵、最近教材和 Git 状态，从未完成项继续。

用户说“讲解 X”时，输出并落盘 X 的完整教程；缺少必要上下文时先补上下文，不要求用户手写。

用户说“只要产出”时，直接扫描、实现、验证和归档，不发起问答式流程。只有目录边界、写入位置或安全前提无法推断时才提出简短问题。

每次运行结束时，在回复中固定报告：当前阶段/批次、已讲文件数/总文件数、已验证/未验证数量、已落盘文件、阻塞项和下一步。回复只是摘要，完整教材必须以磁盘文件为准。

## 9. 质量禁区

- 不漏讲文件，不把“框架自动处理”当解释；
- 不只讲外围 API、名词或 README；
- 不编造源码、运行结果、性能数据和故障；
- 不用“高可用、易维护、解耦、方便扩展”等空泛词代替因果链；
- 不把玩具骨架冒充等价实现；
- 不强制用户手写、复述、提交或闯关；
- 不压缩掉业务、底层、测试和工程视角；
- 不把未经验证的推断写成事实。
- 不把“已经扫描”写成“已经讲解”，不把“已经讲解”写成“已经验证”；
- 不用固定文件数、固定题数或固定批次数套项目，所有数量以真实覆盖矩阵为准；
- 不因项目规模大而只讲入口和核心类，外围文件必须进入覆盖矩阵并给出适配其复杂度的说明。

# 复刻式项目深度学习

## 1. 任务定义

你的任务不是解释几个框架 API，也不是把项目复制出来，而是把一个真实项目转换成一套能让初学者逐步获得以下能力的教材：

1. 说清楚项目服务谁、解决什么业务问题、完整业务闭环如何运行。
2. 说清楚模块、进程、数据、依赖和外部系统为什么这样组织。
3. 读懂项目范围内每一个文件：源码、测试、配置、脚本、SQL、构建文件、前端资源、工具和部署文件。
4. 解释关键代码从入口到出口的真实执行链，并指出边界、失败模式和底层机制。
5. 判断 AI 生成代码是否正确、是否越界、是否缺测试、是否会在生产环境出问题。
6. 使用 Vibecoding 高效生成、修改、验证和演进项目，而不是只会拼接 API。

教材是主要交付物。交互、提问、手写练习和强制用户输入均为可选，不得阻塞主流程。

## 1.1 入口与动作路由

先从用户原话识别模式，不要让用户学习本技能的命令格式：

| 用户意图 | 立即执行的动作 |
|---|---|
| “学习/深度拆解/讲解整个项目/覆盖全部文件” | 定位项目根目录和教材目录，先完成项目考古，落盘四份基础地图，再从第一批继续 |
| “继续学习/继续复刻/next” | 读取磁盘状态、覆盖矩阵、最近教材和 Git 状态，从第一个未完成批次继续 |
| “只要产出/不要问我” | 采用默认路径和默认批次策略，直接扫描、讲解、验证、落盘；只有路径或安全边界无法推断时才提一个问题 |
| “讲解 X/讲第 N 批/讲某文件” | 补齐该对象所需的最小上下文，生成并落盘完整对象教程，同时更新矩阵和索引 |
| “验收/检查是否完整” | 不新增教材为主，审计覆盖矩阵、文件链接、证据等级、验证记录和索引，输出缺口清单 |

若用户同时给出原项目和复刻项目，原项目只读、复刻项目按用户授权使用；若只给出一个项目，默认把它作为被学习项目，教材写入该项目的 `NOTES/教学讲解/`，不擅自创建第二个复刻项目。

## 1.2 Flash 模型执行策略

本技能必须适合上下文和推理能力较小的模型执行。遵守以下机械流程：

1. **摘要先行**：先读取目录树、入口文件、依赖清单、状态文件和已有索引；不要一次性读取全项目源码。
2. **小批推进**：每批只处理一个闭环及其直接依赖；默认先选少量强相关文件，项目越大就增加批次，不把几十个文件压成一篇。
3. **上下文复用**：已解释概念只回链概念词典和旧批次；已读文件通过覆盖矩阵定位，不重复全文装入上下文。
4. **先写后续**：完成一批就立即写入教程、更新矩阵和状态，再开始下一批；不能把成果只留在对话中。
5. **证据优先**：每个结论先找路径、行号、命令或日志；找不到就写“未验证/推断”，不得用模型记忆补齐。
6. **单次运行有边界**：一次运行至少完成一个可读批次或基础地图；若无法完成，先落盘当前扫描结果、未完成清单和下一步入口。

## 1.3 最小可交付产出

任何首次运行至少落盘：

- `NOTES/00-系统全景地图.md`
- `NOTES/项目文件覆盖矩阵.md`
- `NOTES/概念词典.md`
- `NOTES/阶段对照-完整性地图.md`
- `NOTES/教学讲解/00-总索引.md`
- 状态文件中的当前阶段、当前批次、已讲/总文件数、阻塞项和下一步

完成一个批次至少落盘批次正文、阶段总览或索引更新、覆盖矩阵更新和验证记录。若时间、上下文或模型能力不足，优先保证这些可续传文件，不得声称全项目完成。

## 1.4 复杂度适配与降级

- 业务/机制批次执行 L0-L3；能运行时再做 L4。
- 纯配置、资源、文档、锁文件和生成文件重点说明作用、来源、引用关系、风险和排除理由，不强行制造“等价实现”。
- 无法安装依赖、启动服务或访问外部系统时，保留静态源码分析，明确写“未实测”，并记录阻塞命令、错误原文、已排查范围和剩余风险。
- 文件很多时不得删除文件以换取篇幅；应增加批次，或将低复杂度文件集中成“逐文件清单 + 每文件语义/引用/风险”，仍在矩阵中逐项出现。

## 2. 使用者定位与教学原则

假设读者只具备一门语言的基本语法、能运行命令并阅读简单报错，不熟悉当前项目的框架、数据库、中间件、协议和部署方式。

必须遵守：

- 新术语第一次出现时，用白话、类比和本项目真实位置解释；
- 不用一个未解释的术语解释另一个术语；
- 每一层回答“它是什么、为什么存在、数据从哪里来、失败时怎样”；
- 目标是读懂、复述、审查和指导 AI，不是手写速度；
- 不把 DTO、枚举、配置、测试、脚本视为低价值文件；
- 不因文件简单而降低解释完整性，只减少重复。

## 3. 输入与证据边界

开始前自动识别原项目、复刻项目、教材目录、`AGENTS.md`、README、贡献指南、CI 配置、技术栈、构建入口、运行入口、测试入口、外部依赖、已有教材、Git 历史和未完成事项。

优先使用本地真实文件、命令输出、测试结果、Git 历史和可定位源码作为证据。解释第三方底层行为时，优先查阅官方文档、依赖源码、字节码或最小实验。无法验证的内容必须标记为“推断”，不得伪装成事实。

默认不修改原项目；不得删除用户改动、已有教材或历史记录，只能增量补充或纠正。

所有结论标注证据等级：

- `事实-源码`：能回链到本地文件、类、方法和行号；
- `事实-实测`：由命令、测试、日志、堆栈或最小实验得到；
- `事实-历史`：由 Git 提交、差异或 blame 得到；
- `外部事实`：来自官方文档、依赖源码或协议规范；
- `推断`：根据现象和代码推导，但尚未直接验证。

教材不得把不同等级混写。性能、并发、安全、故障和生产行为尤其要说明证据等级。

## 4. 七阶段工作流

### 阶段 A：项目考古

扫描目录、文件类型、模块依赖、入口、配置、数据库、前端、工具、测试、部署和文档，建立：

- `NOTES/00-系统全景地图.md`
- `NOTES/项目文件覆盖矩阵.md`
- `NOTES/概念词典.md`
- `NOTES/阶段对照-完整性地图.md`

覆盖矩阵至少包含：路径、文件类型、所属能力、上下游、是否已讲、教程链接、证据状态、遗留问题。被排除的文件也要记录理由。

不要只扫描“业务源码”。默认范围包括根目录和隐藏目录中的构建、锁定、生成、测试、脚本、配置、资源、迁移、容器、CI、开发工具和运维文件。对自动生成文件、第三方目录和二进制资源可以不逐行讲，但必须记录其作用、来源、被谁引用以及排除理由。

### 阶段 B：业务建模

从用户、角色、场景、输入、业务规则、状态变化、输出、异常、审计和运营视角重建系统。每个核心能力给出真实角色、具体场景、一条端到端闭环、核心对象和约束，以及删除模块后业务如何退化。不要把“用了某框架”当业务解释。

### 阶段 C：架构推导

建立运行时全景图、模块依赖图、请求链路图、异步链路图、数据模型图和部署拓扑，并说明每个重要选择解决的吞吐、延迟、一致性、隔离、维护性或安全问题；给出替代方案、代价、边界和最可能故障。所有图都必须回链到真实模块、类、方法、配置和数据表。

### 阶段 D：全文件教材化

按业务能力和闭环分批，而不是随机按目录讲解。每个纳入范围的文件都必须出现于教材或覆盖矩阵：

- 业务源码、领域对象、控制器、服务、仓储、适配器；
- DTO、VO、枚举、异常、常量、配置属性和注解；
- 单元测试、集成测试、测试夹具；
- 构建文件、锁文件、脚本和插件；
- YAML、环境变量、SQL、迁移、Docker、CI/CD 和部署文件；
- 前端页面、组件、状态管理、请求封装、样式和资源；
- MCP、Agent、命令行、数据初始化和运维工具。

每个文件必须有一个唯一覆盖状态：`未开始`、`已定位`、`已讲解`、`已验证`、`排除-有理由`。同一文件被多个批次使用时，只保留一份主讲解，其他批次回链到它并说明本批新增视角。

### 阶段 E：底层穿透

关键机制至少解释真实源码或依赖证据、框架自动完成的事情、不使用框架时的等价实现、一个具体失败场景的时间线，以及如何通过日志、堆栈、测试或最小实验定位。优先穿透请求分发、依赖注入、事务、线程上下文、序列化、网络协议、连接池、缓存、消息投递、数据库索引、向量检索、流式响应、鉴权、重试、熔断和资源释放。

### 阶段 F：Vibecoding 工程能力

每个重要能力都要展示如何让 AI 正确完成：

- 写项目级上下文、约束、验收标准和变更范围；
- 把大需求拆成可验证批次；
- 先读代码、列影响面、再修改；
- 审查 diff、依赖方向、异常处理、并发、安全和测试；
- 用测试、日志、静态检查和运行结果形成反馈闭环；
- 识别幻觉、过度重构、伪实现、假测试和 API 拼接错误；
- 将一次修改沉淀成规则、模板、脚本和长期记忆。

必须展示真实任务的上下文、约束、变更、验证证据和复盘，不能只写泛泛的提示词建议。

### 阶段 G：验证与归档

每批次执行适合项目的构建、测试、静态检查、启动或最小链路验证。记录命令、关键输出、失败原因、修复过程和剩余风险。没有实际运行不得声称已验证。

完成条件：

1. 所有纳入范围文件均有教程链接或明确排除理由；
2. 每个核心业务闭环均有端到端链路；
3. 每个核心模块均有架构位置、依赖方向和数据流；
4. 关键机制有源码证据或推断标记；
5. 教材已落盘并有总索引；
6. 验证命令和结果可追溯。

若构建或运行失败，仍然产出教材，但必须把失败命令、完整关键错误、失败层级、已排查范围、未解决原因和风险写入教材。禁止用“环境问题”作为没有定位过程的统称。

## 5. 阶段与批次切分

阶段按能力和系统层次组织，例如：系统全景与运行入口、基础设施与数据层、支撑能力、核心业务闭环、前端交互、AI/工具链、部署运维与横向对照。具体名称随项目调整，不得机械套用。

批次按一个可解释、可验证的业务或技术闭环切分。一个批次不应把互不相关的文件堆在一起，也不应为了省篇幅把几十个文件压成一篇目录导读。大型项目宁可增加批次，也不能降低单文件讲解质量。

每批开始前先写两个内部清单：

1. **外部调用穿透清单**：列出本批所有框架、ORM、SDK、中间件、协议和工具调用，标注是否已有词典或前批证据、要穿透到哪一层、证据出处和完成状态。
2. **讲解骨架清单**：列出每个文件的业务镜头、架构位置、实现要点、调用链、失败场景、测试视角、Vibecoding 视角和验证证据，填完后再写正文。

关键机制按 L0-L4 穿透：

- `L0 源码证据`：真实源码、依赖源码、字节码或官方实现位置；
- `L1 机制拆解`：框架替项目自动完成的具体步骤；
- `L2 等价实现`：不依赖当前框架的可读示范，明确它仍省略了哪些生产边界；
- `L3 设计取舍`：替代方案、代价和具体失败时间线；
- `L4 故障实证`：实际破坏、日志、堆栈或数据变化；无法运行时必须写“未实测”，退回 L3。

本批至少有一个新机制达到 L0-L3；核心类和中间件尽量达到 L4。已经在前批完整解释过的机制可以回链，但不能假装本批首次解释。

## 6. 批次教材结构

每个批次至少包含：

1. 在系统全景中的位置；
2. 业务场景和端到端闭环；
3. 文件清单与每个文件的一句话职责；
4. 新概念白话解释；
5. 按文件逐个讲解；
6. 关键文件的完整方法或完整代码段逐行说明；
7. 调用链、数据流、状态变化和边界；
8. 不使用框架的等价实现或伪代码；
9. 失败场景、故障定位和反例；
10. 测试视角；
11. Vibecoding 视角；
12. 验证证据、已知限制、复习问答与索引。

### 6.1 初学者代码讲解硬标准

批次正文不是代码审查摘要，也不是"类职责 + 几个关键片段"。对每个重要源文件必须让读者能从文件入口读到出口：

- 先给"本文件要解决的一个问题"和输入/输出，再解释类、字段、构造器、方法之间的关系；
- 代码块默认贴完整文件；文件过长时按完整方法或完整职责段拆开，并明确上下段如何衔接；
- **★核心类禁止摘录式贴码**：★ 类必须贴完整文件（保留真实行号），**禁止用"关键片段/关键段"替代全类**。上下文预算紧张时，全类源码**一律用脚本从仓库文件直接注入**（如 python 文件对文件拼接，源码不经过对话手打）——手打/摘录必然截断且行号漂移，即使自检表写"关键段全贴"也不算合规；
- 代码块中的关键行必须有**贴近代码的中文注释**，至少说明"这是什么、为什么需要、不这样会怎样"；不能只在代码块外概括；
- 逐行讲解不能只翻译变量名，必须解释控制流、数据变化、状态变化、异常路径和副作用；
- 每个陌生 API 第一次出现时，先解释调用前拿到什么、调用后产生什么，再解释框架/JDK 内部做了什么；
- 必须提供一条"从真实输入到真实输出"的逐步回放，并指出读者应先看哪几个方法；
- 对测试代码，要解释测试前置状态、动作、断言对象、为什么该断言能证明业务行为，以及没有该测试会漏掉什么；
- 对配置、构建和脚本文件，要解释每个有效字段或命令如何影响源码运行，不得只说"添加依赖/配置参数"。

"完整代码"不等于把未经解释的大段源码搬进来。若源码本身没有注释，教材应在代码块中补充教学注释，但必须标明哪些是教材注释，不能把注释冒充源码事实。禁止用"其余类似""这里不展开""显然""读者可自行理解"跳过关键逻辑。

#### 6.1.1 逐行三问注释密度标准（防"贴码不讲解"）

代码块**不能只贴代码 + 代码块外一两句概括**——这是最常见的敷衍形态。每个代码块必须同时满足：

1. **代码块内**：关键行行尾或行首有中文注释，标注真实文件行号（`:L` 格式），每条注释至少答三问之一（①这是什么 ②为什么这行要它 ③不这样会怎样）；**非关键行（import/空行/纯声明）可不注释，但连续 5 行以上无注释 = 密度不足**。
2. **代码块外**：紧跟一张**逐行要点表**（行号 / 讲解），讲控制流、数据变化、状态变化、异常路径、副作用——**不是重复代码块内的注释，而是展开"为什么这样写、不这样会怎样"的因果链**。
3. **★核心类**额外提供至少一条**逐步回放**（真实输入 → 每行发生什么 → 真实输出；含一条失败路径的回放），让读者看到"代码跑起来是什么样"。

**密度自检**：随机翻到任意一个代码块，遮住代码块外的文字，**只读代码块内的注释**，初学者能否知道每行在干什么？如果代码块内注释密度不足以独立支撑理解，就是不合格。

**反面教材**（以下形态均不合格）：
- 贴完整代码 + 代码块外一句"要点：xxx"（无逐行要点表）
- 贴代码 + 逐行要点表但只翻译变量名（"L45：调用 normalize 方法"——没说为什么调、调完产生什么）
- 贴代码 + 要点表但跳过异常路径（只讲"正常跑会怎样"，不讲"LLM 超时会怎样"）
- ★类无逐步回放（读者看不到"代码跑起来是什么样"）

### 6.2 Vibecoding 必须讲真实开发过程

> **读者画像**：本节的读者是"要用 AI 写代码但不知道怎么指挥"的开发者——他们最常用的就是 Vibecoding 教程，因为现在都是 Vibecoding 开发了。**本节是整份教材里实用价值最高的部分，绝不允许敷衍。**

Vibecoding 章节必须回答的是：**面对一个真实需求，如何让 AI 从现有代码中分析、设计、写出、验证并迭代出实现**——不是只讲"如何复刻答案卷"或"给 AI 加几条提示词"。

**写作视角铁律**：全部以**"你现在接到一个需求，要用 AI 完成"**的真实开发场景视角写——**禁止出现"本批/本阶段/教材第N章/答案卷"等教材自指话语**。读者拿这段去真实开发时，不需要知道它出自哪个教材的哪个批次；他需要知道的是"我遇到类似需求时，怎么用 AI 做"。即使是逆向重建的协作记录，也要**改写成"假设你从零接到这个需求"的开发叙事**，而非"这批代码是怎么复刻出来的"。

#### 6.2.1 八条开发过程（每条都有最低深度要求）

每个重要能力至少还原一条完整开发过程，**八条缺一不可，每条都不能是一句话带过**：

**1. 真实需求**（最低深度：4 个要素齐全）
- **谁**遇到什么业务问题（具名角色，不是"用户"）
- 现有代码**为何不够**（具体到"现在没有 X 类/Y 方法，所以做不了 Z"）
- **成功标准**（可验证的 N 条，不是"实现改写功能"这种模糊话）
- 写成"你接到一个工单：……"的开发叙事，不是"本批要实现……"的教材叙事

**2. 现状勘察**（最低深度：5 项以上勘察清单 + 每项翻车场景）
- 列出**让 AI 先读哪些文件**（具体路径/类名），每项说明"为什么要先看它"
- 给出**真实指令形态**（代码块包裹的 prompt，不是行内一句话）
- **每项勘察都配一个"不先看会怎样"的具体翻车场景**（"不先看 RedisKeySerializer 会以为 key 就是写的字面值 → 多环境调试时找不到缓存"）
- 输出要求："输出要新增哪些类、每个类依赖谁、不改谁的边界清单，不要写代码"

**3. 方案比较**（最低深度：3 方案对比表 + 选型理由 + 为什么不是其他方案）
- 至少比较三个方案（A 简单但有缺陷 / B 另一种思路 / C 当前方案）
- **行为/成本/风险三列对比表**
- **为什么选当前方案**：写出 2~3 条理由，每条对应一个具体优势
- **为什么不是其他方案**：写出每个落选方案的具体缺陷（不是"风险高"这种抽象话，是"先拆后改时指代消解拿不到全句上下文"这种具体因果）

**4. 增量实现**（最低深度：6 步以上拆分表 + 不应触碰边界）
- 拆成可独立编译/验证的小批次，用**表格**列出（步序 / 新增或修改什么 / 可验证形态）
- 列出**不应触碰的边界**（"不动 StreamChatPipeline 现有代码" / "不引入 Gson"），每条配理由

**5. 可直接使用的提示词**（最低深度：八段结构完整模板，不是一行抽象话）
- **这是本节的核心交付物**——读者会直接拿去改改就用。必须给出**完整可用的指令模板**，用代码块包裹，包含八段：
  1. **【任务】**：一句话说清要做什么
  2. **【依赖】**：显式列出允许用的已有组件（全限定类名），让 AI 不用猜能不能用某库
  3. **【要新增的类】**：逐个列出类名 + 一句话职责
  4. **【核心约束】**：用"X 失败 → 回退 Y"的因果句式，不是"要兜底"的抽象话；列出所有关键设计约束
  5. **【注释要求】**：逐行三问注释的要求（呼应 §6.1.1）
  6. **【验收标准】**：具体的测试命令 + 期望的测试例数与覆盖路径
  7. **【禁止】**：不该动的文件、不该引入的依赖、不该越界的范围
  8. **【输出格式】**：约定 AI 怎么给结果（逐文件完整给出 / 文件路径作分隔标题）
- 模板后附**"这个提示词的设计要点"**——解释为什么这么写（"依赖清单显式列出 → AI 不用猜能不能用 Gson"；"用 → 表达因果 → 让 AI 知道每条约束的触发条件"），让读者学会**怎么写好提示词**而不只是抄走一个

**6. AI 产出后的审查**（最低深度：6 项以上审查表 + 每项检查方法 + 结果）
- 用**表格**列出审查项 / 检查方法 / 本批结果
- 包含：依赖方向 / 异常路径 / 缓存一致性 / 并发安全 / 注释完整性 / 越界检查
- 每项写**怎么查**（"看 diff 里 rewrite/ 是否依赖 service/"）和**结果**（✅ + 一句依据）

**7. 验证反馈循环**（最低深度：3 轮以上真实迭代，每轮"现象→定位→修正→教训"四段）
- 展示**测试或运行失败后**的真实迭代——每轮包含：
  - **现象**：编译错/测试红的具体报错
  - **定位**：从哪行日志/哪个栈帧看起 → 缩小到哪个类哪行
  - **修正**：改了什么（代码 diff 级别）
  - **教训**：这一轮教会了什么（可复用的规则/踩坑）
- **不能只写"测试通过后微调了一下"**——必须展示真实的"失败 → 定位 → 修正"过程
- 如果某轮失败教会了一个设计约束（如"防重复替换只在 target 以 source 开头时生效"），要标注这个约束最终落到了讲解的哪一节

**8. 最终沉淀**（最低深度：5 条以上可复用模式/规则/踩坑）
- 把本次开发形成的**可复用规则**记录下来——后续遇到类似场景能直接套
- 包含：设计模式（"有损环节必须兜底链"）/ 技术模式（"缓存三层"）/ 踩坑（"Mockito void 方法用 doThrow().when()"）/ 配置纪律 / API 返回类型陷阱
- 每条写成"后续遇到 X 场景应该 Y"的可执行规则，不是"本批学到了 X"的教材总结

#### 6.2.2 提问回链（让 AI 协作产物反查回正文）

列出 4~6 条"协作过程中真实问过的（或应该问的）提问"，每条标注**引出了讲解里的哪个结论**：
- 「`reversed()` 到底反转什么？」——引出 ⑧卡3 的整链反转语义
- 「防重复替换什么情况失效？」——引出 ⑩反例6 的配置纪律

这让读者看到"这条提问直接驱动了讲解里的哪一节"——把 AI 协作过程与教材其他部分**形成反查网**。

#### 6.2.3 三分类标签与复刻对照约束

必须区分三种内容并明确标注：

- `开发任务`：真实项目要增加或修复的能力；
- `AI 协作过程`：如何指挥和审查 AI 产出代码；
- `复刻对照`：如何与答案卷或原项目比较。

复刻对照只能是辅助内容，不能替代真实开发过程。不得把"代码与答案卷一致""提示词要求机制对齐"当作 Vibecoding 教学的主要结论。

**若本节是按已有代码逆向重建的协作记录**（而非真实时序开发），在节首声明："本节开发过程为按最终代码逆向重建的叙事，目的是让读者能按同一条路径自己走一遍——而非声称这是当时的逐字对话实录。"——**声明后仍按真实开发场景视角写正文**，不要通篇用"回顾性重构"做挡箭牌降低详细度。

### 6.3 教材质量自检

写完批次后，必须逐项检查并在文末记录：

- 初学者只读代码块，能否知道每个变量和分支的作用；
- 是否存在没有贴代码、没有解释、却声称“完整讲解”的核心方法；
- 是否解释了失败路径和副作用，而不只是成功路径；
- Vibecoding 是否包含真实需求、可执行提示、AI 修改、验证反馈和迭代结果；
- 是否把“已复刻”误写成“已验证”，把“单测通过”误写成“生产可靠”；
- 是否把推断、源码事实和实测结果分开。
- 自检结论必须给出**可复核的机械证据**（行数、闸门输出、逐项引用），**与合规性自查输出矛盾的结论 = 自检无效**——禁止用"关键段全贴"这类不可验证的表述掩盖摘录式贴码。

每个批次还应记录“本批前置知识、后续依赖、未覆盖项和下一批入口”，避免跨会话后只剩孤立文章。

### 6.4 批次教材 16 节统一化规范

每批教材统一为 16 节结构（①~⑯）+ 索引节。本节定义每节的**必含项**、**可选项**与**反例/正向要点**，确保跨批次呈现一致。

> **节奏纪律**：必含项必须出现；可选项按本批内容复杂度自取；反例列出常见错误写法与警示。A/B/C1/C2 代号仅作"历史风格指纹"溯源，**写新批时按本节规范执行**。

#### 6.4.0 执行约束（本节是强制约束，不是参考建议）

§6.4 不是"写完批次后对照检查"的参考，而是**写批次时必须照填的执行模板**。三个绑定保证它被真正执行：

1. **骨架清单列绑定**（§5）：⑤ 骨架清单的九列（业务镜头/架构位置/实现要点/调用链/失败场景/测试视角/Vibecoding/验证证据）**每一列必须能在 §6.4 找到落点**——业务镜头→②、架构位置→①、实现要点→⑥、调用链→⑦、失败场景→⑩、测试视角→⑪、Vibecoding→⑫、验证证据→⑬。写骨架清单时逐列确认该列会在 §6.4 哪一节落地，**落不了地的列是骨架设计缺陷，不是 §6.4 缺漏**。
2. **自检绑定**（§6.3）：⑯ 质量自检第 2 项"是否完整讲解"必须**对照 §6.4 各节必含项逐项核对**，在"展开依据"列里引用 §6.4 条目号（如"⑥.3 逐行要点表 ✓"、"⑬.4 边界声明 ✓"）——不引用 §6.4 的自检 = 走过场。
3. **模板绑定**（§10 references）：`references/批次讲解全文模板.md` 是 §6.4 的可执行版本——16 节骨架 + 各节表格/卡片空骨架。**生成批次时按模板填空格**，不自由发挥。
4. **合规性自查绑定**（grep 量化，见 §6.4 末尾命令块）：每批讲解**落盘后、commit 前**必须跑末尾的合规性自查命令——**A 组硬闸门（结构约定类，精确值不过关即修）+ B 组存在性与覆盖关系（内容量类不设死数字，用覆盖关系与存在性探测，充分性由 ⑯ 自检判定）**；任何一项不过关当场修、修完复跑，全过才允许 commit；⑯ 自检表末尾记录"合规性自查已跑 + 判定结论"。**效果保证靠机械闸门，不靠"我会注意"。**

#### 执行效率约定（提速不降质）

讲解质量由三样决定：**输入信息量**（源码读了多少）、**交付物清单**（代码/测试/讲解各节深度）、**量化闸门**（⑯ 自检 + A/B 自查）——与执行速度无关。以下三项优化**不改变任何交付物**，自始适用：

1. **源码精读静默批量**：2~3 轮 Bash 多文件读取，**不向用户展示源码全文**（读取是分析输入，不是交付物）——读进上下文的信息量一字不少；
2. **写码批量交付**：连续写完所有文件后**一次性汇报**，不逐文件中途叙述；
3. **构建单次全量**：直接跑 `mvn test`（编译错在 test-compile 阶段同样暴露），省一次 compile 预检。

**保留清单**（以下省了直接伤讲解，禁止精简）：源码精读本身（讲解的全部事实来源）、测试例数（回归保障 + ⑪ 素材）、讲解 17 节各节深度、★类逐步回放与【讲解】块、A/B 合规自查、归档五件、⑮ 下一批入口。

**质量保证机制**：不靠"写得慢"，靠**闸门**——⑯ 自检 + A/B 自查抓出的问题当场修，与执行速度无关。

#### ① 在系统全景中的位置（A 风格：盒状全景图 + 跨批关系）
- 必含：① 一张**盒状嵌套 ASCII 全景图**（节点/盒/箭头定位本批关键对象在系统中的位置）② 关键对象的**频次级分工**（"一次流式问答里调用几百次 vs 注册一次"这种数量级对比）③ 与相邻批次、全局组件（异常处理、配置中心、事务等）的**对接关系与边界**
- 反例：① 只贴数据流图不点本批对象在系统中的"占位" ② 不交代与全局异常处理器/配置/事务等横切组件的关系

#### ② 业务场景与端到端闭环（C1 风格：流水线图 + 分支流预告）
- 必含：① **一句话场景开场**（"用户输入 X 点击 Y，前端发起 Z 请求"）② 一张**纵向 ASCII 流水线图**，**每站标注出自哪个批次**（阶段/批次来源可追溯）③ 结尾一段**分支流预告**（**按实际分支数量 N 写；N≥2 时必含，N=1 可省**；正常/异常/边界/取消等）
- 可选：仅 1 条分支时省第 ③ 项
- 反例：① 多场景轮番登场（破坏流水线一图到底的可读性）② 流水线图不标批次来源（读者无法判断每站出处）

#### ③ 文件清单与一句话职责（C2 风格：分组三表）
- 必含三表：
  1. **源文件表**（# / 文件 / 行数 / 一句话职责 / ★ 标记）
  2. **配置/资源/补丁表**（文件 / 补了什么 / **不补的后果**）——无配置可省
  3. **测试文件表**（# / 文件 / 例数 / 测什么关键断言）
- 反例：① 源+测试混在同一张表（信息密度过大难扫读）② 配置表不带"不补的后果"列（无法做风险预警）

#### ④ 新概念白话解释（A+C2 混合：宽表全量 + 核心深潜）
- 必含：① 三列宽表全量覆盖所有新概念（概念 / 一句话白话 / **本批在哪出现**含源码位置回链）② 其中本批**最核心的 2~3 个概念**附 **C2 式深潜小节**（### 4.x），按"是什么 / 解决什么问题 / 不用它会怎样"三段展开 + 必要时代码示例 + 代价分析
- 反例：① 全部概念都是一句白话（核心讲不透）② 全部概念都深潜（15+ 概念深潜篇幅爆炸）

#### ⑤ 批前两个内部清单（B 风格：六列状态表 + 九列骨架矩阵）
- 必含：
  - 5.1 外部调用穿透清单：**六列表**（# / 调用点 / 属于谁 / 穿透到哪层 / 证据出处 / **状态**：`✅` 本批穿透 或 `↩` 已讲回链）——SKILL 原文定义
  - 5.2 讲解骨架清单：**每文件一行 × 九列**（文件 / 业务镜头 / 架构位置 / 实现要点 / 调用链 / 失败场景 / 测试视角 / Vibecoding 视角 / 验证证据）——填完再写正文
- 反例：① 状态列缺失（无法区分本批穿透与已讲回链，会把已讲概念假装首次解释）② 骨架清单只是节级复选框（无文件级防漏）

#### ⑥ 逐件讲解（完整代码 + 逐行说明）（B 主体 + ★类 C2 块）
- 必含**四层结构**：
  1. **本文件要解决的一个问题** + 输入/输出（SKILL §6.1 硬要求）
  2. 代码块（完整文件或完整职责段；**关键行必须有贴近代码的中文注释，至少答"这是什么/为什么需要/不这样会怎样"**——§6.1 硬要求；**陌生 API 第一次出现必给调用前拿到什么/调用后产生什么/框架内部做了什么**——§6.1 硬要求；**标注真实文件行号 `:L`——存在性是下限（>0 过闸），★类密度对齐历史批次水位（每批自查对比表暴露差距，低于水位即补）**；**连续 5 行以上无注释 = 密度不足，不合格**——§6.1.1 密度标准）
  3. **逐行要点表**（行号 / 讲解）——讲控制流、数据变化、状态变化、异常路径、副作用、**"不这样会怎样"**；**不是重复代码块内注释，是展开因果链**
  4. **边界与副作用段**
- ★ 核心类额外加：
  - **C2 式【讲解】为什么…块**——聚焦一个"为什么这么设计"的问题，含代价与取舍论证
  - **至少一条逐步回放**（真实输入 → 每行发生什么 → 真实输出；含一条失败路径回放）——§6.1.1 硬要求
- 必含**注释归属声明**：源码自带注释 vs 教材补注（`// 【教材补注】`）显式区分
- **密度自检**（§6.1.1）：随机翻到任意代码块，遮住代码块外文字，只读代码块内注释，初学者能否知道每行在干什么？不能 = 不合格
- 反例：① 缺"本文件要解决的一个问题"开场 ② 逐行讲解只翻译变量名不解释控制流 ③ 教材注释冒充源码事实 ④ 陌生 API 未给调用前后+内部行为（§6.1 硬要求） ⑤ 贴码+代码块外一句"要点"无逐行表（最常见敷衍形态） ⑥ ★类无逐步回放 ⑦ 连续 5+ 行无注释

#### ⑦ 调用链、数据流、状态变化与边界（三合一：B 骨架 + C1 分支流 + A 状态图）
- 必含四小节：
  - ⑦.1 调用链 = 编号列表带行号 + 跨批标注（B 式）
  - ⑦.2 数据流 = 变换管道图；**数据载体 ≥3 个时加产出/消费表**（C1 式）
  - ⑦.3 状态变化 = 有状态对象画**状态机图**（A 式）+ **迁移表只列本批触发**（B 式）
  - ⑦.4 边界与不变式 = **编号列表**（C1 式）
- 多分支流（≥2 条）时在 ⑦.1 后加**分支流并列时序图**（C1 式，T=请求线程 / A=回调线程标注）
- 反例：① 缺行号导致读者无法回查 ② 状态变化表把所有迁移都列（已讲回链应只列本批触发的）

#### ⑧ L0-L4 底层穿透卡（B+C1 融合：五级纪律卡 + 省略边界段 + 同构证据）
- 每张卡**统一结构**：
  - 卡标题：`类名★` —— 机制名（**A 式问题副题可选**：`靠什么…` / `为什么…`）
  - **五级列表项**（B 式）：
    - **L0 源码证据**：真实源码/依赖源码/字节码/官方实现位置 + 证据等级
    - **L1 机制拆解**：框架替项目自动完成的具体步骤；可含**与替代方案的对比**（C1 式）
    - **L2 等价实现**：不依赖当前框架的可读示范；L2 后**必带"省略了什么生产边界"段**（B 式，SKILL 硬要求）
    - **L3 设计取舍**：替代方案、代价、具体失败场景
    - **L4 故障实证**：实际破坏/日志/堆栈/数据变化；**无法运行时必须写"未实测"退 L3**
  - 无 L4 实证时用 **C1 的同构证据替代 + 诚实标注**（"本批无线上故障可证；用阶段 X 的 Y 用例作同构证据"）
  - 证据等级统一**内嵌【】标注**（C1 式）：`【事实-源码】` / `【实测】` / `【推断】` / `【外部事实】`
- **核心类尽量达到 L0-L4**；**本批至少有 1 个新机制达到 L0-L3 完整穿透**（对齐 §5 原文——"穿透卡"是教材载体，L0-L3 是穿透层数要求；核心类和中间件尽量 L4）
- 反例：① L2 后缺"省略了什么生产边界"段（违反 SKILL）② L4 无实证时写"理论上会这样"（必须写"未实测"）

#### ⑨ No-Framework 等价实现（A 主体 + C1 点题）
- 必含：
  - ① 一段开篇声明：本批依赖几件"别人的东西"；与 ⑧-L2 的分工（L2 给片段、⑨ 拼闭环）
  - ② **完整可运行闭环手写版**（`TinyXxx` 或 `MiniXxx` 类；**行数按复杂度定——目标"能讲清全貌的最小闭环"而非凑行数**）——只用 JDK + 最薄中间件
  - ③ **C1 式点题句**："目标不是替代，而是证明：本批的复杂度全部来自'边界与容错'，核心编排本身极薄"（或类似洞察）
  - ④ **"框架到底多送了什么"对照表**（A 式）——逐项：框架便利 vs 手写代价
  - ⑤ **显式省略清单**（B 式写在代码首注释）："省略了 X、Y、Z"（防"玩具骨架冒充等价实现"，SKILL 质量禁区明文禁止）
- 反例：① 只贴片段不拼闭环（与 L2 重叠无增量）② 不显式说明省略（等于假装等价）

#### ⑩ 失败反例（C1 主体 + A 对照）
- 必含：**按本批复杂度定的反例数**（通常 4~8 条；简单零件批可少、跨层编排批可多），**统一骨架 = 现象 → 定位 → 根因 → 修复 + 一句教训**（C1 式）
- 错误代码部分用 **A 式 ❌/✅ 对照**（贴错误版与正确版，让"修对长什么样"立等可见）
- 每条结尾**单列一句"教训"**（"教训：兜底分支是下游契约的执行者，不是锦上添花"）
- 可选（按本批内容复杂度）：
  - **C2 的跨实现对比**（"这条故障在 Milvus 下不会发生——天然隔离"）
  - **B 的实测日志解读表**（构建日志原样摘录 + "每条来自哪个测试、证明什么"）
- 反例：① 条数不足以覆盖本批主要坑（每条对应一个真实失败场景）或喧宾夺主挤占主体节 ② 缺"教训"句（反例节最大教学价值丢失）

#### ⑪ 测试视角（B+C1+A 三段）
- 必含三段：
  1. **B 逐例六列表**（# / 用例 / **前置状态** / 动作 / 断言 / 为什么能证明 / 没它会漏什么）——最严最细
  2. **C1 测试类策略分层表**（测试类 / 例数 / 策略："真实 PG / mock / 真 Semaphore / mock 四依赖"）——类级总览
  3. **A 测试五问**（测什么 / 为何这样测 / mock 边界 / 缺陷 / 上限）——方法论抽问
- 优先级：B 六列表 > C1 分层 > A 五问；B 必备，C1+A 可按需
- 反例：① 缺六列表（无法作为"回归测试白名单"用）② 六列表只列用例名不列"为什么能证明"（信息密度不足）

#### ⑫ Vibecoding 视角（B 八条 + C1 回链）
- **这是整份教材实用价值最高的部分**（读者最常用的就是 Vibecoding 教程），**绝不允许敷衍——每条都不能一句话带过**。严格按 SKILL §6.2 八条，每条最低深度见 §6.2.1：
  1. 真实需求（`开发任务`）——谁/问题/现有代码为何不够/4 条以上成功标准；**写成"你接到一个工单"的开发叙事，不是"本批要实现"的教材叙事**
  2. 现状勘察（`AI 协作过程`）——5 项以上勘察清单（代码块包裹的真实指令）+ 每项"不先看会怎样"翻车场景
  3. 方案比较（`开发任务`+`AI 协作过程`）——3 方案行为/成本/风险对比表 + 选型理由 + 为什么不是其他方案
  4. 增量实现（`开发任务`）——6 步以上拆分表 + 不应触碰边界
  5. **可直接使用的提示词**（`AI 协作过程`）——**八段结构完整模板**（任务/依赖/要新增的类/核心约束/注释要求/验收标准/禁止/输出格式），代码块包裹，**不是一行抽象话**；模板后附"设计要点"解释为什么这么写
  6. AI 产出后的审查（`AI 协作过程`）——6 项以上审查表（审查项/检查方法/结果）
  7. 验证反馈循环（`AI 协作过程`）——3 轮以上真实迭代，每轮"现象→定位→修正→教训"四段
  8. 最终沉淀（`开发任务`）——5 条以上可复用模式/规则/踩坑，写成"后续遇到 X 场景应该 Y"
- **写作视角铁律**（§6.2）：全部以"你现在接到一个需求，要用 AI 完成"的真实开发场景视角写——**禁止出现"本批/本阶段/教材第N章/答案卷"等教材自指话语**；逆向重建的协作记录也要改写成"假设你从零接到这个需求"的开发叙事
- 每节带 `开发任务` / `AI 协作过程` / `复刻对照` 分类标签；**复刻对照只能是辅助，不得当主要结论**（SKILL 硬要求）
- C1 亮点：**4~6 条"提问→引出 卡 X/反例 Y"回链**（§6.2.2）——让 AI 协作的产物反查回正文其他节
- 逆向重建时节首声明"按最终代码逆向重建的叙事"——**声明后仍按真实开发场景视角写正文**，不用"回顾性重构"做挡箭牌降低详细度
- 反例：① 缺方案比较表 ② 复刻对照占主要篇幅 ③ 提示词只有一行抽象话（必须八段完整模板）④ 八条每条一句话带过（每条都有最低深度要求）⑤ 出现"本批/本阶段/教材"等教材自指话语 ⑥ 用"回顾性重构"声明做挡箭牌降低详细度

#### ⑬ 验证证据与已知限制（B+C2 主体）
- 必含四件：
  1. **构建命令 + 关键输出**（最好带真实日志片段，C2 式）+ 多模块绿统计
  2. **证据等级标注表**（C2 式）：每条独立标 `实测` / `未实测` / `推断` / `外部事实`
  3. **已知限制详表**（B 式）：每条带 ❌ 标记 + 说明 + **何时/哪批归还标注**
  4. **"已验证≠生产可靠"边界声明**（B 式，SKILL §6.3 硬要求）："本文档所有'✅ 已验证'均指单测通过，不等于生产可靠"
- 可选：**编译修复实录**（C1 式，本批有真实修复坑时写，按轮次编号）
- 反例：① 缺证据等级逐条标注 ② "已验证"边界声明缺失 ③ 已知限制不带归还标注（读者不知道什么时候能解决）

#### ⑭ 复习问答（A+B+C1 融合：按本批决策点定题数 + 答案内嵌钩回）
- 必含：**按本批决策点定的 Q/A 配对数**（通常 10~15 题；A 式：Q+问题紧跟 A+答案，不分离）
- 题目应**均衡覆盖**：
  - 设计动机（"为什么这么选/这么写"）
  - 反面假设（"能不能用 X 实现"）
  - 跨批/跨阶段关系（"和批次3 怎么协作"）
  - 故障推演（"不这样会怎样"）
- 答案内嵌**【钩回标签】**（C1 式）：`【反例 X】` / `【卡 Y】` / `【阶段 Z】` / `【批次 N】` ——让问答与正文其他节形成反查网
- 题目应**指向本批具体实现**（B 式）：不只问概念，要问"resolveTierName 三条分支顺序为什么不能调换"这种本批实现
- 答案应**带具体数值/场景/钉死测试名**（B 式）：不只说"会出问题"，要写"standard 档 30s、deep 档 120s；200 个请求就省下 200 × 30s"
- 反例：① 题数不足以覆盖本批主要决策点（通常少于 10）或稀释教学价值（通常多于 15）② 题目只问概念不指向本批实现 ③ 答案无【钩回】标签

#### ⑮ 前置知识 / 后续依赖 / 未覆盖项 / 下一批入口（A 三表 + 必含段）
- 必含：
  - **15.1 前置知识表**（前置 / 本批哪里用到 / 在哪学过）——回链前批/其他阶段
  - **15.2 后续依赖表**（依赖方 / 用到什么 / 在哪 / 预计哪批）
  - **15.3 未覆盖项诚实清单**（未覆盖 / 原因 / 何时补）——诚实标"本仓库尚未实现"
  - **15.4 下一批入口段**（必含）——侦察答案卷路径、教材对应章节、关键风险
- 当本批内容少时三表可压缩为**段落**（C1 式）；三表骨架不变
- 反例：① 缺"下一批入口"段（续接生命线断裂）② 未覆盖项用"实现完整"掩盖（违反 §6.3）

#### ⑯ 教材质量自检（B 六项表 + 展开依据 + 遗留观察）
- 必含**SKILL §6.3 六项自检表**：
  - 自检项 / 结论（✅/无/否） / **展开依据**（不是一句话敷衍，是"逐项核对"——如"`ModelSelector` 全部 12 个方法均在 ⑥ 出现"）
  - 1. 初学者只读代码块能否知道每个变量和分支的作用
  - 2. 是否存在"没贴代码、没解释、却声称完整讲解"的核心方法
  - 3. 是否解释失败路径与副作用，而不只是成功路径
  - 4. Vibecoding 是否包含真实需求/可执行提示/AI 修改/验证反馈/迭代结果
  - 5. 是否把"已复刻"误写成"已验证"、"单测通过"误写成"生产可靠"
  - 6. 是否把推断/源码事实/实测结果分开
- 必含**遗留观察段**（记给后续批次）——自检中发现的"非本批范畴、但应被后续批次处理"的问题
- 索引节**见下方独立小节**（5 链接：上一批 / 下一批 / 阶段总览 / 总索引 / 覆盖矩阵——此处不重复展开）
- 反例：① 六项自检每项一句"✅"走过场（无展开依据 = 无自检）② 缺遗留观察

#### 索引节（非 16 之数，单独保留）
- 必含**5 链接索引**：上一批 / 下一批 / 阶段总览 / 总索引 / 覆盖矩阵
- 与 ⑯ 末尾的"见下方独立小节"指向同一处；位置合并或单列皆可，但必须出现

#### 每批合规性自查（落盘后、commit 前强制执行——机械闸门，不是口头承诺）

每批讲解落盘后立即跑以下命令（`$F` 替换为批次文件路径）。检查分两组，**判定标准不同**：

- **A 组硬闸门**：检查对象全部是"结构约定"（节数 17 是 §6.4 的定义、八条/八段是 §6.2.1 的定义、自指话语/CONT 是禁令、围栏偶数是语法）——**数字精确、不过关即修**。
- **B 组存在性 + 覆盖关系**：检查对象是"内容量"——**内容量禁止写死数字**（大批次 ⑥ 可 900 行、零件批次可能 300 行；真实协作可能 1 轮迭代也可能 5 轮）。真判据是**覆盖关系**（要点表数 = ⑥ 被讲段数，一表不多一表不少）与**存在性**（有★类则回放/为什么块必须有；行号标注必须 >0）；**充分性**（每张表是否讲了因果、回放是否含失败路径、八条每条是否有实质内容）grep 验不了，由 ⑯ 自检逐段核对。

```bash
F="批次文件.md"

# ── A 组：硬闸门（精确值，任何一项不符 = 当场修）──
echo "节数: $(grep -c '^## ' "$F")"                    # 必须 17（①~⑯ + 索引，§6.4 定义）
echo "围栏数: $(grep -c '^```' "$F")"                  # 必须偶数（markdown 语法）
# ⚠️ 自指误报：直接写 'CONT-\|TODO' 会让这一行命令自身被 grep 命中（=1 而非 0）。
#    把字面量拆开写即可规避；批次讲解正文里引用本命令块时同样要拆开。
RESIDUAL='CON''T-\|TO''DO'
echo "占位符残留: $(grep -c "$RESIDUAL" "$F")"          # 必须 0（占位符必须清）
echo "⑫自指话语: $(awk '/^## ⑫ /,/^## ⑬ /' "$F" | grep -c '本批\|本阶段\|教材第\|答案卷')"  # 必须 0（§6.2 写作视角铁律）
echo "⑫八条: $(awk '/^## ⑫ /,/^## ⑬ /' "$F" | grep -c '^### [0-9]\.')"   # 必须 8（§6.2.1 定义）
echo "提示词八段: $(awk '/^## ⑫ /,/^## ⑬ /' "$F" | grep -c '^【任务】\|^【依赖】\|^【要新增的类】\|^【核心约束】\|^【注释要求】\|^【验收标准】\|^【禁止】\|^【输出格式】')"  # 必须 8（§6.2.1 定义）

# ── B 组：存在性 + 覆盖关系（数字做对比与记录，充分性由 ⑯ 自检判定）──
SECTIONS=$(awk '/^## ⑥ /,/^## ⑦ /' "$F" | grep -c '^### 6\.')                # ⑥ 被讲文件段数（限定 ⑥ 节内统计，避免误匹配其他节的 ### 6.x）
TABLES=$(awk '/^## ⑥ /,/^## ⑦ /' "$F" | grep -c '逐行要点表')                 # 逐行要点表数
echo "⑥段数=$SECTIONS  要点表数=$TABLES"                                     # 覆盖关系：要点表数 ≥ 段数（★类按职责段拆讲可一节多表）；少于段数 = 有段漏表
echo "★类回放: $(awk '/^## ⑥ /,/^## ⑦ /' "$F" | grep -c '逐步回放')"          # 存在性：本批有★类则必须 ≥1（含失败路径回放）
echo "★为什么块: $(awk '/^## ⑥ /,/^## ⑦ /' "$F" | grep -c '【讲解】')"        # 存在性：本批有★类则必须 ≥1
echo "行号标注: $(awk '/^## ⑥ /,/^## ⑦ /' "$F" | grep -o '// :L[0-9]*' | wc -l)" # 存在性：应 >0（格式为 `// :L<真实行号>`，与 §6.4 ⑥ 的 `:L` 约定一致；密度充分性靠 §6.1.1 自检）
# ★类源码完整性（每个★类跑一次，SRC/cls 换成该类源文件路径与类名；摘录式在这里现形）
SRC="模块/src/main/java/.../Foo.java"; cls="Foo"
echo "★完整性[$cls]: 源文件=$(wc -l < "$SRC")  讲解最大:L=$(awk -v c="$cls" '/^### 6\./{p=($0 ~ c)}p' "$F" | grep -o ':L[0-9]*' | grep -o '[0-9]*' | sort -n | tail -1)"
# 判定：讲解最大 :L ≥ 源文件行数 × 0.8 = 全类贴码；明显小于 = 摘录式，当场用脚本补全类
echo "⑫三分类: $(awk '/^## ⑫ /,/^## ⑬ /' "$F" | grep -c '开发任务\|AI 协作过程\|复刻对照')"   # 存在性：应 ≥3（八条各带标签）
echo "⑫提问回链: $(awk '/^## ⑫ /,/^## ⑬ /' "$F" | grep -c '^- 「')"           # 存在性：应 ≥1（数量按真实协作情况，4~6 条为常见量而非门槛）
echo "⑫反馈轮次: $(awk '/^## ⑫ /,/^## ⑬ /' "$F" | grep -c '第 [0-9]* 轮')"    # 存在性：应 ≥1（轮次如实——顺利批 1 轮也合规，每轮四段必须完整）
```

**判定与处置**：
- **A 组任何一项不符 = 不过关**，当场修，修完**整套重跑**（改 ⑫ 可能影响结构项）。
- **B 组判定**：覆盖关系不成立（要点表数 < 段数，即有段漏表）或有★类但回放/为什么块为 0、行号标注为 0、任一★类"讲解最大 :L" < 源文件行数 × 0.8（摘录式贴码）= 不过关当场修；其余计数仅记录留档，**充分性**（每张表讲没讲因果、回放含不含失败路径、八条每条是否有实质内容）由 ⑯ 自检逐段核对。
- 全过之后，⑯ 自检表末尾追加："合规性自查已跑：A 组 6 项全过；B 组覆盖关系成立、存在性与★类源码完整性全过，充分性核对结论=……"
- **批次间对比（质量水位防漂移）**：每批自查时**顺带输出与已交付批次的对比表**（总行数 / ⑥⑫ 行数 / 要点表 / 行号标注 / ★回放 / 讲解块 / 问答 / 反例）——任一指标明显低于历史批次水位即当场补齐（示例：某批行号标注 15 vs 历史水位 79 → 补★类关键行至水位）。**"提速不丢信息"靠这张对比表持续验证，不靠口头承诺。**
- 此检查**不能替代人工抽查**——grep 验证"结构合规与覆盖完整"，⑯ 自检验证"内容充分"，两者都要做。

## 7. 输出目录

教材必须落盘到目标项目的 `NOTES/教学讲解/`：

```text
NOTES/
  00-系统全景地图.md
  项目文件覆盖矩阵.md
  概念词典.md
  阶段对照-完整性地图.md
  教学讲解/
    00-总索引.md
    阶段N-主题/
      00-阶段总览.md
      批次M-主题.md
```

每个总览列出批次、文件范围、业务闭环、依赖关系、验证状态和下一步链接。每批次完成立即写盘并更新索引。

跨会话续传必须以磁盘状态为准。每批更新 `AGENTS.md` 或项目约定的状态文件，至少写入：当前阶段、当前批次、已讲文件数/总数、未完成文件、最近验证命令与结果、已知风险、下一步。不得依赖聊天记录恢复进度。

## 8. 交互约定

用户说“继续复刻”“继续学习”或 `next` 时，读取约束文件、全景地图、覆盖矩阵、最近教材和 Git 状态，从未完成项继续。

用户说“讲解 X”时，输出并落盘 X 的完整教程；缺少必要上下文时先补上下文，不要求用户手写。

用户说“只要产出”时，直接扫描、实现、验证和归档，不发起问答式流程。只有目录边界、写入位置或安全前提无法推断时才提出简短问题。

每次运行结束时，在回复中固定报告：当前阶段/批次、已讲文件数/总文件数、已验证/未验证数量、已落盘文件、阻塞项和下一步。回复只是摘要，完整教材必须以磁盘文件为准。

## 9. 质量禁区

- 不漏讲文件，不把“框架自动处理”当解释；
- 不只讲外围 API、名词或 README；
- 不编造源码、运行结果、性能数据和故障；
- 不用“高可用、易维护、解耦、方便扩展”等空泛词代替因果链；
- 不把玩具骨架冒充等价实现；
- 不强制用户手写、复述、提交或闯关；
- 不压缩掉业务、底层、测试和工程视角；
- 不把未经验证的推断写成事实。
- 不把“已经扫描”写成“已经讲解”，不把“已经讲解”写成“已经验证”；
- 不用固定文件数、固定题数或固定批次数套项目，所有数量以真实覆盖矩阵为准；
- 不因项目规模大而只讲入口和核心类，外围文件必须进入覆盖矩阵并给出适配其复杂度的说明。

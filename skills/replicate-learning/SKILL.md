# 复刻式学习方法（技能入口）

> 这是什么：**通过直接复刻一个成熟项目 + 把每类讲透，来快速学会它**。配置/目录等工程惯例从原项目抄，机制/算法也从原项目复制并讲清楚——**不强制使用者手写第一版**，重点是把「它为什么这么做、转译成自己的代码」讲透，让人快速理解。
> 非强制规范，适配而非照抄。
> 深入：方法论全量在 `docs/复刻式学习方法-通用.md`；讲解深度基准在 `examples/黄金样例.md`；可复用模板在 `references/`。

## 面向谁 · 讲解到多深（先立这条，全程贯穿）

- **默认读者 = 初学者**：只假设你**懂一门语言 + 基础语法**（变量、循环、函数、类、基本类型，其余一律不讲默认会）。任何你没见过的词，讲解都必须**当场停下用大白话 + 例子讲一句**，不许甩名词、不许让新手靠猜。
- **解释必须「到底」（术语不自举，无悬空引用）**：任何解释（先修概念/行注释/实现四问/调用链）里出现的每个词，要么是**生活语言或语言基础**，要么是**本文此前已解释过的**——**禁止用术语解释术语**：拿「预检请求」解释 OPTIONS、拿「异步派发」解释 `DispatcherType.ASYNC` 都是悬空（"预检""派发"本身也是生词，等于没解释）。判定法：把解释读给"只会语言语法的人"，每读到一个词他都认识吗？有一个不认识且没铺垫 = 悬空，**继续往下拆到落地为止**。底层机制**首次出现拆到底**，同批内再出现可简写「见先修概念」。
- **每一个类都讲满深度，不做分级降档**：不管这个类是「复杂机制」还是「一个 DTO / 配置 / 常量」这种零件，六段都**完整走一遍、讲到新手能看懂每一行为止**。区别只在于内容的**份量**（机制行多、DTO 行少），**不降讲解深度、不缩结构**。
- **每一步给你的信息都从「初学者视角」写**：先修概念、业务定位图、逐类六段、验收问答、构建验证——所有流程产物都以「一个只懂语言的人能跟着走通」为合格线。
- **代码必须自带详细注释（写进真实源码文件，每处答三问）**：写码落盘时，就把**逐行级中文注释**写进真实的 `.java`/`.py` 等源文件里。每处注释按**三问**写——**①这是什么**：这个 API/机制本身是什么，一句话落到已知地基（解释里出现新词就继续拆，不许悬空）；**②为什么这行要它**：本行的目的；**③不这样会怎样**：反例（关键分支才写）。**只写"为什么"不写"这是什么" = 没注释**（`// 预检放行`四个字不合格，`OPTIONS` 是什么、预检是啥流程必须讲清）。目标：学习者在**不打开任何讲解**的情况下，光看源码文件就能读懂每一段在干嘛。讲解里的「代码逐行」直接照这份已注释的源码讲，不重复劳动。
- **底层穿透（防「API 调用工程师」，硬要求）**：这类项目的代码**大多是层层包装的框架 / 外部工具 / 中间件 SDK 调用**（注解、拦截器、ORM、Starter、客户端）。如果讲解只是「这行调了 X 的 Y 方法做 Z」，学完 = 记住一份 API 清单，**换个框架就归零**——那是 API 调用工程师，不是开发工程师。所以**凡遇到框架 / 外部工具 / 中间件 / SDK 的调用，一律往下剥，按类的重要性决定剥到第几层**：

  | 层 | 要回答什么 | 达标一句话（含「拆到底」硬要求） |
  |---|---|---|
  | **L1 机制层（所有调用必做）** | 它内部是靠什么做到的？它替你干了哪几件事？ | 能说清「换我自己写是哪些步骤」，**且每个机制词都拆到底、无悬空**——「用 @Around 环绕」「ThreadLocal 是线程私有」这类还是悬空词，要拆到「Spring 给 Bean 生成代理对象、方法调用先过代理 invoke」/「数据存在 Thread 对象的 threadLocals 表里」这种落地层 |
  | **L2 手写层（★ 类与核心依赖必做）** | 不用它，我怎么写一个最小可用版？ | 能写出 20~40 行等价手写实现，**且要「够真」非玩具骨架**——不能只写 try/catch+save 糊弄，要把框架真正替你扛的边界写出来（ThreadLocal 清理 / 失败改写 / 模板求值 / 回调解耦） |
  | **L3 取舍层（★ 类必做）** | 它为什么这么设计？什么时候不该用它？ | 能说出「不用它会出什么**具体**故障」——最好**分钟级时序推演**（"业务 01.250 rollback 把审计一起回滚"），不是"难维护"这种形容词 |

  落地三件套：**①剥一层**（把「框架替你做的 N 件事」逐件拆到「它怎么做到的」——能指到关键类/方法名就指；**指不到也要拆到底**：机制词不许悬空，讲 ThreadLocal 就要讲到 Thread 对象里的 threadLocals 表、讲 AOP 就要讲到代理对象/动态代理，讲 SpEL 就要讲到词法→语法→求值）→ **②手写最小版**（No-Framework 等价实现，20~40 行，**证明没有这个框架你自己也做得出来**；**要够真，不是玩具骨架**——try/catch+save 那种漏掉「清理/失败改写/模板求值/解耦」的 30 行糊弄版不合格，要写出框架真正替你扛的边界）→ **③反例推演**（把这个能力「关掉」，推演会出什么故障，**最好落到分钟级时序**：**「第 3 个并发请求读到脏数据」「业务 01.250 回滚把审计一起回滚」算，「代码会难维护 / 容易出错」不算**——抽象形容词不合格）。

  **L2「够真」vs「玩具骨架」的硬判定（防自己骗自己）**：手写版写完，逐条核对——**它写出框架真正替你兜的边界了吗？** 不是"能取数就行"，而是把这些边界至少写出 3~4 条才算够真：
  | 骨架与否 | 判定 |
  |---|---|
  | ❌ 玩具骨架 | 只写"try/catch + save/取数"30 行就完事，框架替你扛的**清理 / 失败改写 / 模板求值 / 解耦 / 递归嵌套 / 转义解析 / 连接池**这些边界一条没提，读者看完"就这？"感受不到框架价值 |
  | ✅ 够真 | 把框架真正替你做的**边界逐条显式写出**（如 @ConfigurationProperties：松散绑定 `open-duration-ms→openDurationMs`、递归嵌套 `providers.ollama.url`、List/Map 自动绑定、`${}` 占位符解析、缺省默认值；OkHttp：连接池复用、gzip/字符集、超时、Call.cancel、代理——手写版写不出的部分**逐条点明它们去哪了**） |

  **L3「具体故障」vs「形容词」的硬判定**：写完"不用它会怎样"，把它改成"哪个请求、在什么时刻、出什么具体错"——如「业务 01.250 提问 → 读到一个全 null 的配置 → 选不出模型 → NPE，且因启动时没校验、是运行时才炸」算；「代码会难维护 / 容易出错 / 不优雅」不算。**凡写成形容词的 L3，回炉改成具体的"人-时-错"三元组。**

  **零件类 ≠ 说明书（防把 DTO/枚举/配置讲成字典）**：零件类六段照样走满，但要有**具体的人在用 + 方案对比 + 反例**——一个枚举也要像机制类那样有"具名人物 + 具体故障"（"同事把 'bailian' 拼成 'BaiLian'，路由 equals 失配静默跳别家"），而不是"它存了这几家的 id"。**凡六段里出现"它就是个枚举/这个类很简单"，说明滑向说明书，回炉改成"谁在什么时候会被它咬一口"的镜头。**
  
  **示例密度**：本批至少 **1 张完整穿透卡**（三件套齐全，给本批最「包装」的那个依赖）；其余非核心 API 至少做 L1（一句话机制）；**★ 类必须打满三层**。穿透内容落在六段的 ③（手法问）/ ④（API 注释的「这是什么」）/ ⑥（No-Framework 对照），**不另设第七段**。

  **穿透点清单（每批开工先列、逐条销号，防漏穿透）**：这是把「凡框架/工具/中间件/SDK 调用必穿透」从原则变成**可执行动作**——本批写码前，先把代码里出现的**每个外部调用点**列成一张清单（框架注解、ORM、工具类方法、Starter、客户端…），逐条判「归哪类、穿到哪层、销号了吗」：

  | 调用点类型 | 穿透要求 | 销号动作 |
  |---|---|---|
  | 本批**新出现**的框架/工具调用 | 打满三层（至少 1 张完整穿透卡 + 其余 L1） | L1 拆到底（指到真实类名，无「扫描/改写/环绕/线程私有」这类悬空词）；L2 手写版够真；L3 有分钟级时序 |
  | 前面批次/黄金样例**已穿透**过的调用 | 不重复拆，但**必须显式引用**「机制见批次N / 黄金样例 §X」 | 引用一句话 + 指向，不让读者以为没讲 |
  | 语言/平台级（JDK 内置） | 首次出现拆到底，同批内再出现「见先修概念」 | 同「解释必须到底」条 |

  **判定（防糊弄）**：L1 写完后自问——「我是不是还在用『扫描/改写/环绕/私有/解析』这类**悬空动词**？它到底落到哪个类、哪个方法、哪个字段？」答不上 = 没拆到底，回炉。**参照 `examples/黄金样例.md`「一·续三」的例④**：@TableLogic 的 L1 若只写「MP 扫描实体后改写 SQL」就是悬空，要拆到「TableInfoHelper 解析 @TableLogic 进 TableFieldInfo.logicDelete → DefaultSqlInjector 按实体有无逻辑删除字段选 SqlMethod.LOGIC_DELETE_BY_ID（生成 UPDATE）而非 DELETE_BY_ID → select 的 where 由 TableFieldInfo 自动 append AND deleted=0」。

## 认知主线 · 三层递进（业务 → 架构 → 代码，每类都按这个顺序走）

熟练 vibecoding 的前提，是**先有业务能力 → 再有架构设计能力 → 最后能看懂并掌控代码**。所以每类的讲解，都按这条自上而下的认知主线推进（它**不是新造结构，而是给六段加一条顺序准绳**）：

| 层 | 你要练的能力 | 对应六段 | 这一层讲完，你要能回答 |
|---|---|---|---|
| **第①层 业务能力** | 这软件在解决什么、这个类服务哪个业务闭环动作 | ①业务场景（+ 业务闭环定位图） | 「不写代码时，业务上到底要解决什么？删掉这个类，哪个业务问题会回来？」 |
| **第②层 架构设计** | 它站在系统哪一层、上下游是谁、依赖方向怎样、为什么放这 | ②架构位置 | 「它为什么放这一层而不是别处？谁依赖它、它依赖谁，方向对不对？」 |
| **第③层 代码实现** | 每行干嘛、调了什么、**为什么这么设计（还有哪些方案、为什么选这个）**、换我怎么做 | ③实现四问（开发四问）+ ④代码逐行 + ⑤调用链（⑥用法是"会用"的收口） | 「这段代码做了几件事、每件事怎么落地、每个 API 内部怎么做到、**为什么这么设计而不是别的方案、不用框架我怎么做**？」 |

**每层讲完 + 每类讲完，都要做「脱手复述测试」（见下）——这是你「可控 vibecoding」的度量器。**

## 核心思路（一句话）

**直接复刻（样板从原项目抄、机制从原项目复刻）+ 讲解讲透**；每类按**六段**讲透（业务场景→架构概念先补→实现四问→代码逐行→调用链→用法），**每一类都讲满深度**；按「相关类聚合」分批（见下）；每批即构建验证 + 讲解 + 落盘 + **commit**；完成归档 `NOTES/阶段N` + 勾完整性地图 + 更新进度表。**做中学 + 具象化**：直接复刻 + 写码先行 = 动手做（清华 OpenMAIC 的共识：动手优于被动听）；数据流/状态机/调用链等"关系"类内容，能用 ASCII 图/流程图就画一张，别只文字。

## 第一步 · 先问在哪复刻（务必先确认目录）

开始前先问使用者：**要在哪个目录做这次复刻**。据此给目录规范——**官方项目（被复刻的原项目）和复刻目录放在同一级**最好（便于对照 diff、官方只读互不干扰、路径短好找）：

- **本地已有项目**：在**该项目的父目录**下建复刻目录。例：原项目 `D:\dev\myapp` → 复刻目录 `D:\dev\myapp-replica`（同级）。
- **给出 GitHub/远程仓库地址**：先建议一个"项目根"，把官方项目 clone 到该目录，复刻目录也放**同级**。例：`D:\projects\` 下 clone 官方 → `D:\projects\myapp-book`，复刻目录 `D:\projects\myapp-replica`。
- **确认后**：复刻目录 = 本项目根（`AGENTS.md` 就放这里面）；官方项目作为**只读答案卷**始终放在旁边，供对照与 diff。

## 第二步 · 在复刻目录建"开局三件套"

1. `AGENTS.md`：复制模板，填项目名/进度/学习资料指针（模板在 `references/AGENTS.md-复刻增量模板.md`）。
2. `NOTES/阶段对照-完整性地图.md`：把官方项目交付面拆成阶段勾选清单，**★ 标注「重点/难点」**（含算法/状态流转/路由/编排/并发/兜底等逻辑较难、要多花时间讲透的类）。★ 只是「这类的机制逻辑较难、讲透它要花更多工夫」的路标，**不再关联讲解深度**——所有类都同样满深度。
3. `docs/阶段0-开工清单.md`：跑通参照环境的命令序列（阶段0 = **跑通参照**，不是写代码）。

大型项目/多阶段长周期，再额外产出一部《全链路拆解文档》当地图。

## 批次质量基准对照（每批开工与落盘前必做，防"批次间质量漂移"）

> 事故复盘：批次 4 效果好是因为它是被点名批评后**专门重写**的；下一批没对照它就"自由发挥"，出现六段子标题消失、零件类压成大纲句、源码逐行注释归零——**同一套 skill，批次质量却时高时低**。根因：讲解质量没有"批次间基准继承"，每批全凭当场发挥。解法是把"对照基准"变成强制动作：

- **开工前对照（写码/讲解前先做）**：打开 `examples/黄金样例.md`（深度基准）+ **本项目里最近一个"验收通过、你或学员认可"的批次落盘文件**（格式基准），先对齐三样再动手：① 章节骨架（先修/闭环/类清单/调用链/**逐类六段独立成节**/验收/证据/diff）；② 源码注释密度（达标批源码方法内**有逐行中文注释**，不是只有类 Javadoc）；③ 验收形态（脱手复述题数=类数 + 三层出题带答案）。**禁止不打开基准文件直接开写**。
- **源码注释是复刻产物的一部分（写码这步就做，diff 只对代码行）**：答案卷源码往往没有注释——**"跟官方 diff 零差异"只适用于代码行，注释必须自写**（逐行中文、每处答三问：这是什么/为什么这行要它/不这样会怎样）。凡"代码照抄官方、注释也照抄（=没有）"的批次，学习者关掉聊天打开源码就读不懂，必返工。落盘 diff 结论里应写明"代码行 diff 零差异 + 注释为自写增强"两件事。
- **批量不稀释格式**：一批件数变多时，**份量可以短、结构不能缩**——每个件仍是独立六段小节（`### 类 N/M` + 六段子标题），验收题数 = 件数只增不减。宁可把批拆小，不可把非核心件压成加粗大纲句。件多时逐件六段照写，写到核心件自然展开，写到零件自然收短，深度与结构不变。
- **落盘前用达标批做结构 diff**：写完该批文件，和基准批文件并排比章节标题（`grep '^### '` 数独立小节、六段子标题是否齐全、验收题数是否=件数），少了就补，不靠自我感觉。

## 然后 · 标准讲解循环（批次 = 相关类聚合；批只控节奏，不降深度）

**对每一批按序走完这六步。每个类都走**完整六段**；批量只影响"一批装几个类"，不影响每类深度——每一类都讲满深度。**

## 逐类讲解开工 Gate（写码 + 讲解每一类之前必过，过不了就停下，不许带病往下写）

> 为什么要有这个 Gate：前面几批反复"讲完被指出、再事后补"——六段缩水、注释归零、场景无人物、L1 停在悬空动词。根因不是规则不全，而是**规则都写成了"事后检查"，没做成"动笔门禁"**。事后检查必漏（写完就不愿返工），门禁才能根治。**时机关键：写码时逐行注释就要答「①这是什么」到机制层，所以穿透证据表必须在写码前就产出——不是讲解时才补。** 讲每一个类之前，先产出两张中间产物，过了再动笔：

**Gate 1 · 穿透证据表（堵「凭印象写机制」→ 先查证再写，写码前先做）**：扫出这个类用到的**每个外部调用点**（框架注解 / ORM / 工具方法 / SDK / 客户端），逐个填表——

| 调用点 | 真实机制（真实类名+关键实现，禁悬空动词） | 不用它我怎么写（L2 一句话） | 不用会怎样（L3 一句具体故障） | 证据来源 |
|---|---|---|---|---|

- **「真实机制」列必须先查证再填**：去读本地依赖的反编译源码（`~/.m2` 的 jar / IDE 点进去）、官方文档、或 GitHub 源码仓库，拿到**真实类名 + 关键实现**（如 `DefaultSqlInjector#injectMappedStatement`）才写。**凭训练记忆写「扫描/改写/注册/接管/环绕/私有」这类悬空动词 = 没查证 = 停下重查**。
- 前面批次已穿透的调用点填「见批次N / 黄金样例 §X」，不重复拆，但必须显式引用。
- 表填完，①写码时的逐行注释、②六段里的 ③手法 / ④API 注释 / ⑥No-Framework 三段，**都直接照这张表写**——写码与讲解共用同一份查证结论，不会漏、不会悬空。

**Gate 2 · 六段骨架（堵「结构缩水」，讲解动笔前）**：对照 `examples/黄金样例.md` + 本项目最近达标批文件，**先写出六段子标题 + 每段一句话要点**（①场景：哪个具名人物 + 什么数值 ②位置：哪一层 ③四问：哪几条 ④代码：贴哪几方法 ⑤链：几跳、带哪些类名 ⑥用法：什么触发回放），确认「独立成节 / 具象人物 / 逐行注释落点 / 穿透卡落点」四样都在，**再**填全文。禁止跳过骨架直接写全文。

**每类讲完 10 秒自检（3 条，任一 No 回炉）**：① L1 里还有「扫描/改写/环绕/私有」这类悬空动词吗？② 场景里有具名人物 + 具体数值吗？③ 六段独立成节、代码贴整方法（没标"节选"）吗？



- **0️⃣ 先修概念**：把本批涉及、但初学者可能不懂的概念用大白话先解释一遍（不默认会；任何词首次出现给一句解释）。**每句解释 = 大白话 + 一个生活化类比/例子**——类比是记忆钩子，纯定义难记（token=游乐园手环、Redis=键值仓库、HTTP 请求=一封信分信封+信纸；AOP=给方法门口挂道门帘，进出前后自动登记）。**禁止只给「术语→术语定义」**（「AOP=在方法前后插逻辑的技术」是纯定义、无钩子，不合格）。**扫描范围不只业务/框架词，还包括底层平台与协议机制**——HTTP 方法（GET/POST/OPTIONS…）与 CORS 跨域预检、Servlet 容器/过滤器链/请求分发类型、线程池、序列化……都在内。**判定法**：扫一遍本批代码和讲解草稿，凡"解释它时不得不再用另一个没讲过的词"的，全部进先修（如「预检」要讲，就得连 CORS/跨域一起讲）。
- **1️⃣ 业务闭环定位前置**：先输出「业务闭环定位图」——本批每个类在主链路（如 提问→理解→检索→生成→溯源）的哪一段、服务哪个业务场景，一句白话。从全局定位落到类，禁止孤立地逐类念注释。
- **2️⃣ 《本批类清单表》**：列出本批每个类 + **建表脚本 / 配置文件等非类件**（**不再分级，统一满深度**）+ 每个一句「它是干嘛的」（此处不展开讲解，只为让学员先看到全局 X 件；真正的讲解在 ③ 逐类六段）。**答案卷里复刻范围内的文件都要入表**——SQL 建表脚本、yaml/properties 配置同算讲解对象，不许漏文件只挑 .java 讲。
- **3️⃣ 整批写码 + 逐类六段讲解**：**先写该批次的全部类**（复刻出你的实现；写码先于讲解，用户可全程对照真实码）→ **再逐个类照码讲六段**（①业务场景→②架构位置→③实现四问→④代码块逐行→⑤调用链≥8跳→⑥用法），**必须 1 类 1 节、禁止合并**（即便整批先写完，讲解也要逐类完整、不揉成一段）；同类样板才可共享"先修概念+调用链"，每类代码块与用法示例必须各自出现。**讲解必须落到已写好的码上逐行讲**；**整批写完不逐类讲=没讲完**。**对初学者友好（六段每一段都适用）**：术语/概念/手法/API 首次出现都用大白话+例子点一句、不许甩名词、**解释禁术语悬空（见上「解释必须到底」）**；**实现四问 = 开发四问（训练「设计 + 权衡 + 独立实现 + 工程判断」，不是描述 API）**——四问缺一问即不合格，每问完整教学句，禁电报体名词串（「手法：A+B」一行完事 = 不合格）：
①**思路**（拆解能力）：它要解决什么 + 整体分几步 + **为什么这么拆**（而不是别的拆法）；
②**设计决策**（权衡能力，开发工程师的核心）：**为什么这么设计？还有哪些备选方案？为什么选这个不选别的？代价/取舍是什么？**——如「为什么用逻辑删除不用物理删除」「为什么 after 要重查库而不用内存对象」都要给方案对比，不是只陈述现状；
③**手法**（独立实现能力）：每个手法 = **是什么 → L1 它内部怎么做到（拆到底、指真实类名）→ L2 换我怎么做（20~40 行手写）→ L3 不用会怎样（具体故障）**——穿透融进手法问，不另开一张卡；
④**数据流与边界**（工程判断能力）：数据怎么流转 + **异常/并发/降级/边界情况在哪、怎么兜底**。**六段排版独立成节**：每个类的六段各占独立小节（`### ① 业务场景`…`### ⑥ 用法`），段内能用 ASCII 图/表格就别只用纯文字（架构位置给层图、调用链给跳数链）；**禁止把六段压成一行式密集文本**（`**① 业务场景**：…` 全挤一段读起来死板、掉"教学姿态"）。**①业务场景 = 具名人物 + 具体数值 + 镜头感（硬要求，不是可选项）**：每个类的场景段里要有**有身份的人**（运营小李 / 审计员老王 / 新用户小王，带名字，不是「用户/运营/请求」这种无名字的抽象主体）+ **一个具体数值或具体改动内容**（"把答案从 A→B 改成 A→B→C"、"传 200MB 的文件"）+ **期望结果**（"他想知道上个月这条是谁改的"）；**本批定一个贯穿人物**（一个业务域一个主人翁，如 CRUD 批用「运营小李」），从业务闭环定位到每个类的场景都用 TA，读起来像连续剧而不是散点档案——参照 `examples/黄金样例.md`「一·续二 通俗度对照」。**判定：场景里出现「用户/请求/系统」而无人名无数值 = 抽象句，回炉改成具象镜头。****注释要求（写码这步就做，不是讲解时才补）**：写进真实源码文件的注释要**逐行级中文注解、每处答三问（①这是什么 ②为什么这行要它 ③不这样会怎样）**——类头职责、方法头步骤、每个关键行 + 每个陌生 API/库调用全覆盖；这样讲解④里的「代码逐行」照这份已注释源码直接讲，学习者关掉讲解也能单独读懂源码文件。**底层穿透在六段里的分工（见上「底层穿透」条，不另设第七段）**：③实现四问的**手法**——每提一个框架/工具手法，必须补一句「它内部怎么做到的」（L1）；④代码逐行的**每个陌生 API**，三问的「①这是什么」要答到**机制层**（「它内部靠 X 做到的」），而不只是「它是干嘛的」；⑥用法**末尾必须给「No-Framework 最小手写版」**——不用这个框架/工具，你自己怎么写 20~40 行等价实现（★ 类与核心依赖必给，其余至少一句「手写的话要做哪几步」）。**禁止通篇「这行调了 X 的 Y 方法做 Z」就翻到下一行**——那是 API 清单，不是讲解。
- **4️⃣ 每批验收 · 三层出题 + 脱手复述（都附标准答案）**：本批讲完立即验收，**两层都做、且每一题的"标准答案"当场给出（不是只出题让学习者自己猜）**——①**脱手复述测试（每类必做，题数 = 本批类数，动态不固定）**：让学习者**合上讲解，光凭自己写的源码（含注释）**，用自己的话复述这个类「业务上解决什么 / 架在哪个位置 / 代码分几件事、每件怎么落地、每个 API 干嘛」；**复述题列出后，紧跟每题的"标准答案"**（一问一答式，按三层组织），学习者复述完照答案核对，磕巴卡壳的点 = 回炉该层；①·五 **脱手手写（★ 类与穿透卡必做，检验"能不能自己写"而非"能不能背"）**：针对本批 ★ 类或穿透卡的那个框架依赖，让学习者**合上讲解与源码，手写 No-Framework 等价实现**（如不用 @TableLogic 手写逻辑删除、不用 @LogRecord 手写审计切面）——**复述检验"理解了没"，手写检验"真会了没"**；写不出 20 行能跑的等价版 = 底层没通透、还是 API 调用工程师，回炉重讲该依赖再手写；②**三层出题带标准答案（一问一答，题数随批动态）**：按业务/架构/代码三层**分别**出题，**每层出几题 = 该批该层的实际知识点与难点数**（一批有 2 个 ★ 机制难点，代码层可能出 3~4 题、业务层 1~2 题）——**禁止死板"各一题"**；每层至少 1 题、题数随本批类量与难度增减，每题**紧跟标准答案**（不是事后打分；答错/含糊的点=回炉该层）。
- **5️⃣ 每批构建验证**：每写完一批立即构建/测试并如实汇报证据（证据先于断言；不许"全部写完再一次性验证"）。
- **6️⃣ 归档（讲解全文落盘 + 工程三件套，讲完即写，不等阶段结束）**：
  - **① 讲解全文落盘到 `NOTES/教学讲解/`（学习资产，「阶段→批次」两级目录）**——**为什么要落盘：聊天窗口会随会话变长被压缩折叠，讲过的内容回头就翻不到了**（真实事故：某阶段批次2 的整份六段讲解在聊天里消失，只能整批重讲）。所以课堂上那份**完整六段讲解必须整篇写进文件**，不是摘要：

    ```
    NOTES/教学讲解/
      └─ 阶段4-system支撑域（Sa-Token认证+审计变更日志）/        ← 目录名带本阶段关键技术
           ├─ 00-阶段总览.md                                    ← 索引：定位 + 批次清单链接 + 进度
           ├─ 批次1-SaToken认证三件套（三件套+UserDO+UserRole）.md
           ├─ 批次2-Auth登录登出（AuthServiceImpl★+LoginVO）.md   ← 文件名带本批核心类
           └─ 批次3-审计写侧（BizChangeLogContext★+RecordService）.md
    ```
    - **命名规则（括号里"跟什么有关"的标注是强制的）**：阶段目录 = `阶段N-<主题>（<本阶段关键技术 2~3 个>）`；批次文件 = `批次M-<一句话主题>（<本批核心类，★ 标重点>）`。**目的**：日后扫一眼目录就知道每批讲了什么、涉及哪些类，不必逐个点开。**约束**：总长 ≤40 字；禁用 Windows 非法字符 `\ / : * ? " < > |`（多个类名用 `+` 连接，别用 `/`）。
    - **每个批次文件 = 课堂那份完整讲解的全文**，八块齐全：先修概念 / 业务闭环定位（含定位图）/ 本批类清单表 / 全局调用链图 / **逐类六段全文**（每类独立一节：①业务场景 ②架构位置 ③实现四问 ④代码逐行·整方法贴全 ⑤调用链≥8跳带类名 ⑥用法+触发回放）/ 验收（脱手复述题（题数=类数） + 三层出题（每层题数随批动态），**题后紧跟标准答案**）/ 构建验证证据 / 溯源与答案卷 diff 结论。模板见 `references/批次讲解全文模板.md`。
    - **落盘前自查（任一 No 不得落盘，回炉补到 Yes）**：写完逐批文件，对照 `examples/黄金样例.md` 的「三、讲解产出自查」逐项过——①场景有具体的人+数值吗 ②调用链 ≥8 跳带类名吗 ③代码整方法没标"节选"吗 ④用法能复制改改就跑吗 ⑤先修概念带生活化类比吗 ⑥六段独立成节没压成一行式吗 ⑦关键依赖剥开一层讲机制了吗（★ 类给了 No-Framework 手写版吗） ⑧「不用它会怎样」是具体故障推演吗（不是「难维护/易出错」这类抽象形容词）。
    - **写入时机**：**一批讲完立即写该批文件 + 更新 `00-阶段总览.md`**。禁止"攒到阶段结束一起写"——中途开新会话就拿不回聊天里的讲解了。
  - **② 工程三件套（状态与索引，与①分工）**：勾完整性地图对应条目 + 更新 `NOTES/阶段N-主题.md`（**只放机制摘要 / 构建证据 / 下一步等状态与索引，讲解全文一律链接到①**）+ 更新 AGENTS.md「当前进度+下一步」；**每批验证通过即 commit（一批一个 commit = 一个可运行最小增量，不攒到阶段收尾；`NOTES/` 等学习件是否入 git 按项目约定，此处不强求）**。

**深度基准**：每个类的六段都按 `examples/黄金样例.md` 的**单类**尺度校准（详深度只按"件"计，批量不共享、不稀释）；一批装多少个件，判据是**每个件（类/脚本/配置）都还能走满同一个满深度、不压成大纲句**。六段结构与完整性每件不变，份量随件的体量自然伸缩（机制行多、DTO 行少），深度不打折。

## 分批（分阶段 → 按「相关类聚合」分批 → 每件都满深度）

项目先拆成**阶段**；某阶段开工先出**《类清单表》**（覆盖本阶段所有该复刻的官方文件：类 + 建表脚本 + 配置文件），学员确认范围后**按主题切批**。批次怎么分，看三条：

- **批 = 当前做的那件事涉及的相关类聚合**：一批装「同一件事 / 同一自洽主题」的件（如"审计写侧"8 类、"示例问题 CRUD"9 类 + 建表脚本、"登录认证"6 类 + yaml），讲完这批能看见这件事完整跑起来。**数量不设死上限（废除旧「每批 ≤3 类」）**，判定标准是**每个件还能不能六段满深度讲完、不压成大纲句**——3~9 件是常见合理区间；**十几个/几十个件塞一批 = 必然压成大纲句**，就该按主题切块（写侧/读侧、地基/入参/真身、样板/机制）拆多批，宁可多批不量产；反过来 3~5 个强相关的件也不该硬拆成单件批（同一件事拆碎 = 重复上下文、看不到闭环）。
- **每批 = 一个可运行的最小实现增量**：一批写完（代码 + 脚本 + 配置）即构建验证 → 逐件六段讲解 → 落盘 → **commit**——一批一个 commit，不攒到阶段收尾（最小实现原则）。
- **讲解覆盖面 = 复刻范围内官方所有文件**：不只 .java——`schema_pg.sql` 这类建表脚本（建了什么表、每列动机、索引为什么这样建）、application.yaml 这类配置（每个旋钮字段语义、怎么被注入）都要入表、都要讲；答案卷里该复刻的文件不许漏讲。

每阶段开工先出**《类清单表》**：列出本阶段每个件 + 该件的「是什么/它干嘛的」一句，学员确认范围后才开讲；不再分档，全部按满深度六段讲。

> 意图：**每一件都满深度**（学深），不分"机制/样板"高下、不做降档；节奏靠**按主题分批**控，不靠降深度省时间。**全量六段叙事必须落盘进 `NOTES/教学讲解/阶段N-x/批次M-y.md`**（聊天会被压缩折叠，磁盘才是长期可读的载体），`examples/黄金样例.md` 仍作"讲到什么程度算达标"的基准锚点。清单表模板见 `references/类清单表模板.md`。

> **最少够用 vs 可裁剪**：主流程 = 问目录 + 三件套 + 类清单 + 六段 + 每批验证 + 归档续传（**含讲解全文落盘**）。**进阶件可裁剪**（时间紧就砍，不影响主流程）：《全链路拆解文档》（仅大型/多阶段才需要）、面试题卡、会话分配策略。**砍掉过度设计（YAGNI）**——第一版只做够主流程的最小闭环，别为"以后可能用到"的假设需求加料。
>
> **教学讲解全文不可裁剪**：它是唯一能跨会话回看的讲解载体（聊天会被压缩折叠），砍掉等于讲过即丢失。

## 续传 · "继续复刻"怎么接着做

每个阶段都已归档（`AGENTS.md` 的「当前进度+下一步」+ 完整性地图 + `NOTES/阶段N`）。所以下次用户说「继续复刻 / 接着做 / 再来」，或开了新会话，**先读 AGENTS.md + 完整性地图 + NOTES**，从当前状态续接——不靠对话记忆，磁盘就是记忆。

## 常见翻车

- **十几个/几十个类硬塞一批** → 必然压成大纲句。批次按「相关类聚合」（3~9 件合理），再大就按主题切块多批，宁多批不量产；但也不要反过来把 3~5 个强相关的类硬拆成多个单类批（同一件事拆碎 = 重复上下文、看不到闭环）。
- 讲解与实现不同轮、或"全批写完就收工不讲解" → 先写该批次的类、再逐类照码讲（用户直接看码）；别先空讲后写，也别只写码不逐类讲。
- **任何类被降深度/带过（尤其一个 DTO、配置、常量被当成"样板"一笔带过）** → 每一类都该满深度，别省；哪怕这个类只有 3 行，也要把「它为什么存在、数据从哪来、被谁用」讲透。这是学习深度，不是可省的成本。
- 写码前不先走读 / 不讲调用链+数据流 → 只讲手法名 = 没讲完。
- **写码落盘没写逐行中文注释（或注释没答全三问）** → 学习者打开真实源码文件看不懂每一段在干嘛，等于「代码没交付」。注释必须**写进源码文件**（类头职责/方法头步骤/每关键行+每陌生 API 按三问：①这是什么 ②为什么这行要它 ③不这样会怎样），不是只在讲解消息里贴。
- 不分批构建验证、"全部写完再验证" → 每批即验证，证据先于断言。
- **对初学者甩术语、假设对方"这我该会"** → 每个陌生概念/API 首次出现必须白话点一句，读者定位始终是「只懂语言 + 基础语法」的人。
- **用术语解释术语（悬空解释）** → 拿"预检"解释 OPTIONS、拿"异步派发"解释 ASYNC = 没解释。每个词要么是生活语言/语言基础，要么前文已讲过；有一个悬空就继续拆。
- **注释只写"为什么"不写"这是什么"**（如 `// ② 预检放行` 八个字带过）→ 注释三问少一问 = 没注释，回炉补"这是什么"。
- **实现四问写成电报体名词串**（"手法：A+B""边界：A/B/C"一行完事）→ 每问写完整教学句，按「开发四问」展开：思路（为什么这么拆）/ 设计决策（为什么选这个不选别的）/ 手法（带 L1/L2/L3 穿透）/ 数据流与边界（异常并发降级在哪）。
- **代码块标注"节选"** → "节选"就是片段，照样不达标——"源码文件里已有注释"不是节选的理由；④要么贴整方法/整段，要么该类本来很短就整文件贴出。
- **完整讲解只留在聊天消息里、没落盘** → 会话一长就被压缩折叠，回头翻不到（真实事故：某阶段批次2 的六段讲解在聊天里消失，用户问"给了吗怎么没看到"，只能整批重讲）。每批讲完**立即**整篇写入 `NOTES/教学讲解/阶段N-<主题>（技术）/批次M-<主题>（核心类）.md`。
- **目录/文件名不写"跟什么有关"**（如只叫 `阶段4.md`、`批次2.md`）→ 三个月后打开是盲盒，得逐个点开才知道讲了什么。命名必须带主题与技术标注。
- **把上一批的数字当常量照抄到本批**（真实事故：批次2 是 6 类，批次3 有 8 类，验收却沿用「复述固定 3 题」「三层各一题」，逐类标题还写成「类 8/6」）→ **所有数量都随本批动态定**：类编号分母 = 本批类数、脱手复述题数 = 本批类数、三层出题每层题数 = 该批该层知识点/难点数。没有一个数字是固定的，照抄上一批的 6/3/各一题 就会穿帮。
- **补写/落盘时滑向"文档体"**（真实事故：批次3 是节奏失控后"对着源码补写"，场景里没有具体的人、先修概念全是"术语→定义"、六段压成密集一行式、代码标"节选/10 个域略"）→ 落盘时把自己当成"正在给一个只懂语言的新手当面讲"，不是"整理档案"；写完自查六件套——**①场景有具体的人吗 ②先修概念有生活化类比吗 ③代码整方法没节选吗 ④调用链 ≥8 跳吗 ⑤六段独立成节带图/表吗 ⑥用法能复制吗**。
- **先修概念写成"术语→定义"、无类比**（"AOP=在方法前后插逻辑的技术"）→ 定义难记、读完还是抽象。每个词必须带生活化类比/例子（token=手环、Redis=仓库、HTTP 请求=信封+信纸、AOP=门帘），类比是记忆钩子。
- **讲解只罗列 API、不穿透底层**（真实事故：阶段4 通篇「这行调 `eq(...)` 拼条件」「这行调 `selectPage` 分页」，讲完只能照抄调用，换个 ORM 就不会了）→ 这是**API 调用工程师式讲解**，不合格。每个框架/工具/中间件调用至少剥一层讲「它内部怎么做到的」，★ 类打满三层（机制 + No-Framework 手写版 + 反例推演）。判定法：把讲解里所有 API 名字换成别的框架的同款 API，这份讲解还成立吗？成立 = 你讲的只是调用姿势，没讲机制。
- **「不用它会怎样」写成抽象形容词**（「代码会难维护」「容易出错」「不够优雅」）→ 读者感受不到代价，等于没讲。必须推演**具体故障**：哪个请求、哪条数据、在什么时序下会出什么错（如「业务事务回滚时审计记录会跟着被撤掉，事后查不到谁改的」）。
- **穿透卡停在「机制名词」层、又犯了术语悬空**（真实事故：第一次写穿透卡，L1 写「用 @Around 环绕」「ThreadLocal 是线程私有仓库」，读者读完还是不知道「环绕」「私有」是什么）→ 穿透的 L1 也要**拆到底、禁悬空**：环绕 → 代理对象（JDK 动态代理/CGLIB 子类）；线程私有 → Thread 对象的 threadLocals 表；SpEL 解析 → 词法→语法→求值。**穿透卡不是"更高级的先修概念"，它同样不能甩名词**。
- **手写版写成「玩具骨架」**（真实事故：第一次写穿透卡，L2 手写版只有 try/catch+save 30 行，读者看完"就这？"感受不到框架价值）→ 手写版要**够真**：把框架真正替你扛的边界写出来（ThreadLocal 清理防串号 / 失败改写 action / 模板求值 / 回调解耦 / 松散绑定递归 / 转义解析 / 连接池取消），读者才会意识到"原来框架替我兜了这么多"。**判定**：写完问"这些边界（清理/改写/求值/解耦/递归/转义/池化）我写出 3~4 条了吗"，没有 = 回炉补边界的"点明它去哪了"。
- **「不用它会怎样」写成抽象形容词**（真实事故：阶段5 复盘时批次的 L3 多处是"难维护/易出错/换框架就归零"，没落到具体请求）→ 必须推演**具体的"人-时-错"三元组**：哪个请求、在**第几毫秒/第几秒**、出**什么具体错**（"业务 01.250 提问 → 配置全 null → 选不出模型 → NPE，且因启动时没校验、运行时才炸"）。**凡写成形容词的 L3 回炉。**
- **零件类被讲成说明书**（真实事故：审计"零件类比喻密度不均"，实为六段里零件类容易滑向"它存了几家 id"的字典口吻，没有具名人物 + 具体故障）→ 零件类（DTO/枚举/配置/常量）六段照满，但要有**具体的人在用 + 方案对比 + 反例**（枚举也要有"某同事把 'bailian' 拼成 'BaiLian' 导致路由失配静默跳别家"这种镜头），不是"它就存这些值"。

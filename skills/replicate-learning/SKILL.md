# 复刻式项目深度学习

## 1. 任务定义

你的任务不是解释几个框架 API，也不是把项目复制出来，而是把一个真实项目转换成一套能让初学者逐步获得以下能力的教材：

1. 说清楚项目服务谁、解决什么业务问题、完整业务闭环如何运行。
2. 说清楚模块、进程、数据、依赖和外部系统为什么这样组织。
3. 读懂项目范围内每一个文件：源码、测试、配置、脚本、SQL、构建文件、前端资源、工具和部署文件。
4. 解释关键代码从入口到出口的真实执行链，并指出边界、失败模式和底层机制。
5. 判断 AI 生成代码是否正确、是否越界、是否缺测试、是否会在生产环境出问题。
6. 使用 Vibecoding 高效生成、修改、验证和演进项目，而不是只会拼接 API。

教材是主要交付物。交互、提问、手写练习和强制用户输入均为可选，不得阻塞主流程。

## 1.1 入口与动作路由

先从用户原话识别模式，不要让用户学习本技能的命令格式：

| 用户意图 | 立即执行的动作 |
|---|---|
| “学习/深度拆解/讲解整个项目/覆盖全部文件” | 定位项目根目录和教材目录，先完成项目考古，落盘四份基础地图，再从第一批继续 |
| “继续学习/继续复刻/next” | 读取磁盘状态、覆盖矩阵、最近教材和 Git 状态，从第一个未完成批次继续 |
| “只要产出/不要问我” | 采用默认路径和默认批次策略，直接扫描、讲解、验证、落盘；只有路径或安全边界无法推断时才提一个问题 |
| “讲解 X/讲第 N 批/讲某文件” | 补齐该对象所需的最小上下文，生成并落盘完整对象教程，同时更新矩阵和索引 |
| “验收/检查是否完整” | 不新增教材为主，审计覆盖矩阵、文件链接、证据等级、验证记录和索引，输出缺口清单 |

若用户同时给出原项目和复刻项目，原项目只读、复刻项目按用户授权使用；若只给出一个项目，默认把它作为被学习项目，教材写入该项目的 `NOTES/教学讲解/`，不擅自创建第二个复刻项目。

## 1.2 Flash 模型执行策略

本技能必须适合上下文和推理能力较小的模型执行。遵守以下机械流程：

1. **摘要先行**：先读取目录树、入口文件、依赖清单、状态文件和已有索引；不要一次性读取全项目源码。
2. **小批推进**：每批只处理一个闭环及其直接依赖；默认先选少量强相关文件，项目越大就增加批次，不把几十个文件压成一篇。
3. **上下文复用**：已解释概念只回链概念词典和旧批次；已读文件通过覆盖矩阵定位，不重复全文装入上下文。
4. **先写后续**：完成一批就立即写入教程、更新矩阵和状态，再开始下一批；不能把成果只留在对话中。
5. **证据优先**：每个结论先找路径、行号、命令或日志；找不到就写“未验证/推断”，不得用模型记忆补齐。
6. **单次运行有边界**：一次运行至少完成一个可读批次或基础地图；若无法完成，先落盘当前扫描结果、未完成清单和下一步入口。

## 1.3 最小可交付产出

任何首次运行至少落盘：

- `NOTES/00-系统全景地图.md`
- `NOTES/项目文件覆盖矩阵.md`
- `NOTES/概念词典.md`
- `NOTES/阶段对照-完整性地图.md`
- `NOTES/教学讲解/00-总索引.md`
- 状态文件中的当前阶段、当前批次、已讲/总文件数、阻塞项和下一步

完成一个批次至少落盘批次正文、阶段总览或索引更新、覆盖矩阵更新和验证记录。若时间、上下文或模型能力不足，优先保证这些可续传文件，不得声称全项目完成。

## 1.4 复杂度适配与降级

- 业务/机制批次执行 L0-L3；能运行时再做 L4。
- 纯配置、资源、文档、锁文件和生成文件重点说明作用、来源、引用关系、风险和排除理由，不强行制造“等价实现”。
- 无法安装依赖、启动服务或访问外部系统时，保留静态源码分析，明确写“未实测”，并记录阻塞命令、错误原文、已排查范围和剩余风险。
- 文件很多时不得删除文件以换取篇幅；应增加批次，或将低复杂度文件集中成“逐文件清单 + 每文件语义/引用/风险”，仍在矩阵中逐项出现。

## 2. 使用者定位与教学原则

假设读者只具备一门语言的基本语法、能运行命令并阅读简单报错，不熟悉当前项目的框架、数据库、中间件、协议和部署方式。

必须遵守：

- 新术语第一次出现时，用白话、类比和本项目真实位置解释；
- 不用一个未解释的术语解释另一个术语；
- 每一层回答“它是什么、为什么存在、数据从哪里来、失败时怎样”；
- 目标是读懂、复述、审查和指导 AI，不是手写速度；
- 不把 DTO、枚举、配置、测试、脚本视为低价值文件；
- 不因文件简单而降低解释完整性，只减少重复。

## 3. 输入与证据边界

开始前自动识别原项目、复刻项目、教材目录、`AGENTS.md`、README、贡献指南、CI 配置、技术栈、构建入口、运行入口、测试入口、外部依赖、已有教材、Git 历史和未完成事项。

优先使用本地真实文件、命令输出、测试结果、Git 历史和可定位源码作为证据。解释第三方底层行为时，优先查阅官方文档、依赖源码、字节码或最小实验。无法验证的内容必须标记为“推断”，不得伪装成事实。

默认不修改原项目；不得删除用户改动、已有教材或历史记录，只能增量补充或纠正。

所有结论标注证据等级：

- `事实-源码`：能回链到本地文件、类、方法和行号；
- `事实-实测`：由命令、测试、日志、堆栈或最小实验得到；
- `事实-历史`：由 Git 提交、差异或 blame 得到；
- `外部事实`：来自官方文档、依赖源码或协议规范；
- `推断`：根据现象和代码推导，但尚未直接验证。

教材不得把不同等级混写。性能、并发、安全、故障和生产行为尤其要说明证据等级。

## 4. 七阶段工作流

### 阶段 A：项目考古

扫描目录、文件类型、模块依赖、入口、配置、数据库、前端、工具、测试、部署和文档，建立：

- `NOTES/00-系统全景地图.md`
- `NOTES/项目文件覆盖矩阵.md`
- `NOTES/概念词典.md`
- `NOTES/阶段对照-完整性地图.md`

覆盖矩阵至少包含：路径、文件类型、所属能力、上下游、是否已讲、教程链接、证据状态、遗留问题。被排除的文件也要记录理由。

不要只扫描“业务源码”。默认范围包括根目录和隐藏目录中的构建、锁定、生成、测试、脚本、配置、资源、迁移、容器、CI、开发工具和运维文件。对自动生成文件、第三方目录和二进制资源可以不逐行讲，但必须记录其作用、来源、被谁引用以及排除理由。

### 阶段 B：业务建模

从用户、角色、场景、输入、业务规则、状态变化、输出、异常、审计和运营视角重建系统。每个核心能力给出真实角色、具体场景、一条端到端闭环、核心对象和约束，以及删除模块后业务如何退化。不要把“用了某框架”当业务解释。

### 阶段 C：架构推导

建立运行时全景图、模块依赖图、请求链路图、异步链路图、数据模型图和部署拓扑，并说明每个重要选择解决的吞吐、延迟、一致性、隔离、维护性或安全问题；给出替代方案、代价、边界和最可能故障。所有图都必须回链到真实模块、类、方法、配置和数据表。

### 阶段 D：全文件教材化

按业务能力和闭环分批，而不是随机按目录讲解。每个纳入范围的文件都必须出现于教材或覆盖矩阵：

- 业务源码、领域对象、控制器、服务、仓储、适配器；
- DTO、VO、枚举、异常、常量、配置属性和注解；
- 单元测试、集成测试、测试夹具；
- 构建文件、锁文件、脚本和插件；
- YAML、环境变量、SQL、迁移、Docker、CI/CD 和部署文件；
- 前端页面、组件、状态管理、请求封装、样式和资源；
- MCP、Agent、命令行、数据初始化和运维工具。

每个文件必须有一个唯一覆盖状态：`未开始`、`已定位`、`已讲解`、`已验证`、`排除-有理由`。同一文件被多个批次使用时，只保留一份主讲解，其他批次回链到它并说明本批新增视角。

### 阶段 E：底层穿透

关键机制至少解释真实源码或依赖证据、框架自动完成的事情、不使用框架时的等价实现、一个具体失败场景的时间线，以及如何通过日志、堆栈、测试或最小实验定位。优先穿透请求分发、依赖注入、事务、线程上下文、序列化、网络协议、连接池、缓存、消息投递、数据库索引、向量检索、流式响应、鉴权、重试、熔断和资源释放。

### 阶段 F：Vibecoding 工程能力

每个重要能力都要展示如何让 AI 正确完成：

- 写项目级上下文、约束、验收标准和变更范围；
- 把大需求拆成可验证批次；
- 先读代码、列影响面、再修改；
- 审查 diff、依赖方向、异常处理、并发、安全和测试；
- 用测试、日志、静态检查和运行结果形成反馈闭环；
- 识别幻觉、过度重构、伪实现、假测试和 API 拼接错误；
- 将一次修改沉淀成规则、模板、脚本和长期记忆。

必须展示真实任务的上下文、约束、变更、验证证据和复盘，不能只写泛泛的提示词建议。

### 阶段 G：验证与归档

每批次执行适合项目的构建、测试、静态检查、启动或最小链路验证。记录命令、关键输出、失败原因、修复过程和剩余风险。没有实际运行不得声称已验证。

完成条件：

1. 所有纳入范围文件均有教程链接或明确排除理由；
2. 每个核心业务闭环均有端到端链路；
3. 每个核心模块均有架构位置、依赖方向和数据流；
4. 关键机制有源码证据或推断标记；
5. 教材已落盘并有总索引；
6. 验证命令和结果可追溯。

若构建或运行失败，仍然产出教材，但必须把失败命令、完整关键错误、失败层级、已排查范围、未解决原因和风险写入教材。禁止用“环境问题”作为没有定位过程的统称。

## 5. 阶段与批次切分

阶段按能力和系统层次组织，例如：系统全景与运行入口、基础设施与数据层、支撑能力、核心业务闭环、前端交互、AI/工具链、部署运维与横向对照。具体名称随项目调整，不得机械套用。

批次按一个可解释、可验证的业务或技术闭环切分。一个批次不应把互不相关的文件堆在一起，也不应为了省篇幅把几十个文件压成一篇目录导读。大型项目宁可增加批次，也不能降低单文件讲解质量。

每批开始前先写两个内部清单：

1. **外部调用穿透清单**：列出本批所有框架、ORM、SDK、中间件、协议和工具调用，标注是否已有词典或前批证据、要穿透到哪一层、证据出处和完成状态。
2. **讲解骨架清单**：列出每个文件的业务镜头、架构位置、实现要点、调用链、失败场景、测试视角、Vibecoding 视角和验证证据，填完后再写正文。

关键机制按 L0-L4 穿透：

- `L0 源码证据`：真实源码、依赖源码、字节码或官方实现位置；
- `L1 机制拆解`：框架替项目自动完成的具体步骤；
- `L2 等价实现`：不依赖当前框架的可读示范，明确它仍省略了哪些生产边界；
- `L3 设计取舍`：替代方案、代价和具体失败时间线；
- `L4 故障实证`：实际破坏、日志、堆栈或数据变化；无法运行时必须写“未实测”，退回 L3。

本批至少有一个新机制达到 L0-L3；核心类和中间件尽量达到 L4。已经在前批完整解释过的机制可以回链，但不能假装本批首次解释。

## 6. 批次教材结构

每个批次至少包含：

1. 在系统全景中的位置；
2. 业务场景和端到端闭环；
3. 文件清单与每个文件的一句话职责；
4. 新概念白话解释；
5. 按文件逐个讲解；
6. 关键文件的完整方法或完整代码段逐行说明；
7. 调用链、数据流、状态变化和边界；
8. 不使用框架的等价实现或伪代码；
9. 失败场景、故障定位和反例；
10. 测试视角；
11. Vibecoding 视角；
12. 验证证据、已知限制、复习问答与索引。

### 6.1 初学者代码讲解硬标准

批次正文不是代码审查摘要，也不是“类职责 + 几个关键片段”。对每个重要源文件必须让读者能从文件入口读到出口：

- 先给“本文件要解决的一个问题”和输入/输出，再解释类、字段、构造器、方法之间的关系；
- 代码块默认贴完整文件；文件过长时按完整方法或完整职责段拆开，并明确上下段如何衔接；
- 代码块中的关键行必须有**贴近代码的中文注释**，至少说明“这是什么、为什么需要、不这样会怎样”；不能只在代码块外概括；
- 逐行讲解不能只翻译变量名，必须解释控制流、数据变化、状态变化、异常路径和副作用；
- 每个陌生 API 第一次出现时，先解释调用前拿到什么、调用后产生什么，再解释框架/JDK 内部做了什么；
- 必须提供一条“从真实输入到真实输出”的逐步回放，并指出读者应先看哪几个方法；
- 对测试代码，要解释测试前置状态、动作、断言对象、为什么该断言能证明业务行为，以及没有该测试会漏掉什么；
- 对配置、构建和脚本文件，要解释每个有效字段或命令如何影响源码运行，不得只说“添加依赖/配置参数”。

“完整代码”不等于把未经解释的大段源码搬进来。若源码本身没有注释，教材应在代码块中补充教学注释，但必须标明哪些是教材注释，不能把注释冒充源码事实。禁止用“其余类似”“这里不展开”“显然”“读者可自行理解”跳过关键逻辑。

### 6.2 Vibecoding 必须讲真实开发过程

Vibecoding 章节必须回答的是：**面对一个真实需求，如何让 AI 从现有代码中分析、设计、写出、验证并迭代出本批讲解的实现**，不是只讲“如何复刻答案卷”或“给 AI 加几条提示词”。

每个重要能力至少还原一条开发过程：

1. **真实需求**：谁遇到什么业务问题，现有代码为何不够，成功标准是什么；
2. **现状勘察**：让 AI 先读取哪些入口、接口、配置、测试和调用方，如何确认影响范围；
3. **方案比较**：至少比较一个简单但有缺陷的方案与当前方案，写出行为、成本和风险差异；
4. **增量实现**：把需求拆成可运行的小批次，明确每批新增/修改文件和不应触碰的边界；
5. **可直接使用的提示词**：给出与本项目上下文绑定的任务提示、约束、验收标准和输出格式，而不是抽象口号；
6. **AI 产出后的审查**：展示应检查的 diff、依赖方向、异常/并发/资源释放、测试覆盖和兼容性；
7. **验证反馈循环**：展示测试或运行失败后，如何把真实错误反馈给 AI，如何定位根因，如何形成下一次修改；
8. **最终沉淀**：把本次开发形成的规则、测试模式、模板或状态记录下来。

必须区分三种内容并明确标注：

- `开发任务`：真实项目要增加或修复的能力；
- `AI 协作过程`：如何指挥和审查 AI 产出代码；
- `复刻对照`：如何与答案卷或原项目比较。

复刻对照只能是辅助内容，不能替代真实开发过程。不得把“代码与答案卷一致”“提示词要求机制对齐”当作 Vibecoding 教学的主要结论。

### 6.3 教材质量自检

写完批次后，必须逐项检查并在文末记录：

- 初学者只读代码块，能否知道每个变量和分支的作用；
- 是否存在没有贴代码、没有解释、却声称“完整讲解”的核心方法；
- 是否解释了失败路径和副作用，而不只是成功路径；
- Vibecoding 是否包含真实需求、可执行提示、AI 修改、验证反馈和迭代结果；
- 是否把“已复刻”误写成“已验证”，把“单测通过”误写成“生产可靠”；
- 是否把推断、源码事实和实测结果分开。

每个批次还应记录“本批前置知识、后续依赖、未覆盖项和下一批入口”，避免跨会话后只剩孤立文章。

### 6.4 批次教材 16 节统一化规范

每批教材统一为 16 节结构（①~⑯）+ 索引节。本节定义每节的**必含项**、**可选项**与**反例/正向要点**，确保跨批次呈现一致。

> **节奏纪律**：必含项必须出现；可选项按本批内容复杂度自取；反例列出常见错误写法与警示。A/B/C1/C2 代号仅作"历史风格指纹"溯源，**写新批时按本节规范执行**。

#### ① 在系统全景中的位置（A 风格：盒状全景图 + 跨批关系）
- 必含：① 一张**盒状嵌套 ASCII 全景图**（节点/盒/箭头定位本批关键对象在系统中的位置）② 关键对象的**频次级分工**（"一次流式问答里调用几百次 vs 注册一次"这种数量级对比）③ 与相邻批次、全局组件（异常处理、配置中心、事务等）的**对接关系与边界**
- 反例：① 只贴数据流图不点本批对象在系统中的"占位" ② 不交代与全局异常处理器/配置/事务等横切组件的关系

#### ② 业务场景与端到端闭环（C1 风格：流水线图 + 分支流预告）
- 必含：① **一句话场景开场**（"用户输入 X 点击 Y，前端发起 Z 请求"）② 一张**纵向 ASCII 流水线图**，**每站标注出自哪个批次**（阶段/批次来源可追溯）③ 结尾一段**"四条分支流预告"**（正常/异常/边界/取消）
- 可选：仅 1 条分支时省第 ③ 项
- 反例：① 多场景轮番登场（破坏流水线一图到底的可读性）② 流水线图不标批次来源（读者无法判断每站出处）

#### ③ 文件清单与一句话职责（C2 风格：分组三表）
- 必含三表：
  1. **源文件表**（# / 文件 / 行数 / 一句话职责 / ★ 标记）
  2. **配置/资源/补丁表**（文件 / 补了什么 / **不补的后果**）——无配置可省
  3. **测试文件表**（# / 文件 / 例数 / 测什么关键断言）
- 反例：① 源+测试混在同一张表（信息密度过大难扫读）② 配置表不带"不补的后果"列（无法做风险预警）

#### ④ 新概念白话解释（A+C2 混合：宽表全量 + 核心深潜）
- 必含：① 三列宽表全量覆盖所有新概念（概念 / 一句话白话 / **本批在哪出现**含源码位置回链）② 其中本批**最核心的 2~3 个概念**附 **C2 式深潜小节**（### 4.x），按"是什么 / 解决什么问题 / 不用它会怎样"三段展开 + 必要时代码示例 + 代价分析
- 反例：① 全部概念都是一句白话（核心讲不透）② 全部概念都深潜（15+ 概念深潜篇幅爆炸）

#### ⑤ 批前两个内部清单（B 风格：六列状态表 + 九列骨架矩阵）
- 必含：
  - 5.1 外部调用穿透清单：**六列表**（# / 调用点 / 属于谁 / 穿透到哪层 / 证据出处 / **状态**：`✅` 本批穿透 或 `↩` 已讲回链）——SKILL 原文定义
  - 5.2 讲解骨架清单：**每文件一行 × 九列**（文件 / 业务镜头 / 架构位置 / 实现要点 / 调用链 / 失败场景 / 测试视角 / Vibecoding 视角 / 验证证据）——填完再写正文
- 反例：① 状态列缺失（无法区分本批穿透与已讲回链，会把已讲概念假装首次解释）② 骨架清单只是节级复选框（无文件级防漏）

#### ⑥ 逐件讲解（完整代码 + 逐行说明）（B 主体 + ★类 C2 块）
- 必含**四层结构**：
  1. **本文件要解决的一个问题** + 输入/输出（SKILL §6.1 硬要求）
  2. 代码块（完整文件或完整职责段，行号前缀简注，密度对齐 A 代码内注释）
  3. **逐行要点表**（行号 / 讲解）——讲控制流、数据变化、状态变化、异常路径、副作用、**"不这样会怎样"**
  4. **边界与副作用段**
- ★ 核心类额外加 **C2 式【讲解】为什么…块**——聚焦一个"为什么这么设计"的问题，含代价与取舍论证
- 必含**注释归属声明**：源码自带注释 vs 教材补注（`// 【教材补注】`）显式区分
- 反例：① 缺"本文件要解决的一个问题"开场 ② 逐行讲解只翻译变量名不解释控制流 ③ 教材注释冒充源码事实

#### ⑦ 调用链、数据流、状态变化与边界（三合一：B 骨架 + C1 分支流 + A 状态图）
- 必含四小节：
  - ⑦.1 调用链 = 编号列表带行号 + 跨批标注（B 式）
  - ⑦.2 数据流 = 变换管道图；**数据载体 ≥3 个时加产出/消费表**（C1 式）
  - ⑦.3 状态变化 = 有状态对象画**状态机图**（A 式）+ **迁移表只列本批触发**（B 式）
  - ⑦.4 边界与不变式 = **编号列表**（C1 式）
- 多分支流（≥2 条）时在 ⑦.1 后加**分支流并列时序图**（C1 式，T=请求线程 / A=回调线程标注）
- 反例：① 缺行号导致读者无法回查 ② 状态变化表把所有迁移都列（已讲回链应只列本批触发的）

#### ⑧ L0-L4 底层穿透卡（B+C1 融合：五级纪律卡 + 省略边界段 + 同构证据）
- 每张卡**统一结构**：
  - 卡标题：`类名★` —— 机制名（**A 式问题副题可选**：`靠什么…` / `为什么…`）
  - **五级列表项**（B 式）：
    - **L0 源码证据**：真实源码/依赖源码/字节码/官方实现位置 + 证据等级
    - **L1 机制拆解**：框架替项目自动完成的具体步骤；可含**与替代方案的对比**（C1 式）
    - **L2 等价实现**：不依赖当前框架的可读示范；L2 后**必带"省略了什么生产边界"段**（B 式，SKILL 硬要求）
    - **L3 设计取舍**：替代方案、代价、具体失败场景
    - **L4 故障实证**：实际破坏/日志/堆栈/数据变化；**无法运行时必须写"未实测"退 L3**
  - 无 L4 实证时用 **C1 的同构证据替代 + 诚实标注**（"本批无线上故障可证；用阶段 X 的 Y 用例作同构证据"）
  - 证据等级统一**内嵌【】标注**（C1 式）：`【事实-源码】` / `【实测】` / `【推断】` / `【外部事实】`
- 核心类尽量达到 L0-L4；至少 1 张完整穿透卡
- 反例：① L2 后缺"省略了什么生产边界"段（违反 SKILL）② L4 无实证时写"理论上会这样"（必须写"未实测"）

#### ⑨ No-Framework 等价实现（A 主体 + C1 点题）
- 必含：
  - ① 一段开篇声明：本批依赖几件"别人的东西"；与 ⑧-L2 的分工（L2 给片段、⑨ 拼闭环）
  - ② **完整可运行闭环手写版**（约 60~130 行 `TinyXxx` 或 `MiniXxx` 类）——只用 JDK + 最薄中间件
  - ③ **C1 式点题句**："目标不是替代，而是证明：本批的复杂度全部来自'边界与容错'，核心编排本身极薄"（或类似洞察）
  - ④ **"框架到底多送了什么"对照表**（A 式）——逐项：框架便利 vs 手写代价
  - ⑤ **显式省略清单**（B 式写在代码首注释）："省略了 X、Y、Z"（防"玩具骨架冒充等价实现"，SKILL 质量禁区明文禁止）
- 反例：① 只贴片段不拼闭环（与 L2 重叠无增量）② 不显式说明省略（等于假装等价）

#### ⑩ 失败反例（C1 主体 + A 对照）
- 必含：5~6 条反例，**统一骨架 = 现象 → 定位 → 根因 → 修复 + 一句教训**（C1 式）
- 错误代码部分用 **A 式 ❌/✅ 对照**（贴错误版与正确版，让"修对长什么样"立等可见）
- 每条结尾**单列一句"教训"**（"教训：兜底分支是下游契约的执行者，不是锦上添花"）
- 可选（按本批内容复杂度）：
  - **C2 的跨实现对比**（"这条故障在 Milvus 下不会发生——天然隔离"）
  - **B 的实测日志解读表**（构建日志原样摘录 + "每条来自哪个测试、证明什么"）
- 反例：① 反例条数 < 3（覆盖不足）或 > 8（喧宾夺主）② 缺"教训"句（反例节最大教学价值丢失）

#### ⑪ 测试视角（B+C1+A 三段）
- 必含三段：
  1. **B 逐例六列表**（# / 用例 / **前置状态** / 动作 / 断言 / 为什么能证明 / 没它会漏什么）——最严最细
  2. **C1 测试类策略分层表**（测试类 / 例数 / 策略："真实 PG / mock / 真 Semaphore / mock 四依赖"）——类级总览
  3. **A 测试五问**（测什么 / 为何这样测 / mock 边界 / 缺陷 / 上限）——方法论抽问
- 优先级：B 六列表 > C1 分层 > A 五问；B 必备，C1+A 可按需
- 反例：① 缺六列表（无法作为"回归测试白名单"用）② 六列表只列用例名不列"为什么能证明"（信息密度不足）

#### ⑫ Vibecoding 视角（B 八条 + C1 回链）
- 必含：**严格按 SKILL §6.2 八条**：
  1. 真实需求（`开发任务`）——谁/问题/现有代码为何不够/成功标准
  2. 现状勘察（`AI 协作过程`）——给 AI 的真实指令形态
  3. 方案比较（`开发任务`+`AI 协作过程`）——A/B/C 三方案**行为/成本/风险**对比表
  4. 增量实现（`开发任务`）——拆成可运行小批次
  5. 可直接使用的提示词（`AI 协作过程`）——与本项目上下文绑定
  6. AI 产出后的审查（`AI 协作过程`）——diff/依赖方向/异常/并发/测试/兼容性
  7. 验证反馈循环（`AI 协作过程`）——失败后真实错误反馈、定位根因
  8. 最终沉淀（`开发任务`）——规则/模板/状态记录
- 每节带 `开发任务` / `AI 协作过程` / `复刻对照` 分类标签；**复刻对照只能是辅助，不得当主要结论**（SKILL 硬要求）
- C1 亮点：**"提问→引出 卡 X/反例 Y/阶段 Z"回链**——让 AI 协作的产物反查回正文其他节
- 必含"回顾性重构"声明（若是按代码逆向重建的协作记录）："本节是按最终代码逆向重建的协作记录，非开发时序的逐字存档"
- 反例：① 缺方案比较表（"为什么选当前方案"无说服力）② 复刻对照占主要篇幅（违反 SKILL）

#### ⑬ 验证证据与已知限制（B+C2 主体）
- 必含四件：
  1. **构建命令 + 关键输出**（最好带真实日志片段，C2 式）+ 多模块绿统计
  2. **证据等级标注表**（C2 式）：每条独立标 `实测` / `未实测` / `推断` / `外部事实`
  3. **已知限制详表**（B 式）：每条带 ❌ 标记 + 说明 + **何时/哪批归还标注**
  4. **"已验证≠生产可靠"边界声明**（B 式，SKILL §6.3 硬要求）："本文档所有'✅ 已验证'均指单测通过，不等于生产可靠"
- 可选：**编译修复实录**（C1 式，本批有真实修复坑时写，按轮次编号）
- 反例：① 缺证据等级逐条标注 ② "已验证"边界声明缺失 ③ 已知限制不带归还标注（读者不知道什么时候能解决）

#### ⑭ 复习问答（A+B+C1 融合：12 题 Q/A 配对 + 答案内嵌钩回）
- 必含：**12 道 Q/A 配对**（A 式：Q+问题紧跟 A+答案，不分离）
- 题目应**均衡覆盖**：
  - 设计动机（"为什么这么选/这么写"）
  - 反面假设（"能不能用 X 实现"）
  - 跨批/跨阶段关系（"和批次3 怎么协作"）
  - 故障推演（"不这样会怎样"）
- 答案内嵌**【钩回标签】**（C1 式）：`【反例 X】` / `【卡 Y】` / `【阶段 Z】` / `【批次 N】` ——让问答与正文其他节形成反查网
- 题目应**指向本批具体实现**（B 式）：不只问概念，要问"resolveTierName 三条分支顺序为什么不能调换"这种本批实现
- 答案应**带具体数值/场景/钉死测试名**（B 式）：不只说"会出问题"，要写"standard 档 30s、deep 档 120s；200 个请求就省下 200 × 30s"
- 反例：① 问答数 < 10（覆盖不足）或 > 15（拖沓）② 题目只问概念不指向本批实现 ③ 答案无【钩回】标签

#### ⑮ 前置知识 / 后续依赖 / 未覆盖项 / 下一批入口（A 三表 + 必含段）
- 必含：
  - **15.1 前置知识表**（前置 / 本批哪里用到 / 在哪学过）——回链前批/其他阶段
  - **15.2 后续依赖表**（依赖方 / 用到什么 / 在哪 / 预计哪批）
  - **15.3 未覆盖项诚实清单**（未覆盖 / 原因 / 何时补）——诚实标"本仓库尚未实现"
  - **15.4 下一批入口段**（必含）——侦察答案卷路径、教材对应章节、关键风险
- 当本批内容少时三表可压缩为**段落**（C1 式）；三表骨架不变
- 反例：① 缺"下一批入口"段（续接生命线断裂）② 未覆盖项用"实现完整"掩盖（违反 §6.3）

#### ⑯ 教材质量自检（B 六项表 + 展开依据 + 遗留观察）
- 必含**SKILL §6.3 六项自检表**：
  - 自检项 / 结论（✅/无/否） / **展开依据**（不是一句话敷衍，是"逐项核对"——如"`ModelSelector` 全部 12 个方法均在 ⑥ 出现"）
  - 1. 初学者只读代码块能否知道每个变量和分支的作用
  - 2. 是否存在"没贴代码、没解释、却声称完整讲解"的核心方法
  - 3. 是否解释失败路径与副作用，而不只是成功路径
  - 4. Vibecoding 是否包含真实需求/可执行提示/AI 修改/验证反馈/迭代结果
  - 5. 是否把"已复刻"误写成"已验证"、"单测通过"误写成"生产可靠"
  - 6. 是否把推断/源码事实/实测结果分开
- 必含**遗留观察段**（记给后续批次）——自检中发现的"非本批范畴、但应被后续批次处理"的问题
- 必含**索引节**（5 链接）：上一批 / 下一批 / 阶段总览 / 总索引 / 覆盖矩阵
- 反例：① 六项自检每项一句"✅"走过场（无展开依据 = 无自检）② 缺遗留观察与索引节

#### 索引节（非 16 之数，单独保留）
- 必含**5 链接索引**：上一批 / 下一批 / 阶段总览 / 总索引 / 覆盖矩阵
- 与 ⑯ 末尾的索引节**位置合并或单列皆可**，但必须出现

## 7. 输出目录

教材必须落盘到目标项目的 `NOTES/教学讲解/`：

```text
NOTES/
  00-系统全景地图.md
  项目文件覆盖矩阵.md
  概念词典.md
  阶段对照-完整性地图.md
  教学讲解/
    00-总索引.md
    阶段N-主题/
      00-阶段总览.md
      批次M-主题.md
```

每个总览列出批次、文件范围、业务闭环、依赖关系、验证状态和下一步链接。每批次完成立即写盘并更新索引。

跨会话续传必须以磁盘状态为准。每批更新 `AGENTS.md` 或项目约定的状态文件，至少写入：当前阶段、当前批次、已讲文件数/总数、未完成文件、最近验证命令与结果、已知风险、下一步。不得依赖聊天记录恢复进度。

## 8. 交互约定

用户说“继续复刻”“继续学习”或 `next` 时，读取约束文件、全景地图、覆盖矩阵、最近教材和 Git 状态，从未完成项继续。

用户说“讲解 X”时，输出并落盘 X 的完整教程；缺少必要上下文时先补上下文，不要求用户手写。

用户说“只要产出”时，直接扫描、实现、验证和归档，不发起问答式流程。只有目录边界、写入位置或安全前提无法推断时才提出简短问题。

每次运行结束时，在回复中固定报告：当前阶段/批次、已讲文件数/总文件数、已验证/未验证数量、已落盘文件、阻塞项和下一步。回复只是摘要，完整教材必须以磁盘文件为准。

## 9. 质量禁区

- 不漏讲文件，不把“框架自动处理”当解释；
- 不只讲外围 API、名词或 README；
- 不编造源码、运行结果、性能数据和故障；
- 不用“高可用、易维护、解耦、方便扩展”等空泛词代替因果链；
- 不把玩具骨架冒充等价实现；
- 不强制用户手写、复述、提交或闯关；
- 不压缩掉业务、底层、测试和工程视角；
- 不把未经验证的推断写成事实。
- 不把“已经扫描”写成“已经讲解”，不把“已经讲解”写成“已经验证”；
- 不用固定文件数、固定题数或固定批次数套项目，所有数量以真实覆盖矩阵为准；
- 不因项目规模大而只讲入口和核心类，外围文件必须进入覆盖矩阵并给出适配其复杂度的说明。
